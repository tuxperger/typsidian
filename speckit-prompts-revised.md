# Spec Kit — команды и промпты (пересмотрено)

## 1. `/speckit.constitution` — один раз на проект

```
/speckit.constitution
Проект: локальный, local-first редактор заметок на языке Typst (аналог
Obsidian). Клиенты: web (Next.js), desktop и mobile (Tauri) — общий
UI-код. Общее Rust-ядро (packages/core) компилируется в WASM для веба
и нативно для desktop/mobile.

Принципы (MUST, если не указано иное):
1. Вся бизнес-логика (компиляция Typst, парсинг ссылок, построение
   графа, vault-manager) живёт только в packages/core и покрыта
   тестами (cargo test, wasm-bindgen-test). UI не дублирует эту логику.
2. Любое изменение в packages/core обязано собираться и под
   wasm32-unknown-unknown, и под нативный таргет — иначе фича не
   считается готовой.
3. spec.md описывает только наблюдаемое пользователем поведение —
   без упоминания конкретных API, библиотек или файлов. Технические
   решения — только в plan.md.
4. Фронтенд на TypeScript strict, без any.
5. Изменения, затрагивающие msgpack-rpc мост к Neovim, — зона
   повышенного риска: перед /speckit.plan обязателен отдельный
   /speckit.clarify.
6. Данные пользователя (vault) остаются локальными файлами на диске;
   синхронизация — опциональная фича (SHOULD), не блокирует базовый
   функционал.
7. Любая фича с сетевым взаимодействием обязана корректно
   деградировать в офлайне — это local-first приложение.
```

## 2. `/speckit.specify` — что строим (без технологий)

```
/speckit.specify
Vault manager: пользователь открывает папку с заметками как vault.

Пользовательский сценарий:
- Пользователь выбирает папку на диске — приложение находит все
  заметки в ней (рекурсивно, включая вложенные папки) и показывает
  их в дереве файлов.
- Если файл в vault создан, изменён, переименован или удалён вне
  приложения — приложение обнаруживает это и обновляет своё состояние
  без перезапуска.
- Пользователь может создать, переименовать и удалить заметку прямо
  из интерфейса приложения.
- Если заметка, которую пользователь сейчас редактирует, была изменена
  на диске снаружи — пользователь предупреждён и выбирает: оставить
  свою версию, принять внешнюю, или посмотреть diff.
- Удаление заметки, на которую ссылаются другие заметки, не проходит
  молча — пользователь видит, какие заметки останутся с "битой" ссылкой.

Вне скоупа этой фичи: синхронизация между устройствами, история версий
файла.
```

## 3. `/speckit.checklist` — проверка качества спеки (новый шаг)

```
/speckit.checklist
Сгенерируй чеклист для проверки полноты спецификации vault-manager
с фокусом на: (1) поведение при потере доступа к диску/разрешений
на web, (2) конкурентные изменения одного файла из нескольких
вкладок/окон приложения, (3) производительность на vault с 10000+
заметок.
```

Можно вызывать не только сразу после specify, но и повторно после
plan — как QA-гейт с другим углом (например, "чеклист по безопасности"
перед implement).

## 5. `/speckit.plan` — как строим (технологии здесь, не в specify)

```
/speckit.plan
Технический план:
- Vault-manager реализуется в Rust (packages/core) с единым трейтом
  VaultBackend и двумя реализациями:
  - NativeBackend — крейт notify для FS-watcher, доступ к файловой
    системе через Tauri fs API (desktop/mobile).
  - WebBackend — File System Access API, подписка на доступные
    события изменений плюс периодическая сверка.
- Внутреннее состояние — in-memory индекс путей и метаданных.
  Персистентный кэш — SQLite (sqlx нативно, wa-sqlite в вебе), чтобы
  не пересканировать vault полностью при каждом запуске.
- Конфликт "файл изменён на диске, пока открыт в редакторе" —
  сравнение mtime/hash при событии изменения; если в буфере
  редактора есть несохранённые правки — эмитим событие в UI для
  диалога выбора, не решаем автоматически.
- Публичный API одинаков для всех таргетов — единый Rust-трейт,
  платформенные различия скрыты за ним.
```
