# Typsidian Constitution

Typsidian — локальный, local-first редактор заметок на языке Typst (аналог Obsidian).
Клиенты: web (Next.js), desktop и mobile (Tauri) с общим UI-кодом. Общее Rust-ядро
(`packages/core`) компилируется в WASM для веба и нативно для desktop/mobile.

## Core Principles

### I. Бизнес-логика живёт в ядре

Вся бизнес-логика MUST находиться только в `packages/core`. Сюда явно входят: компиляция
Typst, парсинг ссылок, построение графа, vault-manager. UI MUST NOT дублировать,
переизобретать или «подстраховывать» эту логику — он только вызывает ядро и отображает
результат.

Каждая единица логики ядра MUST быть покрыта тестами, проходящими и через `cargo test`
(нативно), и через `wasm-bindgen-test` (WASM). Логика без тестов на обоих путях не
считается готовой.

Обоснование: три клиента опираются на один поведенческий контракт. Вторая реализация в UI —
это второй источник истины, и они разойдутся молча и по-разному на разных платформах.

### II. Паритет двух таргетов (NON-NEGOTIABLE)

Любое изменение в `packages/core` MUST собираться под `wasm32-unknown-unknown` **и** под
нативный таргет. Фича, собирающаяся только под один таргет, не считается готовой: её MUST
NOT мержить и MUST NOT отчитываться о ней как о завершённой.

Платформенные различия MUST быть скрыты за общей абстракцией (трейтом) с одинаковым
публичным API на всех таргетах; условная компиляция допустима только внутри реализаций за
этой абстракцией.

Обоснование: в WASM нет окружающей файловой системы, по умолчанию нет потоков и доступен
урезанный набор крейтов. Обнаружить это к релизу — значит переделывать архитектуру, а не
чинить.

### III. Спецификация описывает только поведение

`spec.md` MUST описывать только наблюдаемое пользователем поведение: что пользователь
делает, что видит и какие гарантии даёт система. Он MUST NOT упоминать конкретные API,
библиотеки, крейты, фреймворки, пути к файлам и схемы данных.

Все технические решения — выбор крейтов, хранилище, форма API, раскладка модулей —
принадлежат `plan.md`. Спека, фиксирующая реализацию до появления плана, MUST быть
переписана.

Обоснование: смешение «что» и «как» закрепляет технологию до разбора компромиссов и делает
спеку нечитаемой для всех, кто ещё не принял эту реализацию как данность.

### IV. TypeScript strict, без any

Фронтенд MUST компилироваться в режиме TypeScript `strict`. Тип `any` запрещён; `@ts-ignore`
и `@ts-expect-error` запрещены как способ заглушить ошибку типов (допустимы только для
документирования известного дефекта во внешней зависимости).

Типы, пересекающие границу WASM/JS, MUST порождаться из определений Rust или сверяться с
ними. Ручные дубликаты типов ядра запрещены.

Обоснование: граница JS↔WASM не типизирована в рантайме. `any` на этом шве превращает
ошибку компиляции в падение прямо в редакторе пользователя.

### V. Мост к Neovim — зона повышенного риска

Любое изменение, затрагивающее msgpack-rpc мост к Neovim, MUST проходить отдельный
`/speckit-clarify` до запуска `/speckit-plan`. Переход к планированию в обход этого шага —
нарушение конституции, независимо от кажущегося размера изменения.

Обоснование: мост — асинхронный версионированный протокол к внешнему процессу, который мы
не контролируем. Неоднозначность здесь проявляется как потеря данных в буфере пользователя,
а не как ошибка сборки.

### VI. Данные принадлежат пользователю (local-first)

Vault пользователя MUST оставаться обычными файлами на диске, читаемыми и редактируемыми без
Typsidian. Приложение MUST NOT требовать сервер, аккаунт или проприетарный контейнерный
формат для того, чтобы открыть, отредактировать или сохранить заметку.

Синхронизация между устройствами — опциональная фича уровня SHOULD. Она MUST NOT быть
предусловием для базового функционала, и её отключение MUST оставлять приложение полностью
работоспособным.

Обоснование: local-first — причина существования продукта. Любая зависимость, делающая
заметки недоступными без нашей инфраструктуры, ломает главное обещание пользователю.

### VII. Корректная деградация в офлайне

Любая фича с сетевым взаимодействием MUST корректно деградировать при отсутствии сети: она
падает заметно для пользователя, сохраняет его данные и оставляет остальное приложение
рабочим. Молчаливые зависания, бесконечные спиннеры и потеря данных при обрыве связи — это
дефекты, а не краевые случаи.

Поведение в офлайне MUST проверяться тестами, а не только декларироваться в плане.

Обоснование: офлайн — штатный режим работы local-first редактора, а не аварийное состояние,
которое когда-нибудь обработают.

### VIII. Внешние движки — чёрный ящик с синхронизацией через vault

Любая фича, встраивающая сторонний движок (Excalidraw, draw.io, будущие интеграции), MUST
следовать паттерну «внешний движок + синхронизация состояния с файлом vault» — тому же, что
и мост к Neovim (принцип V). Движок владеет своим внутренним состоянием; приложение владеет
файлом; между ними — явный двусторонний контракт синхронизации, а не общая изменяемая
структура данных.

UI-обвязка вокруг такого движка MUST стилизовать только контейнер: тулбар, заголовок панели,
индикатор сохранения, рамку. Она MUST NOT перекрашивать, патчить или переопределять
внутренний DOM или iframe самого движка — ни глобальными CSS-селекторами, ни инъекцией
стилей внутрь, ни правкой его узлов из JS.

Обоснование: внутренний DOM встраиваемого движка — не его публичный API. Он меняется в любом
минорном обновлении, и стили, залезающие внутрь, ломаются молча — прямо в редакторе
пользователя. Граница «движок владеет пикселями, мы владеем файлом» оставляет обновление
зависимости рутинной операцией вместо разбора регрессий вёрстки.

### IX. Полная локальность поиска и индексов

Полнотекстовый поиск и любые локальные индексы MUST строиться и храниться целиком на
устройстве пользователя. Содержимое заметок MUST NOT покидать устройство — ни целиком, ни
фрагментами, ни в виде эмбеддингов, сводок или иных производных представлений.

Это ограничение распространяется и на будущие AI-фичи: функция, требующая отправки
содержимого заметок во внешний сервис, противоречит этому принципу и MUST NOT добавляться
без MAJOR-поправки к конституции, принятой явно.

Обоснование: обещание local-first (принцип VI) касается не только доступности файлов, но и
конфиденциальности. Индекс и эмбеддинги — это содержимое заметок в другой форме; отправка их
наружу нарушает то же обещание, что и загрузка самих файлов.

### X. Массовые операции — отменяемые и неблокирующие

Любая массовая операция (batch-экспорт, переиндексация vault, массовое переименование и
подобное) MUST быть отменяемой в середине выполнения и MUST NOT блокировать основной
UI-поток. Пользователь MUST видеть прогресс и MUST иметь возможность продолжать работать с
приложением, пока операция идёт.

Отмена MUST оставлять vault в предсказуемом состоянии: уже завершённые единицы работы
сохранены, текущая — либо завершена целиком, либо откачена целиком. Частично записанные
файлы после отмены недопустимы.

Обоснование: vault пользователя может содержать тысячи заметок. Операция без отмены на
таком объёме — это зависшее приложение, которое остаётся только убить, а убитая на середине
запись превращает потерю времени в потерю данных.

## Архитектурные ограничения

- **Ядро**: `packages/core` на Rust — единственное место бизнес-логики (принцип I),
  собирается в WASM (web) и нативно (desktop/mobile).
- **Клиенты**: web на Next.js; desktop и mobile на Tauri. UI-код общий для всех трёх;
  клиент-специфичный код ограничен платформенным связующим слоем.
- **Платформенные швы**: файловая система, вотчеры, персистентность и любая другая
  возможность, различающаяся по платформам, MUST находиться за трейтом, принадлежащим ядру,
  с одной реализацией на таргет. Вызывающий код MUST NOT ветвиться по платформе.
- **Данные**: vault — директория файлов на диске. Производное состояние (индексы, кэши)
  восстановимо и MUST NOT быть авторитетной копией чего-либо, написанного пользователем.
- **Внешние процессы**: msgpack-rpc мост к Neovim — единственная санкционированная
  интеграция с внешним процессом, регулируется принципом V.
- **Встраиваемые движки**: сторонний движок, работающий внутри клиента (полотно для
  рисования и подобные), изолируется как чёрный ящик и синхронизируется с файлом vault по
  принципу VIII. Его внутренний DOM/iframe не является поверхностью для стилизации.
- **Индексы и поиск**: строятся и хранятся локально (принцип IX); как и прочее производное
  состояние, восстановимы из файлов vault.

## Рабочий процесс и гейты качества

Работа над фичей идёт по последовательности Spec Kit:

1. `/speckit-specify` — только поведение (принцип III).
2. `/speckit-checklist` — гейт качества спеки; может повторно запускаться после плана под
   другим углом (например, «чеклист по безопасности») перед реализацией.
3. `/speckit-clarify` — снятие неоднозначностей. ОБЯЗАТЕЛЕН для работ по мосту к Neovim
   (принцип V).
4. `/speckit-plan` — технические решения.
5. `/speckit-tasks` — декомпозиция.
6. `/speckit-analyze` — read-only гейт согласованности spec/plan/tasks. MUST NOT
   пропускаться.
7. `/speckit-implement` — реализация, при необходимости со скоупом на подмножество задач.

Definition of done для любого изменения, затрагивающего `packages/core`:

- Собирается под `wasm32-unknown-unknown` и под нативный таргет (принцип II).
- `cargo test` и `wasm-bindgen-test` проходят.
- В UI не добавлено бизнес-логики (принцип I).
- Фронтенд проходит проверку типов в `strict` без `any` (принцип IV).

## Governance

Эта конституция имеет приоритет над прочими практиками и договорённостями проекта. Если
дефолт инструмента, шаблон или привычка противоречат принципу отсюда — выигрывает принцип.

**Поправки** MUST вноситься правкой этого файла через `/speckit-constitution`, MUST включать
Sync Impact Report в начале файла и MUST содержать обоснование изменения.

**Версионирование** по semver:

- MAJOR — принцип удалён или переопределён так, что ранее соответствующая работа перестаёт
  соответствовать.
- MINOR — добавлен принцип или раздел, либо существующее руководство существенно расширено.
- PATCH — уточнения формулировок и опечатки, не меняющие требований.

**Соответствие**: каждое ревью MUST проверять соблюдение принципов выше. Любое отклонение
MUST быть обосновано в `plan.md` в разделе Complexity/Deviation и принято явно —
необоснованное отклонение является основанием отклонить изменение. Runtime-руководство для
агентов живёт в файле руководства в корне репозитория (например, `CLAUDE.md`) и MUST NOT
противоречить этой конституции.
