# Research: Note Rendering and Live Preview

**Feature**: `specs/005-live-preview/spec.md` | **Plan**: [plan.md](./plan.md)

Все решения ниже проверены на месте, а не по памяти: версии взяты из индекса crates.io,
сигнатуры — из исходников `typst` 0.15.1 в локальном реестре, числа по весу и времени сборки
получены сборкой вертикального зонда под оба таргета. Где утверждение опирается на исходник,
указан файл.

## §1. Компилятор: крейт `typst` 0.15.1

**Decision**: брать официальные крейты `typst`, `typst-layout`, `typst-svg` версии 0.15.1;
`typst-assets` — только как источник шрифтов, и не через feature `fonts` (см. §6).

**Rationale**: 0.15.1 — актуальный стабильный релиз в индексе (проверено `cargo search typst`).
В индексе видны служебные пакеты `0.16.0-rc.1`, то есть следующий мажор в работе; садиться на
rc в фиче, которая и так вводит самую тяжёлую зависимость проекта, незачем.

**Проверено сборкой**: `cargo build --release --target wasm32-unknown-unknown` со связкой
`typst` + `typst-svg` + `typst-html` + `typst-assets/fonts` завершается успешно за 2 мин 44 с
на чистом кэше. Принцип II исполним — это был главный риск фичи, и он снят измерением, а не
рассуждением.

**Alternatives considered**:
- `typst-ide` — даёт автодополнение и переходы; вне скоупа (Out of Scope спеки), в зависимости
  не берём.
- `typst-render` (растр) — отвергнут вместе с растровым выводом, см. §4.
- Форк или собственный парсер Typst — не рассматривался всерьёз: это второй источник истины
  для языка, который мы не контролируем.

## §2. Синхронный `World` против асинхронной файловой системы

**Факт** (`typst-library-0.15.1/src/lib.rs:60`): `pub trait World: Send + Sync` со **строго
синхронными** методами — `source(&self, id) -> FileResult<Source>`,
`file(&self, id) -> FileResult<Bytes>`, `font(&self, index) -> Option<Font>`. Асинхронности в
трейте нет и быть не может: `typst::compile` вызывает их из середины вёрстки.

Web-бэкенд фичи 001 асинхронный целиком (File System Access API). Прямо подружить их нельзя.
Дополнительно `Send + Sync` запрещает держать в `World` любой `JsValue` — хендлы браузера туда
не положить даже теоретически.

**Decision**: разделить сборку на две фазы с явной границей.

1. **Фаза резолва (асинхронная)** — собирает *снимок зависимостей*: набор `FileId → Bytes`,
   вычитанный через существующий `VaultBackend`. Живёт на той стороне, где есть vault.
2. **Фаза сборки (синхронная)** — `typst::compile::<PagedDocument>(&world)` над `World`,
   который читает **только из снимка** и никогда не ходит в файловую систему.

Замыкание зависимостей заранее неизвестно: какой файл понадобится, выясняется по ходу
вычисления. Поэтому фаза сборки выполняется **итеративно**: `World` записывает каждый
запрошенный и отсутствующий в снимке `FileId`; если после прогона список непустой — недостающее
догружается фазой резолва, и прогон повторяется. Число итераций ограничено (предлагается 8) —
иначе патологический документ зациклит резолв вместо сборки.

**Rationale**: это единственная форма, при которой синхронный `World` сосуществует с
асинхронным vault, не заводя второй реализации доступа к файлам и не нарушая принцип I. Тот же
приём используют существующие web-сборки Typst.

**Alternatives considered**:
- Синтаксический предразбор импортов через `typst-syntax` до сборки — отвергнут: пути в Typst
  вычислимы, статический разбор даст неполное замыкание и молчаливо неверный документ.
- Блокирующее чтение из `World` — на wasm невозможно физически.

## §3. Сборка вне UI-потока

**Проблема**: `typst::compile` — блокирующий синхронный вызов. На web он выполнялся бы в том же
потоке, что и ввод, и FR-007 («ввод не подтормаживает») был бы нарушен по построению: предел
FR-026 — 10 секунд полной заморозки вкладки.

**Decision**:
- **web**: сборка идёт в выделенном Web Worker со своим экземпляром wasm-ядра. Снимок
  зависимостей передаётся в воркер сообщением, результат — обратно.
- **native**: сборка идёт в отдельном потоке (`tokio::task::spawn_blocking`), результат
  возвращается каналом.

**Отмена — честная асимметрия, которую фиксируем явно.** У `typst::compile` нет токена отмены
и нет кооперативных точек прерывания. Поэтому:
- на web отмена настоящая: `worker.terminate()` убивает вычисление вместе с воркером;
- на native отмена — отказ от результата: поток дорабатывает до конца, его результат
  отбрасывается. Пользователь наблюдает одно и то же (FR-026 выполняется), но одно ядро
  занято до завершения.

Это расхождение **не** нарушает принцип II: наблюдаемое поведение одинаково, различается только
цена. Зафиксировано в plan.md → Complexity Tracking.

**Alternatives considered**:
- Сборка на UI-потоке с дроблением по страницам — невозможно: `compile` неделим.
- Отдельный процесс на native ради killability — цена (запуск процесса на каждую пересборку)
  несопоставима с выигрышем.

## §4. Формат вывода: постраничный SVG + отдельный текстовый слой

**Факт** (`typst-svg-0.15.1/src/text.rs:64-76, 208-209`): `typst-svg` выводит каждый глиф как
`<path>` с контуром (`text.font.ttf().outline_glyph(...)`) либо как растровое изображение.
Элемента `<text>` в выводе нет вообще. **Значит текст из SVG, выданного `typst-svg`, не
выделяется, не копируется и не читается программой чтения с экрана.**

Это прямо противоречит FR-031 и FR-032, выбранным пользователем на шаге clarify.

**Факт** (`typst-library-0.15.1/src/text/item.rs:12-29`): `TextItem` в свёрстанном кадре несёт
`pub text: EcoString` (тот самый текст), `lang: Lang`, `size: Abs` и `glyphs: Vec<Glyph>` с
`x_advance`/`x_offset`. `FrameItem::Text(TextItem)`
(`typst-library-0.15.1/src/layout/frame.rs:490`) обходится вместе с трансформациями групп.

**Decision**: вывод состоит из двух частей на каждую страницу:
1. **Визуальный слой** — `typst_svg::svg(page, &opts)` (`typst-svg-0.15.1/src/lib.rs:32`,
   постранично, а не `svg_merged`).
2. **Текстовый слой** — список текстовых прогонов, извлечённых обходом `Frame` страницы:
   текст, позиция, размер, ширина прогона, язык. UI кладёт их прозрачным текстом поверх SVG.

Приём тот же, что у просмотрщиков PDF: картинка отвечает за вид, невидимый текст — за
выделение, копирование, поиск и доступность. `lang` из `TextItem` закрывает объявление языка
для программы чтения с экрана.

**Alternatives considered**:
- **`typst-html`** (крейт есть, 0.15.1) — даёт настоящий HTML с настоящим текстом, то есть
  FR-031 и FR-032 бесплатно. **Отвергнут**: HTML-вывод Typst принципиально не постраничный —
  `HtmlDocument` (`typst-html-0.15.1/src/dom.rs:26`) не содержит страниц вовсе. Это ломает
  FR-003 (переход к любой странице, различимые границы) и SC-008 (совпадение с внешней
  сборкой). Пагинация и HTML-вывод в Typst — разные цели (`Target::Paged` против HTML).
- **Растр `typst-render`** — отвергнут: и текста нет, и масштабирование хуже SVG.
- **Только SVG, без текстового слоя** — отвергнут: нарушает FR-031, FR-032 и SC-011.

## §5. Пересборка: страница как единица обновления

**Факт** (`typst-layout-0.15.1/src/document.rs:17-45, 79-105`): `PagedDocument::pages() ->
&[Page]`, а `Page` — `#[derive(Debug, Clone, Hash)]` с полями `frame`, `number`, `fill`.

**Decision**: после каждой сборки считать хэш каждой страницы. Ядро отдаёт наверх **все**
страницы документа, каждую со своим `digest`; UI сравнивает `digest` с уже показанным и
перерисовывает только те, что изменились.

Фильтровать на стороне ядра было бы дешевле по объёму передачи, но тогда `CompiledDocument`
перестал бы описывать документ целиком, и первая сборка, переоткрытие заметки и любой сброс
состояния UI требовали бы отдельного пути «отдай всё». Полный список с хэшами оставляет один
путь на все случаи, а экономия перерисовки — там, где она и нужна, в UI.

**Rationale**: обслуживает сразу три требования. SC-002 (обновление ≤1 с) — не перерисовываем
50 страниц на каждое нажатие. FR-004/FR-034 (удержание места в содержимом) — если видимая
страница не изменилась, её узел в DOM не трогается вовсе, и держать нечего. FR-009 (старый
результат не вытесняет новый) — вместе с версией текста, см. §9.

Приём прямо повторяет фичу 002, где `blake3` по нормализованному содержимому доски решает,
устарела ли вставка. Здесь хэш даёт `Page: Hash`, свой считать не нужно.

## §6. Шрифты: рядом с модулем, а не внутри него

**Измерено** сборкой зонда под `wasm32-unknown-unknown`, release, `wasm-opt -Oz`, сжатие
brotli `-q 11`:

| Состав | Сырой `.wasm` | После `-Oz` | gzip -9 | brotli -q11 |
|--------|--------------|-------------|---------|-------------|
| Компилятор + `typst-assets/fonts` | 44,5 МБ | 35,1 МБ | 15,6 МБ | **10,8 МБ** |
| Компилятор без встроенных шрифтов | 34,8 МБ | 25,4 МБ | — | **6,8 МБ** |

Каталог шрифтов `typst-assets` — 9,6 МБ на диске; в доставке они добавляют ≈4,1 МБ, потому что
сжимаются плохо.

**Decision**: **не** включать feature `fonts` у `typst-assets`. Встроенный набор (FR-027)
поставляется отдельными файлами рядом с wasm-модулем, подгружается при первом открытии vault и
кладётся в кэш устройства. Шрифты из папки vault (FR-027, FR-029) приходят тем же путём, что и
прочие связанные файлы, — через снимок зависимостей §2.

**Rationale**: шрифты меняются раз в никогда, а wasm-модуль будет пересобираться на каждом
релизе; вшив их внутрь, мы заставили бы пользователя выкачивать 4 МБ неизменных байтов при
каждом обновлении приложения. Разделение оставляет модулю 6,8 МБ, а шрифтам — собственный
жизненный цикл. Это же делает исполнимым FR-029: набор шрифтов меняется без пересборки wasm.

Отдельно: 6,8 МБ на компилятор — всё равно много, и это осознанная цена постраничной вёрстки,
совпадающей с внешним `typst compile` (SC-008). Загрузка обязана быть ленивой — модуль
компилятора не нужен, пока пользователь не открыл текстовую заметку.

**Alternatives considered**:
- Подмножество встроенных шрифтов вместо полного набора `typst-assets` — сокращает те же
  4,1 МБ, но расходится с внешним `typst compile` по умолчанию (SC-008) ровно на выброшенных
  шрифтах. Решение отложено до тасков: это вопрос выбора списка, а не архитектуры.
- Системные шрифты — исключены на шаге clarify (см. spec.md → Clarifications).

## §7. Диагностики и переход к месту ошибки

**Факт**: `typst::compile` (`typst-0.15.1/src/lib.rs:74`) возвращает
`Warned<SourceResult<T>>` — то есть предупреждения приходят **отдельно** от результата, а
ошибки — списком `SourceDiagnostic` со спанами. `WorldExt::range(span)`
(`typst-library-0.15.1/src/lib.rs:139-155`) переводит спан в байтовый диапазон внутри
конкретного файла.

**Decision**: ядро отдаёт наверх список диагностик, где у каждой: серьёзность, текст, `FileId`
источника и байтовый диапазон, переведённый в строку и колонку. Разделение
«ошибки/предупреждения» берётся из формы `Warned`, а не изобретается.

Этим закрываются FR-012 (причина словами — текст из `SourceDiagnostic`), FR-013 (файл и
позиция), FR-016 (порядок по месту — сортировка по `(FileId, начало диапазона)`), FR-018
(предупреждения отдельно и не мешают показу), FR-015 и FR-033 (переход: `FileId` прямо говорит,
чей это файл, и открывается ли он в редакторе).

## §8. Границы vault

**Факт** (`typst-syntax-0.15.1/src/path.rs:195-227`): `VirtualPath` нормализует сегменты и
отдаёт `PathError::Escapes` при попытке выйти за корень; `VirtualPath::virtualize` явно
отказывает, если путь не лежит внутри корня.

**Decision**: корнем (`VirtualRoot::Project`) объявляется папка vault. FR-023 при этом
обеспечивается **дважды**: структурно самим `VirtualPath` и фактически тем, что снимок
зависимостей §2 наполняется только через `VaultBackend`, который за пределы vault не ходит.
Пакеты Typst (`VirtualRoot::Package`) в этой фиче не поддерживаются: их загрузка — сеть, что
противоречит FR-024 и принципу IX.

## §9. Версионирование результата и порядок обновлений

**Decision**: каждая сборка помечается монотонной версией текста (revision), под которую она
запущена. Результат с версией меньше уже показанной отбрасывается на входе в UI.

**Rationale**: закрывает FR-009 буквально и без гонок. Механизм ровно тот же, что уже
используется в 002 (`contentRevision` в `useBoardDocument`), — новой машинерии не заводим.

Дебаунс: сборка запускается не на каждое нажатие, а после паузы ввода. Порог выбирается под
SC-002 (обновление ≤1 с после остановки) с запасом на саму сборку; конкретное значение —
предмет таска, а не архитектуры.

## §10. Кэш инкрементальной пересборки

**Факт**: `typst` использует `comemo` 0.5.1; `comemo::evict(max_age)`
(`comemo-0.5.1/src/memoize.rs:100`) вытесняет запомненные вычисления.

**Decision**: между пересборками кэш `comemo` **сохраняется** — на этом и держится скорость
живого набора; `evict` вызывается с небольшим `max_age` после каждой сборки, чтобы память не
росла неограниченно за сессию.

**Rationale**: без сохранения кэша каждая пересборка — сборка с нуля, и SC-002 недостижим.
Без вытеснения долгая сессия набора течёт по памяти. Конкретный `max_age` подбирается замером
в бенчмарке, по образцу бенчмарков фичи 002.

## §11. Что осталось риском

- **Вес доставки.** 6,8 МБ brotli на компилятор — верхняя граница приемлемого для веба. Ленивая
  загрузка обязательна, иначе SC-001 («вид ≤2 с после открытия») не выполнится на первом
  открытии при небыстрой сети. Требует замера на реальном канале.
- **Цикл импортов (FR-022).** Полагаемся на то, что `typst` сам обнаруживает циклическую
  зависимость и возвращает диагностику, а не зависает. Утверждение **не проверено** зондом —
  это первый тест, который надо написать (см. quickstart.md, Сценарий 6).
- **Время сборки проекта — измерено на реальном ядре (T006).** `cargo build -p typsidian-core`
  под нативный таргет на прогретом кэше зависимостей — 9 с; под
  `wasm32-unknown-unknown` в debug — 2 мин 40 с; `pnpm build:wasm` (release + `wasm-opt`) —
  6 мин 00 с. Первая сборка на чистом кэше добавляет к каждому из этих чисел время компиляции
  самих крейтов typst (~2 мин 45 с). Это заметно удлиняет и локальную работу, и CI: релизная
  wasm-сборка теперь шестиминутная.
- **Вес доставки пока не измерим, и это ожидаемо.** После подключения `preview` к ядру
  `ui/src/wasm-core/typsidian_core_bg.wasm` весит 0,6 МБ — потому что ни один
  `#[wasm_bindgen]`-экспорт не достигает модуля `preview`, и линковщик выбрасывает typst
  целиком. Что typst действительно тяжёл, видно на тестовом артефакте: `preview_wasm` в debug
  — 438 МБ против 344 МБ у `vault_wasm` без typst. Настоящий вес приложения станет
  измеримым только после T025/T041, когда экспорт дотянется до сборки документа; до тех пор
  ориентир — 6,8 МБ brotli, полученные на зонде (§6).
- **`Send + Sync` у `World`.** На wasm32 ограничение выполнимо только потому, что снимок
  зависимостей — простые байты. Любая попытка положить в `World` браузерный хендл не
  скомпилируется; это скорее страховка, чем риск, но о ней надо знать.

## Объявление правок ядру — по паузе (T064, 2026-10-20)

`NoteDocument.changed` объявлял ядру буфер целиком на каждое нажатие (`beginEdit`) — через
очередь вызовов wasm в web и IPC на рабочем столе. Теперь первая правка после сохранения
объявляется сразу (с этого мига внешнее изменение не применяется молча, FR-035), а
следующие — не чаще раза в 150 мс последним буфером (`EDIT_ANNOUNCE_DEBOUNCE_MS`);
автосохранение отменяет отложенное объявление — запись его покрывает. Сборка
предпросмотра от этого не зависит: она берёт текст из документа. Сценарии `tabs`,
`properties`, `attachments`, `sources`, `completion` — без провалов.

## Шрифты рядом с модулем (T029, 2026-10-20)

Встроенный набор (17 файлов `typst-assets`, 9,6 МБ) больше не вшит в wasm-модуль
приложения. `typst-assets` с feature `fonts` — только у нативной сборки (рабочий стол,
Android) и у тестов обоих таргетов (feature крейта `embedded-fonts`, включается
зависимостью тестов на сам крейт). Для web `pnpm build:wasm` кладёт файлы и `index.json` в
`apps/web/public/fonts/typst/` (`scripts/builtin-fonts.mjs`, в git не входят);
`ui/src/preview/builtin-fonts.ts` грузит их перед первой сборкой и держит в Cache API
(`typsidian-fonts-<версия>`) — второе открытие и работа без сети их не скачивают. Движок
получает набор `PreviewEngine.addBuiltinFonts`, воркер сборки — один раз после старта
(`setWorkerBuiltinFonts`), а не с каждой сборкой.
