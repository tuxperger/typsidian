# Research: Мультиязычный интерфейс (фича 010)

Все решения ниже сняты разбором текущего кода (2026-09-29). Открытых NEEDS CLARIFICATION нет.

## Исходное состояние (замер)

- `ui/src`: 88 файлов, ≈1250 строк с кириллицей вне комментариев. Библиотеки i18n нет.
  Единственная языковая утилита — `ui/src/plural.ts`, зашитая на `ru-RU`.
- Оболочки: строки в `apps/desktop/src` (заголовок нативного диалога выбора папки),
  `apps/mobile/src` (сообщения о правах Android, обзор папок), `apps/web/app`
  (`<html lang="ru">`, мета-описание).
- Ядро (`packages/core`) и `packages/shell`: ≈100 пользовательских сообщений. Два вида:
  1. **Уже структурные** — перечисления отказов с `#[serde(tag = "kind")]` (`ReadError`,
     `WriteError`, `CreateError`, `RenameError`, `OpenError`, отказы настроек и т. п.).
     UI уже сопоставляет `kind` с русским текстом сам (`useVault.ts`,
     `VaultTreeActions.tsx`, `useConflictResolution.ts`).
  2. **Готовая строка** — `Diagnostic.message` у замечаний, которые формирует приложение
     (непрочитанный связанный файл, загрузка шаблона, расхождение отпечатка, шрифт vault,
     экспорт), и места, где UI показывает `error.message` (`OpenVault.tsx`,
     `useVaultList.ts`) — это `Display` из `thiserror`, по-русски.

## §1. Своя тонкая прослойка вместо библиотеки i18n

**Decision**: Собственный модуль `ui/src/i18n/` (~150 строк): React-контекст языка,
типизированные каталоги-модули TypeScript, формы чисел/дат через стандартный `Intl`.

**Rationale**:
- Полнота переводов проверяется **компилятором**: каталог русского объявлен типом,
  выведенным из английского, — отсутствующий ключ или несовпадающая сигнатура параметров
  роняют `tsc --strict` (FR-028) без отдельного инструмента и без `any` (принцип IV).
- `Intl.PluralRules` / `NumberFormat` / `DateTimeFormat` есть во всех трёх рантаймах
  (Chromium/WebView2/WebKitGTK/Android WebView) — формы слов и форматирование (FR-021,
  FR-022) не требуют данных CLDR в бандле.
- Ноль новых зависимостей: нет вопросов к Nix-окружению и к размеру бандла.

**Alternatives considered**:
- *i18next + react-i18next* — строковые ключи без проверки параметров на этапе компиляции,
  +40 КБ, собственный формат плюралов, дублирующий `Intl`.
- *FormatJS / react-intl (ICU)* — сообщения в ICU-строках разбираются в рантайме; типизация
  параметров только через генерацию; тяжелее.
- *Fluent* — лучшая модель плюралов и падежей, но отдельный формат файлов, парсер в
  рантайме и отсутствие типов; избыточно для двух языков.

## §2. Формат каталога

**Decision**: Каталог — объект TypeScript `as const`: ключ → строка **или** функция от
типизированных параметров. Английский (`locales/en.ts`) — эталон; тип `Catalog` выводится из
него. Для чисел — хелпер `plural(lang, n, { one, few?, many?, other })`, выбирающий форму через
`Intl.PluralRules` текущего языка. Каталог каждого языка несёт `meta: { code, nativeName }`.

**Rationale**: функции дают типизированные подстановки (`(p: { file: string }) => …`), а
сверка сигнатур между языками — работа `tsc`. Имена пользователя подставляются как есть —
никакой интерполяции внутри значений (FR-005).

**Alternatives considered**: JSON-файлы — подстановки только строковые, типы параметров
теряются; YAML — ещё и парсер.

## §3. Сообщения ядра: вид + параметры, а не текст

**Decision**:
- Новый модуль `packages/core/src/messages.rs`: перечисление `AppMessage`
  (`#[serde(tag = "code")]`, tsify) — по варианту на каждое сообщение, которое приложение
  формирует **само**, с полями-параметрами (путь, спецификация шаблона, адрес, число).
- `Diagnostic` получает поле `app: Option<AppMessage>`. У сообщений Typst оно `None`, и UI
  показывает `message` как есть (FR-004). У сообщений приложения UI собирает текст из
  `app` на текущем языке; `message` остаётся языконезависимым текстом для журналов (FR-031).
- Отказы, уже приходящие перечислениями с `kind`, остаются как есть: UI переводит `kind` →
  ключ каталога. Места, где UI показывает `error.message`, переводятся на `kind`.
- `Display` (`#[error(...)]`) в ядре не удаляется: это текст журналов и тестов, в
  интерфейс он больше не попадает.

**Rationale**: FR-014 (уже показанное перерисовывается на новом языке) выполним, только если
в UI лежат не строки, а данные. Типы `AppMessage` порождаются из Rust (принцип IV), а
исчерпывающий `switch` с `never` в UI делает «код без перевода» ошибкой компиляции.

**Alternatives considered**:
- *Каталог в ядре на Rust* (ядро возвращает готовый текст на запрошенном языке) — язык
  пришлось бы передавать в каждый вызов ядра, а перевод уже показанного требовал бы
  повторного вызова; каталоги разделились бы на два места (UI и ядро).
- *Стабильные строковые ключи в `message`* — без типизации параметров; опечатка в ключе
  обнаруживается только на экране.

## §4. Хранение выбора языка

**Decision**: `Settings.language: Option<String>` в настройках устройства (`None` —
«как в системе»), ключ `"language"` в `settings.json`. `SettingsChange.language:
Option<LanguageChoice>`, где `LanguageChoice = System | Tag(String)`.
`touches_vault_scoped_values()` язык **не** учитывает — набор с одним языком всегда идёт в
`ChangeTarget::Device` (FR-016). `reset_to_defaults()` возвращает `System` (FR-017).
Ядро проверяет только синтаксис тега (латиница, цифры, `-`, до 35 знаков); какие языки
поддерживаются, знает UI. Нераспознанное значение сохраняется при записи других значений
(FR-018) — это уже гарантия формата: неизвестное не затирается.

**Rationale**: язык — свойство устройства, как `current_vault` (фича 006 FR-028). Список
поддерживаемых языков живёт вместе с каталогами, иначе добавление языка требовало бы правки
ядра (FR-026).

**Alternatives considered**: перечисление языков в ядре — нарушает FR-026; хранение в
`localStorage` — расходится с desktop/Android и с «Сбросом» фичи 004.

## §5. Выбор действующего языка

**Decision**: Чистая функция `resolveLanguage(choice, systemLanguages, available)` в
`ui/src/i18n/resolve.ts`: явный поддерживаемый выбор → он; иначе первый из
`navigator.languages`, чей основной подтег поддерживается (`en-GB` → `en`); иначе `en`.

**Rationale**: вход функции — список каталогов, который существует только в UI; перенос в
ядро потребовал бы передавать каталоговую информацию через границу и IPC на старте ради
трёх строк сравнения. Бизнес-логики (vault, сборка, ссылки) здесь нет — это выбор
представления, того же рода, что выбор CSS-темы. Обоснование отклонения от буквы принципа I
— в plan.md → Complexity Tracking.

**Alternatives considered**: функция в ядре + вызов через биндинг/IPC — задержка первого
кадра на desktop и зависимость ядра от состава каталогов.

## §6. Немедленное применение без потери состояния

**Decision**: `I18nProvider` в корне каждой оболочки; смена языка меняет значение
контекста, потребители перерисовываются. Ни один компонент не использует язык в `key` —
редактор, доска и предпросмотр не пересоздаются (FR-013). `document.documentElement.lang`
выставляется при каждой смене (FR-006). На web `layout.tsx` отдаёт `lang` по умолчанию
`en`, клиент исправляет его при гидрации.

## §7. Встроенный редактор досок

**Decision**: Передавать движку проп `langCode` (`ru` → `ru-RU`, `en` → `en`) — это
конфигурация через публичный API, а не стилизация (принцип VIII соблюдён). Строка —
примитив, поэтому проблема мемоизации инлайновых пропов (объекты и функции) его не касается.

## §8. Оболочки

**Decision**: Строки `apps/desktop/src`, `apps/mobile/src`, `apps/web/app` переходят на
тот же `useT()` из `@typsidian/ui/i18n`. Заголовок нативного диалога берётся из каталога
в момент вызова.

## §9. Палитра команд

**Decision**: Каждая команда получает подписи на текущем языке и на английском; фильтр
сравнивает запрос с обеими, показывается текущая (clarification 3, FR-024).

## §10. Автоматические проверки и хуки

**Decision**:
1. `tsc --strict` — полнота каталогов и исчерпывающее покрытие `AppMessage`.
2. `scripts/check-i18n.sh` — ищет литералы с кириллицей в `ui/src`, `apps/*/src`,
   `apps/web/app` вне `ui/src/i18n/locales/` и вне комментариев; ненулевой код возврата —
   провал. Скрипт на bash + grep: работает и вне `nix develop`.
3. Хук Claude Code `PostToolUse` (Edit|Write) запускает тот же скрипт на изменённом файле и
   возвращает агенту предупреждение — хардкод не появляется заново в ходе реализации.
4. Хуки Spec Kit (`.specify/extensions.yml`): clarify после specify, analyze после tasks,
   converge после implement.

## §11. Тестирование

- Ядро: `settings_native.rs` / `settings_wasm.rs` — разбор и запись `language`,
  сохранение нераспознанного значения, маршрут в устройство при открытом vault, сброс.
  `preview_native.rs` / `preview_wasm.rs` — у диагностик приложения заполнен `app`, у
  диагностик Typst — нет.
- UI: инфраструктуры JS-тестов в репозитории нет; проверка — `tsc`, `check-i18n.sh` и стенд
  на headless Chromium по `quickstart.md`.
