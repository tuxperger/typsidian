# Feature Specification: Синхронизация на своём сервере

**Feature Branch**: `038-server-sync`

**Created**: 2026-10-24

**Status**: Implemented

**Priority**: P2

**Summary**: Vault на своём сервере получает историю версий и удалённый репозиторий по HTTPS так же, как папка на рабочем столе, — синхронизацию выполняет сервер, а токены хранятся на нём для каждого аккаунта отдельно.

**Input**: User description: "Синхронизация git и Syncthing (фича 011) в серверном режиме web (фича 037): vault на своём сервере получает историю версий, удалённый репозиторий и Syncthing так же, как на рабочем столе — их выполняет сервер. Секреты (токены, ключи) и настройки устройства хранятся на сервере отдельно для каждого аккаунта и никогда не попадают в vault; команды синхронизации идут через общую реализацию команд и белый список сервера."

## Clarifications

### Session 2026-10-24

- Q: Какие адреса удалённого репозитория поддерживает сервер? → A: Только HTTPS с токеном.
  ssh на сервере не поддерживается: ключ системного пользователя сервера стал бы общим для
  всех аккаунтов. Адрес ssh отклоняется при подключении, а уже записанный в `.git` — при
  отправке и получении, с понятной причиной.
- Q: Нужен ли Syncthing в серверном режиме? → A: Нет. Раздел Syncthing панели недоступен с
  объяснением, как в браузере (011); команды Syncthing не входят в белый список сервера.
  Бывшая US3 — вне фичи.
- Q: Какие ещё адреса отклоняются на сервере? → A: Адреса «этого устройства» — каталог
  (`file://`, путь) и `http://localhost`: на сервере это файлы и службы самого сервера, в том
  числе чужие vault. Адреса HTTPS с IP из внутренних диапазонов и `localhost` отклоняются,
  пока администратор не разрешит их настройкой сервера.
- Q: Где подсказка о хранении токена? → A: В серверном режиме — «Хранится на сервере для
  вашего аккаунта, в vault и браузер не попадает».
- Q: Где лежат настройки устройства и секреты? → A: В папке данных аккаунта на сервере:
  настройки устройства (011) — файл настроек аккаунта, секреты — файл аккаунта с правами
  0600 с ключом записи (vault, вид секрета), как на Android. Удаление vault удаляет его
  секреты, удаление аккаунта — всю его папку данных.
- Q: Нужна ли поправка конституции? → A: Нет: ssh и Syncthing не вводятся, сервер остаётся
  «своим устройством» по принципу IX (3.0.0), безопасность — по XI.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - История версий vault на сервере (Priority: P1)

Анна открыла vault на своём сервере, включает историю в панели «Синхронизация», делает
снимки, смотрит историю заметки и возвращает прежнюю версию — так же, как на рабочем столе.

**Independent Test**: в серверном режиме включить историю, сделать два снимка, вернуть
заметку к первому — текст первого снимка в редакторе; в папке vault на сервере обычный `.git`.

**Acceptance Scenarios**:

1. **Given** vault на сервере без истории, **When** Анна включает её мастером, **Then**
   правила исключения и первый снимок — как на рабочем столе (011).
2. **Given** история включена, **Then** список изменений, снимок, история заметки,
   сравнение и возврат работают так же, как на рабочем столе.

---

### User Story 2 - Удалённый репозиторий (Priority: P2)

Анна подключает удалённый репозиторий по адресу и токену; отправка и получение со слиянием
выполняются сервером. Токен хранится на сервере, привязан к её аккаунту и vault, в vault и
в браузер не попадает.

**Acceptance Scenarios**:

1. **Given** адрес и токен, **When** Анна подключает репозиторий, **Then** отправка и
   получение работают, встречные правки открывают редактор слияния (011).
2. **Given** два аккаунта на одном сервере, **Then** токен одного недоступен другому ни
   через интерфейс, ни через команды.
3. **Given** токен сохранён, **Then** ни один ответ сервера и ни одна запись журнала его не
   содержат.

---

### Вне фичи

Syncthing в серверном режиме (бывшая US3) не поддерживается — см. Clarifications.

### Edge Cases

- Удаление vault или аккаунта — его секреты синхронизации удаляются вместе с ним.
- Связь с сервером рвётся во время отправки — после восстановления панель показывает итог
  операции, выполненной сервером, а не повторяет её.
- Адрес ssh (`git@…`, `ssh://…`) — подключение отклоняется с причиной «на сервере только
  HTTPS»; ssh-адрес, уже записанный в `.git` vault, не используется для отправки и получения.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Vault на своём сервере MUST поддерживать историю версий и удалённый
  репозиторий по HTTPS с теми же возможностями, что на рабочем столе (011); ssh и Syncthing
  в серверном режиме MUST NOT предлагаться.
- **FR-002**: Секреты синхронизации MUST храниться на сервере отдельно для каждой пары
  (аккаунт, vault) и MUST NOT попадать в vault, ответы сервера и журнал.
- **FR-003**: Настройки синхронизации, которые на рабочем столе хранятся на устройстве, MUST
  храниться на сервере для аккаунта.
- **FR-004**: Команды синхронизации MUST выполняться той же реализацией, что на рабочем
  столе, и только из белого списка сервера.
- **FR-005**: Один аккаунт MUST NOT иметь доступа к истории, секретам и настройкам
  синхронизации другого.

### Key Entities

- **Секрет синхронизации** — имя пользователя и токен удалённого репозитория аккаунта для vault.
- **Настройки синхронизации аккаунта** — то, что на рабочем столе лежит в настройках устройства.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Сценарии 011 (включение истории, снимок, возврат, отправка, получение, слияние)
  проходят в серверном режиме в 100% случаев так же, как на рабочем столе.
- **SC-002**: 0 появлений токена в ответах сервера, журнале и файлах vault в проверке на двух
  аккаунтах.

## Assumptions

- Зависит от 011 (синхронизация) и 037 (серверный режим).
- Секреты на сервере хранятся в папке данных с правами только для процесса сервера;
  шифрование секретов сверх этого — вне фичи.
- Конституция XI: перед планом — `/speckit-clarify`, перед «готово» — `security-review-agent`.
