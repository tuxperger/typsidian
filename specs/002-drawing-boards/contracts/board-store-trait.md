# Contract: BoardStore (внутренний контракт ядра)

**Feature**: `specs/002-drawing-boards/spec.md` | **Plan**: [../plan.md](../plan.md)

Публичный API фичи со стороны `packages/core`. Одна реализация на оба таргета: логика здесь
платформенно-нейтральна (JSON, хэш, строки путей), а всё, что различается по платформам —
чтение и запись файлов, — уже скрыто трейтом `VaultBackend` из 001. Отдельных
`NativeBoardStore`/`WebBoardStore` не существует, и это осознанно: заводить вторую пару
реализаций там, где нет платформенного различия, значит создать место для расхождения
(принцип II).

## Форма

```rust
pub trait BoardStore {
    // ── Доска как файл ────────────────────────────────────────────────────

    /// Создать пустую доску. Имя и коллизии — по правилам vault-manager (FR-001, FR-003).
    fn create_board(&mut self, path: &Path) -> Result<Board, CreateError>;

    /// Прочитать доску. Содержимое возвращается непрозрачными байтами: ядро не разбирает
    /// модель движка (research.md §9).
    fn read_board(&self, path: &Path) -> Result<BoardContent, ReadBoardError>;

    /// Записать доску. Отклоняется, пока по ней есть неразрешённый конфликт (инвариант 1)
    /// и на профиле, у которого нет права записи доски (FR-035).
    fn write_board(
        &mut self,
        path: &Path,
        content: &BoardContent,
        expected: Option<FileStamp>,
    ) -> Result<FileStamp, WriteBoardError>;

    /// Хэш нормализованного содержимого (data-model.md «BoardDigest»).
    fn digest(&self, content: &BoardContent) -> Result<BoardDigest, DigestError>;

    // ── Вставки ───────────────────────────────────────────────────────────

    /// Разобрать текст заметки и вернуть все вставки досок с их состоянием (FR-026).
    /// Чистая функция от текста заметки и состояния файлов — не пишет ничего.
    fn embeds_of(&self, note_path: &Path, note_text: &str) -> Vec<Embed>;

    /// Путь и идентификатор для новой вставки (research.md §4). Файл не создаётся:
    /// его пишет UI после экспорта движком.
    fn plan_embed(&self, note_path: &Path, board_path: &Path) -> Result<EmbedPlan, EmbedError>;

    /// Текст вызова `#image(...)`, который UI вставляет в заметку (FR-022, research.md §11).
    fn embed_markup(&self, plan: &EmbedPlan) -> String;

    /// Метаданные, которые UI обязан вложить в SVG перед записью (data-model.md «Snapshot»).
    fn snapshot_metadata(&self, board_path: &Path, digest: &BoardDigest) -> SnapshotMetadata;

    /// Прочитать метаданные из существующего снимка. Отсутствие или порча метаданных —
    /// не ошибка вызова, а `EmbedState::Undeterminable` у соответствующей вставки.
    fn read_snapshot_metadata(&self, snapshot_path: &Path) -> Result<SnapshotMetadata, SnapshotError>;
}
```

## Правила

**Ядро не знает, как выглядит рисунок.** `BoardContent` — байты файла. Ядро вычисляет по
ним хэш, но не умеет их рисовать и не должно уметь: экспорт в SVG выполняет движок в UI
(research.md §9). Следствие: смена движка не меняет ни одну сигнатуру этого трейта.

**Ядро не пишет файлы снимков.** Оно решает, *куда* и *с какими метаданными* писать
(`plan_embed`, `snapshot_metadata`), но сама запись идёт через `VaultBackend`, после того
как UI получил SVG от движка. Иначе ядру пришлось бы принимать чужой рендер как аргумент и
отвечать за его корректность.

**`embeds_of` — чистая функция.** Она не открывает заметку, не пишет и не кэширует:
вызывающая сторона передаёт текст, который у неё и так есть. Это делает разбор вставок
тестируемым таблицей входов-выходов на обоих таргетах, без файловой системы.

**Отказы называются причиной.** `ReadBoardError`, `WriteBoardError` и прочие — размеченные
объединения с конкретными вариантами (`NotFound`, `Unreadable`, `Conflicted`,
`ReadOnlyProfile`, …), а не общий «не удалось». Требование то же, что в 001 (FR-008) и 004:
пользователь должен увидеть причину, а не факт неудачи.

**Повреждённый файл доски не перезаписывается.** `read_board` на нечитаемом файле возвращает
`Unreadable`, и это состояние не даёт пути к `write_board` (FR-017, spec.md Edge Cases) —
ровно как испорченный `settings.json` в 004 не перезаписывается молча.

## Гейты записи

`write_board` отклоняет запись в трёх случаях, и все три проверяются тестами на обоих
таргетах:

| Условие | Отказ | Требование |
|---|---|---|
| по доске есть неразрешённый конфликт | `Conflicted` | FR-014 |
| `expected` не совпадает с текущим `FileStamp` | `Conflicted` | FR-014 |
| профиль клиента не имеет права записи доски | `ReadOnlyProfile` | FR-035 |
| vault недоступен или открыт только на чтение | наследуется от `VaultBackend` | 001 FR-020, FR-036 |

Третья строка — то, чем мобильный просмотр отличается от desktop: не флагом в интерфейсе, а
отсутствием пути записи в ядре (research.md §8).

## Тестируемость

Каждый метод покрывается `cargo test` и `wasm-bindgen-test` (принципы I, II). Отдельно
фиксируются:

- одинаковый `BoardDigest` для одного входа на обоих таргетах;
- устойчивость `digest` к полям ревизий движка — открытие доски без правок хэш не меняет
  (research.md §5);
- `embeds_of` на тексте с двумя вставками одной доски возвращает две записи с разными
  `EmbedId` (FR-020, FR-023);
- `write_board` при активном конфликте не касается файла (FR-014).
