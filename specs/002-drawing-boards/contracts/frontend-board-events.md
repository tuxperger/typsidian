# Contract: ядро → UI (доски)

**Feature**: `specs/002-drawing-boards/spec.md` | **Plan**: [../plan.md](../plan.md)

Что ядро сообщает интерфейсу и как интерфейс обязан это обрабатывать. Продолжение
`001-vault-manager/contracts/frontend-events.md`: доски проходят по тем же событиям vault,
что и заметки, и этот документ описывает только добавленное.

## Типы приходят из Rust

Все типы ниже порождаются из определений `packages/core` через `tsify` и импортируются в
UI из сгенерированного `typsidian_core.d.ts`. Ручной копии на TypeScript не существует
(принцип IV). Если тип понадобился в UI, а его нет в биндингах, правильный шаг — экспортировать
его из ядра, а не объявить рядом.

## События vault, которые доски переиспользуют

Отдельного потока событий для досок нет. Создание, изменение, переименование и удаление
доски приходят теми же `VaultEvent`, что и для заметок (FR-005), — меняется только
`FileKind` в полезной нагрузке. Это сознательно: второй канал означал бы второй порядок
доставки и гонки между ними на одном и том же файле.

Из этого следует поведение краевого случая «та же доска открыта в двух окнах»
(spec.md Edge Cases): второе окно — обычный внешний источник изменений, и правило одно с
заметками.

## BoardEvent

Добавляется к существующему потоку. Размеченное объединение; в UI обрабатывается
исчерпывающе — `default` ветка с `never` обязательна, как в 001.

| Вариант | Когда | Что делает UI |
|---|---|---|
| `SaveStateChanged { path, state }` | смена `BoardSaveState` | показывает состояние сохранения (FR-009) |
| `SaveFailed { path, reason }` | запись не удалась | показывает причину, полотно не трогает (FR-010) |
| `ConflictDetected { path }` | внешнее изменение при несохранённых правках | открывает выбор из двух версий (FR-014, FR-015) |
| `EmbedsChanged { note_path }` | изменилось состояние вставок открытой заметки | пересчитывает индикаторы (FR-026, FR-027) |

`EmbedsChanged` приходит и тогда, когда изменилась доска, а не заметка: устаревание вставки
вызывается правкой источника, а не текста, где она стоит. Без этого события индикатор
появлялся бы только при повторном открытии заметки, и SC-008 выполнялся бы с задержкой,
которую пользователь воспринимает как «не работает».

## EmbedState в интерфейсе

Пять вариантов из `data-model.md`. Требование к обработке — каждый виден пользователю
по-своему:

| Вариант | Что показывается |
|---|---|
| `UpToDate` | ничего дополнительного |
| `Stale` | индикатор устаревания с действием «обновить вставку» |
| `BoardMissing` | «источник вставки отсутствует»; заметка остаётся редактируемой |
| `SnapshotMissing` | «снимок отсутствует» с действием восстановить из доски |
| `Undeterminable { reason }` | «сравнить не удалось» с причиной |

**Запрещено** схлопывать `Undeterminable` в `UpToDate` — «не смогли сравнить» и «совпадает»
для пользователя разные вещи, и молчаливое расхождение спека запрещает прямо (SC-008).
Схлопывание `SnapshotMissing` в `BoardMissing` тоже запрещено: у них разные действия
восстановления (FR-031 против FR-032).

## Что UI делает сам

Не всё, что нужно фиче, — события ядра. За UI закреплены:

- построение обеих превью при конфликте через `exportToSvg` (FR-015) и явное сообщение,
  если превью построить не удалось (FR-016);
- вызов экспорта и запись файла снимка после того, как ядро выдало `EmbedPlan`;
- сброс дебаунса перед переключением заметки, закрытием окна и построением снимка
  (research.md §6);
- предупреждение перед закрытием окна при несохранённых правках доски (FR-011) — тем же
  механизмом, что `ui/src/editor/useWindowCloseGuard.ts` для заметок.

Ни один из этих пунктов не содержит правил: они вызывают примитивы ядра и рендерят
результат. Как только в UI появляется ветвление вида «если хэши разошлись, то…» — правило
уехало из ядра, и это нарушение принципа I, а не удобное сокращение.
