# Data Model: Drawing Boards

**Feature**: `specs/002-drawing-boards/spec.md` | **Plan**: [plan.md](./plan.md)

Сущности Phase 1. Именование соответствует «Key Entities» спеки; техническая форма выбрана
здесь. Всё, что пересекает границу WASM/JS, порождается из этих определений через `tsify` —
ручных дубликатов на TypeScript нет (принцип IV).

## FileKind

Классификация файла vault. Заменяет два разошедшихся `is_note` — в `vault/web.rs:21` и
`vault/native.rs:27` (research.md §3).

| Вариант | Признак | Показывается в дереве |
|---|---|---|
| `Note` | расширение `.typ` | да |
| `Board` | расширение `.excalidraw` | да (FR-004, с отдельным признаком) |
| `Snapshot` | лежит в папке `*.assets/` рядом с заметкой того же имени | нет (FR-021) |
| `Other` | всё остальное | нет |

Правила:
- Классификация выполняется по пути, без чтения содержимого: дерево строится обходом, и
  открытие каждого файла ради определения типа сломало бы бюджет SC-002 фичи 001.
- `Snapshot` опознаётся по расположению, а не по расширению: произвольный SVG, положенный
  пользователем в vault, — это `Other`, и в дереве он тоже не появляется, но снимком не
  считается и в связях со вставками не участвует.
- Скрытые и служебные каталоги исключаются раньше классификации — правилом vault-manager
  (FR-004 фичи 001), эта фича его не меняет.

## Board

Доска как файл vault.

| Поле | Тип | Смысл |
|---|---|---|
| `path` | `PathBuf` | путь относительно корня vault |
| `name` | `String` | имя файла для показа в дереве |
| `stamp` | `FileStamp` | отпечаток файла на диске; тип из 001, переиспользуется |
| `digest` | `BoardDigest` | хэш нормализованного содержимого (см. ниже) |
| `has_unsaved_edits` | `bool` | есть ли в сессии буфер, не записанный в файл |

Доска участвует в дереве, переименовании, перемещении и удалении на общих правилах
vault-manager (FR-003) — отдельных операций для неё не вводится. `Board` намеренно повторяет
форму `Note` из `vault/index.rs`: это позволяет дереву работать с обоими типами
единообразно, а различие оставить в `FileKind`.

**Содержимого доски здесь нет.** Ядро не хранит и не разбирает модель Excalidraw
(research.md §9): содержимое живёт в файле и в памяти движка, а через границу ходит
непрозрачными байтами.

## BoardDigest

Хэш содержимого доски, по которому определяется устаревание вставки.

| Поле | Тип | Смысл |
|---|---|---|
| `value` | `[u8; 32]` | BLAKE3 по нормализованной проекции содержимого |

Нормализация (research.md §5) — обязательная часть определения, а не деталь реализации:

- **Входит в хэш**: порядок элементов, геометрия, тип, стилевые свойства, текст, привязки
  между элементами, файлы-вложения по их собственным хэшам.
- **Не входит**: `version`, `versionNonce`, `updated`, `seed` и прочие счётчики ревизий
  движка; `appState` целиком, включая положение и масштаб камеры (spec.md Assumptions);
  порядок ключей в объектах JSON.

Без этого правила простое открытие доски меняло бы хэш и зажигало индикатор устаревания на
всех её вставках — то есть SC-008 выполнялся бы формально и при этом бесполезно.

`BoardDigest` вычисляется в ядре и покрывается тестами на обоих таргетах: одинаковый вход
даёт одинаковый хэш на native и в WASM (принцип II).

## Snapshot

Файл изображения, принадлежащий конкретной вставке.

| Поле | Тип | Смысл |
|---|---|---|
| `path` | `PathBuf` | `<папка заметки>/<имя заметки>.assets/<id>.svg` |
| `embed_id` | `EmbedId` | идентификатор вставки, за которой закреплён файл |
| `board_path` | `PathBuf` | доска-источник на момент записи снимка |
| `board_digest` | `BoardDigest` | состояние доски, отражённое этим снимком |

`board_path` и `board_digest` физически лежат внутри самого SVG, в
`<desc data-typsidian-board="…" data-typsidian-board-hash="…">` (research.md §5). Это
единственное место, где приложение пишет свои метаданные в файл vault, и оно выбрано
потому, что файл снимка целиком порождается приложением — в отличие от заметки (FR-022) и
файла доски (research.md §2).

Имя файла закрепляется за вставкой при её создании и при обновлении не меняется (FR-028,
FR-029): обновляется содержимое того же файла. Отсюда же следует FR-020 — у каждой вставки
свой файл, потому что идентификатор уникален для вставки, а не для доски.

## Embed

Вставка доски в текст заметки. **В файлах не хранится** — вычисляется разбором текста
заметки при её открытии.

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `EmbedId` | извлекается из имени файла снимка, на который ведёт вставка |
| `note_path` | `PathBuf` | заметка, содержащая вставку |
| `range` | `Range<usize>` | положение вызова `#image(...)` в тексте, для индикатора и обновления |
| `snapshot_path` | `PathBuf` | путь из аргумента `#image` |
| `state` | `EmbedState` | наблюдаемое состояние актуальности |

Вставка опознаётся по адресу, а не по маркеру: вызов `#image`, чей путь ведёт в
`*.assets/` этой заметки (research.md §11). Поэтому заметка остаётся обычным Typst
(FR-022), а удаление вызова из текста просто означает, что вставки больше нет — никакого
состояния, требующего уборки, не остаётся.

## EmbedState

Наблюдаемое состояние вставки. Размеченное объединение — именно оно решает SC-008.

| Вариант | Когда | Что видит пользователь |
|---|---|---|
| `UpToDate` | хэш доски равен хэшу из снимка | ничего дополнительного |
| `Stale` | хэши различаются | индикатор устаревания с действием «обновить вставку» (FR-027) |
| `BoardMissing` | доска по `board_path` не найдена | «источник вставки отсутствует», заметка остаётся редактируемой (FR-031) |
| `SnapshotMissing` | файла снимка нет, доска на месте | «снимок отсутствует» с действием восстановить (FR-032) |
| `Undeterminable { reason }` | снимок есть, но метаданных в нём нет или они не читаются | «сравнить не удалось» с причиной |

`Undeterminable` — отдельный вариант, а не `None` и не «считаем актуальным». Спека
запрещает молчаливое расхождение (SC-008), и краевой случай «файл снимка заменён сторонним
инструментом» (spec.md Edge Cases) приводит именно сюда. В TypeScript `strict` объединение
обрабатывается исчерпывающе, поэтому забыть этот вариант в UI нельзя (принцип IV).

## BoardSaveState

Видимое пользователю состояние сохранения открытой доски (FR-009).

| Вариант | Когда |
|---|---|
| `Clean` | буфер совпадает с файлом |
| `Dirty` | есть изменения, дебаунс ещё не истёк |
| `Saving` | запись идёт |
| `Failed { reason }` | запись не удалась; содержимое полотна не потеряно (FR-010) |

Переходы: `Clean → Dirty` (правка), `Dirty → Saving` (истёк дебаунс либо принудительный
сброс перед переключением заметки, закрытием окна и построением снимка — research.md §6),
`Saving → Clean` (успех), `Saving → Failed` (отказ), `Failed → Dirty` (следующая правка).
Из `Failed` нет автоматического перехода в `Clean`: пока запись не удалась, окно не
закрывается без предупреждения (FR-011).

## BoardConflict

| Поле | Тип | Смысл |
|---|---|---|
| `board_path` | `PathBuf` | доска, по которой возник конфликт |
| `local_digest` | `BoardDigest` | хэш буфера пользователя |
| `external_stamp` | `FileStamp` | отпечаток версии на диске |

Существует до явного выбора пользователя (FR-014). Обнаружение переиспользует
`vault/conflict.rs` из 001 без изменений (research.md §7) — новой машины состояний не
вводится.

Превью обеих версий **в модель не входят**: это результат экспорта движком, живущий в UI и
не пересекающий границу ядра. Отказ построения превью (FR-016) — состояние UI, а не поле
конфликта; на решение «в файл ничего не пишется до выбора» он не влияет никак.

## Инварианты

1. Пока `BoardConflict` существует, запись в файл доски не выполняется ни автосохранением,
   ни принудительным сбросом дебаунса (FR-014).
2. Снимок обновляется только явным действием пользователя (FR-030); никакой переход
   `EmbedState` не влечёт записи файла снимка сам по себе.
3. Обновление вставки затрагивает ровно один файл снимка — тот, что закреплён за её
   `EmbedId` (FR-029).
4. Удаление вставки из текста заметки не изменяет ни доску, ни файл снимка (FR-024).
5. На профиле просмотра путь записи доски отсутствует: просмотр не может изменить файл
   (FR-035, research.md §8). С 2026-09-23 этот профиль не назначается ни одним клиентом —
   инвариант остаётся, но проверяется тестами ядра, а не мобильной сборкой.
6. Ни одна операция фичи не обращается к сети (FR-013, SC-010).
