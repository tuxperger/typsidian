# Quickstart: Drawing Boards

**Feature**: `specs/002-drawing-boards/spec.md` | **Plan**: [plan.md](./plan.md)

Сценарии проверки, что фича работает сквозь ядро и движок. Не полный набор тестов (он в
`tasks.md`), а быстрый прогон golden path и тех отказных путей, которые автотестами не
берутся.

## Предпосылки

- Собранное ядро под нативный таргет (`nix develop --command cargo test -p typsidian-core`)
  и под `wasm32-unknown-unknown`
  (`nix develop --command wasm-pack test --headless --chrome packages/core`) — принцип II
  требует оба таргета до начала проверки.
- Собранный web-клиент: `nix develop --command pnpm dev`, открыть `http://localhost:3000`.
- Браузер с поддержкой File System Access API (Chromium-based) — как в 001.
- Тестовый vault из 001 (~20 заметок во вложенных папках).
- Сторонний `typst` в PATH для сценария 6 — проверка, что заметка собирается без Typsidian.

**Про native и mobile.** `apps/desktop` в репозитории пока нет
(`001-vault-manager/tasks.md` → T112), поэтому desktop-половина FR-033 и все сценарии
мобильного просмотра (FR-034…FR-036) на момент написания невыполнимы. Это блокировка
приёмки фичи, а не повод считать сценарии пройденными: до появления оболочек они
фиксируются как «не проверено», а не как «работает».

## Сценарий 1 — Создать доску и рисовать (US1, FR-001…FR-004, FR-008)

1. В открытом vault создать доску — теми же средствами, что и заметку.
2. Ожидаемо: доска появилась в дереве **с признаком, отличающим её от заметки с одного
   взгляда** (FR-004), и открылась на полотне.
3. Нарисовать несколько фигур. Область «редактор + preview» заменена полотном **в том же
   окне**, отдельного окна не открылось (FR-006).
4. Подождать 2 секунды после последнего штриха → состояние сохранения показывает
   «сохранено» (FR-009), файл `.excalidraw` появился в папке vault (проверить `ls`).
5. Открыть этот файл сторонним просмотрщиком JSON или на excalidraw.com → рисунок
   открывается (принцип VI: файл не наш контейнер).
6. Переключиться на текстовую заметку → workspace вернулся в «редактор + preview» (FR-007),
   изменения доски сохранены (US1 AS4).
7. Перезагрузить страницу, открыть доску снова → рисунок на месте полностью (FR-012).
8. Отключить сеть целиком и повторить шаги 1-4 → поведение не отличается (FR-013, SC-010).

## Сценарий 2 — Отказ записи и предупреждение при закрытии (FR-010, FR-011)

1. Открыть доску, нарисовать, затем сделать vault недоступным на запись.
2. Ожидаемо: показана причина неудачи понятной формулировкой, **нарисованное на полотне не
   исчезло** (FR-010).
3. Попытаться закрыть вкладку → предупреждение о несохранённых изменениях (FR-011).
4. Вернуть доступ на запись, внести правку → сохранение проходит, состояние возвращается в
   «сохранено».

## Сценарий 3 — Конфликт доски (US1 AS8, AS9, FR-014…FR-016, SC-006)

1. Открыть доску, нарисовать, **не дожидаться** автосохранения.
2. Снаружи изменить тот же файл (записать другой `.excalidraw`).
3. Ожидаемо: показаны **две превью рядом** — своя и внешняя; выбор обязателен, ни одна
   версия не применяется сама (FR-015). Обе превью появляются ≤3 с (SC-006).
4. Проверить каждый исход по отдельности: оставить свою → в файле своя версия; принять
   внешнюю → на полотне внешняя.
5. **Ключевая проверка.** Повторить шаги 1-2, но подложить снаружи **повреждённый** файл
   доски. Ожидаемо: на месте недоступной превью сказано, что показать её не удалось, а
   выбор между версиями по-прежнему доступен (FR-016). Пока выбор не сделан, в файл доски
   не записано ничего.
6. Открыть повреждённый файл доски напрямую → сообщение о причине, файл **не перезаписан
   автоматически** (FR-017).

## Сценарий 4 — Вставить доску в заметку (US2, FR-018…FR-023)

1. Открыть текстовую заметку, вызвать вставку доски, выбрать доску из vault.
2. Ожидаемо: в текст добавился обычный вызов `#image(...)`, preview заметки показывает
   рисунок ≤2 с (SC-007). Действий от открытой заметки — не более трёх.
3. Посмотреть текст заметки: **никаких маркеров Typsidian вокруг вставки нет** (FR-022).
4. Посмотреть дерево: **файл снимка в дереве не показан** (FR-021), но существует в
   `<имя заметки>.assets/` — проверить `ls`.
5. Вставить **ту же** доску в эту же заметку второй раз → создан **отдельный** файл снимка
   (FR-020); в дереве по-прежнему ничего не добавилось.
6. Вставить ту же доску в другую заметку → снова отдельный файл (FR-020, FR-023).
7. В vault без досок вызвать вставку → понятное сообщение и предложение создать доску, без
   ошибки (US2 AS2).
8. Вставить **пустую** доску → вставка создаётся, показывает пустое полотно, без ошибки
   (US2 AS3).
9. Перейти по вставке → открывается соответствующая доска на полотне (FR-025).
10. Удалить вызов `#image` из текста → **доска в vault нетронута** (FR-024).

## Сценарий 5 — Устаревание вставки (US3, FR-026…FR-030, SC-008, SC-009)

1. Вставить доску в заметку, затем изменить доску и вернуться к заметке.
2. Ожидаемо: у вставки виден индикатор устаревания (FR-027).
3. **Ключевая проверка нормализации.** Открыть доску и **закрыть, ничего не меняя** →
   индикатор устаревания **не появляется**. Если появился — хэш считается по полям ревизий
   движка, а не по содержимому (research.md §5), и это дефект.
4. Нажать «обновить вставку» → снимок совпал с текущим состоянием доски, индикатор исчез
   (FR-028). Действие одно (SC-009).
5. **Ключевая проверка изоляции.** Та же доска вставлена в две заметки и изменена. Обновить
   вставку в первой → вторая заметка показывает **прежний** снимок и сохраняет собственный
   индикатор (FR-029, SC-009).
6. Изменить доску и **не обновлять** вставку → снимок в тексте остаётся прежним; система не
   обновляет его сама ни через какое время (FR-030).
7. Удалить доску из vault → у вставки показано «источник отсутствует», заметка остаётся
   читаемой и редактируемой (FR-031).
8. Вернуть доску, удалить **файл снимка** → показано «снимок отсутствует», восстановление
   одним действием из доски (FR-032).
9. **Краевой случай.** Заменить файл снимка сторонним SVG без метаданных → состояние
   вставки «сравнить не удалось» с причиной. Ожидаемо: **не** «актуально» (SC-008).

## Сценарий 6 — Заметка живёт без Typsidian (FR-022, SC-011)

1. Взять заметку со вставленной доской из сценария 4.
2. Скопировать папку vault целиком в другое место — снимки уезжают вместе с заметкой
   (FR-021).
3. Собрать заметку сторонним инструментом: `typst compile "<заметка>.typ"`.
4. Ожидаемо: документ собран **без участия Typsidian**, и рисунок в нём тот же (SC-011).
   Это же проверяет, что путь во вставке относительный и остался валидным после копирования.

## Сценарий 7 — Отзывчивость на пределе (SC-003…SC-005)

1. Подготовить доску с 2 000 элементов.
2. Открыть её → готова к рисованию ≤2 с (SC-003).
3. Рисовать непрерывно ≥30 секунд, наблюдая отклик: задержка ≤100 мс, **в том числе в
   моменты автосохранения** (SC-005). Если рывки совпадают с записью — сериализация или хэш
   выполняются в главном потоке вопреки research.md §6.
4. Перестать рисовать → изменения в файле ≤2 с (SC-004).
5. Закрыть приложение штатно сразу после правки → потерь нет (SC-004).
6. Выше 2 000 элементов поведение best-effort: проверяется отсутствие краха и потери
   данных, а не бюджеты.

## Сценарий 8 — Мобильный просмотр (FR-034…FR-036)

**Выполним только после появления `apps/mobile`.**

1. Открыть доску на мобильном клиенте → содержимое видно, инструменты рисования недоступны,
   ограничение объявлено понятной формулировкой (FR-034, SC-012).
2. Перепробовать все доступные действия → изменить содержимое доски нельзя ни одним из них;
   файл доски не изменился (FR-035) — проверить отпечаток файла до и после.
3. Вставить доску в заметку и обновить устаревшую вставку на мобильном → работает так же,
   как на web (FR-036).

## Проверка паритета таргетов (принцип II)

Логика ядра — классификация файлов, нормализация и хэш, разбор вставок, состояния —
покрывается `cargo test` и `wasm-bindgen-test` одинаковыми проверками; расхождение
результатов между таргетами является дефектом, а не платформенной особенностью.

Допустимые различия — и **только** они:

| Различие | Основание |
|---|---|
| Рисование недоступно на mobile, доска открыта на просмотр | FR-034, spec.md Clarifications |
| Источник обнаружения внешнего изменения: вотчер нативно, сверка в вебе | наследуется от 001, research.md §7 |

Любое иное расхождение поведения между таргетами — дефект.
