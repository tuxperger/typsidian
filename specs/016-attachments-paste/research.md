# Research: Вложения из буфера и перетаскиванием

**Feature**: 016-attachments-paste · **Date**: 2026-10-10

Сборка и тесты на этапе планирования не запускались (общий бриф P2): всё ниже выведено
чтением кода репозитория и исходников `wry 0.57.0` / `tauri-utils 2.10.1` из реестра cargo.
Что требует проверки прогоном — собрано в §17.

## §1 Откуда приходят файлы: один путь на три оболочки

**Decision**: во всех оболочках источник — объект `File` веб-платформы:
- вставка из буфера — `ClipboardEvent.clipboardData.files`;
- перетаскивание — `DragEvent.dataTransfer.files`;
- «Вставить изображение…», галерея и камера — скрытый `<input type="file">`.

Байты читаются `file.arrayBuffer()` по одному файлу, в момент его шага пачки. Для этого на
рабочем столе в `apps/desktop/src-tauri/tauri.conf.json` окну задаётся
`"dragDropEnabled": false`.

**Rationale**: по умолчанию Tauri перехватывает перетаскивание файлов сам
(`drag_drop_enabled: true`, `tauri-utils/src/config.rs`) и событие `drop` с файлами до
страницы не доходит. Событиями `tauri://drag-*` в проекте никто не пользуется (поиск по
`ui/` и `apps/` пуст), поэтому отключение ничего не ломает, а редактор получает то же
событие DOM, что и в браузере. Один путь — одна реализация индикатора, одна обработка,
один сценарий проверки. Диалог выбора файлов тоже не требует плагина: `<input type="file">`
открывает системный диалог и в WebKitGTK, и в Android WebView.

**Alternatives considered**:
- Оставить перехват Tauri и слушать `onDragDropEvent` — отдаёт абсолютные пути вместо
  байтов. Понадобились бы команда чтения произвольного файла вне vault, пересчёт координат
  окна в позицию текста и второй путь кода рядом с web-версией. Отклонено.
- `tauri-plugin-dialog` для выбора файлов — на Android его нет в оболочке намеренно
  (`apps/mobile/src-tauri/src/lib.rs`), а на рабочем столе он дал бы пути, а не байты.
  Отклонено.

**Следствие**: пути исходного файла приложение не знает ни в одной оболочке. «Файл уже
лежит в vault» (FR-011) определяется по содержимому — §7.

## §2 Android: камера и галерея

**Decision**: без плагинов и без кода на Kotlin. Три действия шторки — три вида одного
`<input type="file">`:

| Действие | Атрибуты | Что делает WebView (`wry`, `RustWebChromeClient.kt`) |
|---|---|---|
| Снять фото | `accept="image/*" capture="environment"` | `onShowFileChooser` видит `isCaptureEnabled` и запускает `MediaStore.ACTION_IMAGE_CAPTURE`; снимок пишется во временный файл через `FileProvider` |
| Выбрать из галереи | `accept="image/*" multiple` | `ACTION_GET_CONTENT` с типом `image/*` |
| Выбрать файл… | `multiple` | `ACTION_GET_CONTENT` без фильтра; лишнее отсеет ядро (FR-006) |

`FileProvider` с `cache-path` уже объявлен в
`apps/mobile/src-tauri/gen/android/app/src/main/AndroidManifest.xml` и
`res/xml/file_paths.xml`. Разрешение `CAMERA` в манифест **не добавляется**.

**Rationale**: `isMediaCaptureSupported` в `wry` истинно, когда разрешение выдано **или не
объявлено в манифесте**. Приложению, которое не объявляет `CAMERA`, Android позволяет
запускать системную камеру без запроса: снимает не приложение, а камера устройства. Меньше
прав у приложения, нет диалога разрешения и нет состояния «отказано».

Какие действия показывать, решает оболочка: `Workspace` получает проп
`imageSources: { camera: boolean; gallery: boolean }`. Web и рабочий стол его не передают
(оба `false`) — «Снять фото» и «галерея» там отсутствуют (FR-022). Мобильная оболочка
передаёт `gallery: true`, а `camera` — по наличию камеры:
`navigator.mediaDevices.enumerateDevices()` перечисляет устройства `videoinput` без запроса
разрешения. Это платформенная склейка в `apps/mobile`, а не правило.

**Alternatives considered**:
- Свой плагин Tauri на Kotlin (`ActivityResultContracts.TakePicture`, явный запрос
  `CAMERA`) — даёт различимый отказ в разрешении и точное определение камеры, но это
  первый нативный код в оболочке, новая зона сборки (`nix-env-agent`) и работа, которую
  нельзя проверить без устройства. Отложено: понадобится, только если нужен собственный
  экран съёмки.
- Объявить `CAMERA` в манифесте — `wry` начнёт запрашивать разрешение, но при отказе
  возвращает странице пустой результат, неотличимый от отмены. Причину назвать было бы
  нечем, то есть FR-022 оказался бы нарушен там, где сейчас он не срабатывает вовсе.
  Отклонено.

**Что это значит для FR-022 и US4 AS2**: отмена съёмки возвращает пустой выбор — текст не
меняется. Ветка «не дал разрешения на камеру» при таком решении недостижима: разрешение не
запрашивается. Строка макета «Нет доступа к камере…» поэтому не верстается (§16).
Вынесено в открытые вопросы.

**Имя снимка**: временный файл камеры называется служебно (`JPEG_…`). Источник «камера»
получает имя по правилу буфера (§5); файлы из галереи и диалога сохраняют своё.

**HEIC**: галерея может отдать HEIC — Typst его не читает, вид не входит в FR-006, файл
пропускается с именем в отчёте.

## §3 Вставка из буфера: текст или картинка

**Decision**: обработчик `paste` в расширении CodeMirror забирает событие только при
одновременном выполнении условий:
1. `clipboardData.getData("text/plain")` пуст;
2. в `clipboardData.files` есть хотя бы один файл.

Иначе событие не трогается и CodeMirror вставляет текст как раньше (FR-002, US1 AS3, AS4).
`text/html` при пустом `text/plain` текстом не считается: так выглядит копирование картинки
со страницы браузера.

**Rationale**: это маршрутизация события DOM — кому оно достанется, — того же рода, что
распознавание `/` в `CodeEditor.tsx`. Является ли файл изображением, решает ядро по
содержимому (§4): обработчик передаёт ему все файлы буфера, не глядя на MIME.

**Alternatives considered**: `navigator.clipboard.read()` по команде — требует разрешения,
в WebKitGTK и Android WebView работает неодинаково. Обычная вставка даёт картинку без
разрешений там, где браузер её отдаёт (Edge Case спеки про web-оболочку). Отклонено.

## §4 Вид файла — по содержимому

**Decision**: `attachments::kind::sniff(bytes) -> Option<ImageKind>`:

| Вид | Сигнатура |
|---|---|
| PNG | `89 50 4E 47 0D 0A 1A 0A` |
| JPEG | `FF D8 FF` |
| GIF | `GIF87a` или `GIF89a` |
| WebP | `RIFF` + 4 байта длины + `WEBP` |
| SVG | текст UTF-8: после BOM, пробелов, `<?xml …?>`, комментариев и `<!DOCTYPE …>` идёт `<svg` с границей имени; просматриваются первые 4 КБ |

Всё остальное — `None`: файл не копируется и называется в отчёте (FR-006).

Расширение приводится к виду: если расширение исходного имени не принадлежит найденному
виду (`photo.png` с содержимым JPEG, имя без расширения), оно **заменяется** на каноническое
(`photo.jpg`), а в отчёте сказано, под каким именем файл сохранён.

**Rationale**: Typst выбирает декодер изображения по расширению пути и только при
незнакомом расширении смотрит в данные (`determine_format_from_path` в
`typst-library 0.15.1`, `visualize/image/mod.rs`). JPEG под именем `.png` дал бы ошибку сборки вместо картинки и
нарушил FR-008. Основа имени при этом сохраняется (FR-012).

**Alternatives considered**: крейт `infer` или `image` — новая зависимость ради пяти
сигнатур; `image` ещё и тяжёл для wasm. Отклонено.

## §5 Имя вложения

**Decision**:
- буфер и камера: `<имя заметки без расширения>-ГГГГ-ММ-ДД-ЧЧММСС.<расширение>` —
  `Результаты-2026-10-10-142305.png`, как в макете 1a;
- перетащенный, выбранный и взятый из галереи файл: исходное имя после очистки.

Момент вставки — местное время устройства, приходит из UI структурой `InsertMoment`: часов
в ядре нет ни на одном таргете (тот же довод, что у `set_aside_invalid`).

Очистка имени: остаётся последняя часть пути; символы `/ \ : * ? " < > |`, управляющие и
NUL заменяются на `-`; пробелы и точки по краям срезаются; пустой результат — `image`.

**Rationale**: vault доставляется на другие устройства (SC-006), и имя, допустимое на
Linux, но не на Android или Windows, сломало бы доставку. Кавычка, кроме того, попадает в
строку Typst.

## §6 Папка вложений и настройка

**Decision**: два поля `VaultOverrides`, таблица `attachments` в `.typsidian/vault.json`:

```json
{ "attachments": { "placement": "next-to-note", "folder": "attachments" } }
```

- `attachments_placement: Option<AttachmentsPlacement>` — `NextToNote` (умолчание) или
  `VaultFolder`;
- `attachments_folder: Option<String>` — умолчание `attachments` (общий бриф, решение 7).

Папка назначения: `NextToNote` → `<папка заметки>/<folder>`; `VaultFolder` → `<folder>` от
корня vault. Название проверяет `attachments::folder::validate_folder` — те же правила, что
у папки экспорта (`export::folder::validate_folder`), вызванные оттуда же, с собственным
типом причины `AttachmentsFolderProblem` (`Empty`, `Absolute`, `LeavesVault`,
`ServiceFolder`). `write_vault_settings` отклоняет негодное значение ошибкой
`InvalidAttachmentsFolder { problem }`, не трогая файл; разбор файла отбрасывает негодное
значение молча — как папку экспорта.

Название может состоять из нескольких частей (`файлы/картинки`) в обоих режимах.

**Rationale**: отдельная таблица, а не поля в `assets`: `assets.placement` — расположение
снимков досок (006) с тремя вариантами и разделами, это другая настройка с другим набором
значений. Старые версии приложения незнакомую таблицу сохраняют (`render` переносит
неизвестные ключи).

**Alternatives considered**: переиспользовать `AssetsPlacement` — у него есть `SectionRoot`,
которого спека 016 не просит, а раскладка `assets/<заметка>/` не совпадает с плоской папкой
вложений. Отклонено.

## §7 Сопоставление по содержимому (FR-010, FR-011)

**Decision**: сравниваются **байты**, а не хэши. Кандидаты отбираются по размеру, каждый
читается `read_bytes_any_size` и сравнивается с входящим файлом целиком.

- FR-010: кандидаты — изображения в папке назначения с тем же размером, имя любое;
- FR-011 (только для файлов с собственным именем): кандидаты — изображения где угодно в
  vault с тем же именем и тем же размером.

Совпало — файл не пишется, вставка ведёт на найденный.

Список изображений даёт новый метод трейта:

```rust
async fn list_images(&self, folder: Option<&Path>) -> Vec<ImageFile>;  // { path, size }
```

`None` — обход всего vault по правилам обхода шрифтов (`list_fonts`: скрытые папки и
символические ссылки пропускаются, читаются только метаданные). `Some(folder)` — файлы
одной папки без вложенных. Умолчание трейта — пустой список.

Обход выполняется **один раз на действие**, в `batch::start`. В состоянии пачки остаются
только нужные записи: изображения папки назначения и изображения, совпавшие с входящими по
имени и размеру. Записанные пачкой файлы добавляются туда же — два одинаковых файла в одной
пачке дают один файл на диске. Для буфера и камеры полный обход не нужен и не делается.

**Rationale**: хэш понадобился бы для индекса «содержимое → путь», а индекса нет и заводить
его незачем: производное состояние пришлось бы хранить и чинить. Кандидата всё равно нужно
прочитать, и сравнение байтов после чтения точнее и дешевле хэширования обеих сторон.
`blake3` в ядре есть (`FileStamp::from_content`, `sync::ignore::version_mark`), но здесь не
нужен.

Пути исходного файла нет (§1), поэтому «уже лежит в vault» означает «в vault есть файл с
тем же именем и содержимым». Для пользователя исход тот же: копия не создаётся.

**Alternatives considered**: `DataTransferItem.getAsFileSystemHandle()` +
`FileSystemDirectoryHandle.resolve()` в web и абсолютные пути в Tauri — точное «тот самый
файл», но два платформенных механизма в UI вместо одного правила в ядре. Отклонено
(принципы I и II).

## §8 Коллизии имён и запрет перезаписи (FR-009, SC-003)

**Decision**: имя занято, если `file_mark(папка/имя)` вернул отметку **или** в папке есть
изображение с тем же именем без учёта регистра. Занятое имя получает суффикс перед
расширением: `схема.png` → `схема-2.png` → `схема-3.png`. Затем `ensure_folder` и
`write_bytes`.

**Rationale**: регистр учитывается потому, что vault может доставляться на файловую систему
без различения регистра, где `Фото.PNG` и `фото.png` — один файл.

Запись атомарна на обоих таргетах (009 research.md §4): при отказе на месте файла ничего не
остаётся (FR-014). Пустая папка вложений, созданная до отказавшей записи, остаётся — это
папка, а не частично записанный файл.

**Известное окно**: между проверкой имени и записью посторонняя программа может создать
файл с тем же именем, и атомарная запись его заменит. Операции «создать, только если нет»
для байтов у `VaultBackend` нет; заводить её ради окна в миллисекунды на имени, которое
приложение только что придумало, не стали. Проверка выполняется непосредственно перед
записью.

## §9 Путь и текст вставки

**Decision**:
- путь во вставке — от папки заметки до файла, разделитель `/`, с `../` при общей папке
  vault: `boards::placement::relative_to` (становится `pub(crate)`), тот же расчёт, что у
  снимков досок;
- запись — `#image("<путь>")`, в строке экранируются `\` и `"`;
- правку считает ядро: `attachments::markup::plan_markup(text_length, point, before, after,
  paths, block) -> InsertionEdit` (тип фичи 003). `before`/`after` — текст строки до и
  после точки вставки;
- правило строк: `block = false` (одна картинка из буфера, с камеры или выбранная командой)
  — запись встаёт в точку как есть, каретка после неё (US1 AS1); `block = true`
  (перетаскивание и любая пачка из нескольких файлов) — записи разделяются `\n`, перед
  первой добавляется `\n`, если в строке до точки есть непробельный текст, после последней
  — если есть после (US2 AS2);
- точка вставки при перетаскивании — начало строки под указателем; ниже последней строки —
  конец документа. Так её и показывает индикатор макета;
- правка применяется через порт `InsertionTarget` фичи 003 (`plainInputTarget`): одна
  транзакция CodeMirror, одна единица отмены (FR-005).

**Rationale**: правило «где переносы» обязано быть одним для трёх оболочек и трёх
источников; порт уже гарантирует одну отмену и сохранность истории. Принцип V — см. plan.md
→ Complexity Tracking.

## §10 Пачка: машина состояний, подтверждение, отмена

**Decision**: `attachments::batch` по образцу `export::batch`. Одна картинка из буфера —
пачка из одного элемента, отдельного пути нет.

1. `start(backend, overrides, note_path, items, moment)` — асинхронная: проверяет право
   записи, считает папку, один раз собирает кандидатов (§7) и признак «папка исключена»
   (§12). Vault только на чтение → фаза `Refused` (FR-024).
2. Элементы больше 20 МБ (`LARGE_IMAGE_BYTES`, строго больше) получают статус
   `AwaitingConfirmation`. `step` сначала выдаёт все подтверждения, потом копирование:
   пользователь отвечает до начала работы, а не посреди неё. `confirm(state, index,
   accept)` → `Queued` либо `Declined`.
3. `step` → `Copy { index }`; UI читает байты этого файла и вызывает `store(backend, state,
   index, bytes)`. Он определяет вид, сопоставляет, выбирает имя, пишет и записывает исход в
   состояние.
4. `cancel` действует между файлами: текущий доводится до конца, остальные `Cancelled`.
5. `view` отдаёт прогресс, итог и пути для вставки в порядке элементов.

Отказ одного файла пачку не останавливает: остальные копируются и вставляются, отказавший
назван с причиной.

**Одна правка в конце.** Текст меняется один раз — когда пачка закончилась или отменена, —
всеми записями сразу (FR-005). Пока идёт копирование, пользователь может печатать: позиция
вставки хранится в `StateField` расширения и переносится через каждую правку (`mapPos`),
как поля сниппета в `snippet.ts`.

**Заметка закрыта до конца копирования.** Редактор уничтожен, вставлять некуда. Пачка
отменяется, уже скопированные файлы остаются в vault, в отчёте сказано, что они сохранены,
но не вставлены. Писать в файл закрытой заметки в обход редактора не стали: это вторая
дорога записи текста мимо автосохранения и обнаружения конфликтов (001). Вынесено в
открытые вопросы.

**Rationale**: правила очереди живут в ядре и проверяются на обоих таргетах; состояние
ходит через границу значением, оболочкам не нужно хранить объект (то же, что 009
research.md §5).

## §11 Байты через границу

**Decision**:
- web: `attachmentsBatchStore(backend, state, index, bytes: &[u8])` — `Uint8Array` напрямую,
  вызов через `wasm-call-queue`, как прочие обращения к `WebBackend`;
- Tauri: команда `attachments_batch_store` принимает **сырое тело** (`tauri::ipc::Request`,
  `InvokeBody::Raw`). Формат тела: 4 байта длины little-endian, затем JSON
  `{ "state": …, "index": … }` в UTF-8, затем байты файла.

**Rationale**: `Vec<u8>` в аргументах команды сериализуется массивом чисел JSON — в 3–4 раза
больше исходного и заметно медленно на 20 МБ. Заголовки запроса для состояния не годятся:
в нём пути с кириллицей. Остальные команды пачки — обычные, с JSON.

Сегодня бинарных команд в `packages/shell` нет — это первая. Зона `tauri-shell-agent`.

## §12 «Папка исключена правилами» (FR-020)

**Decision**: чистая функция `sync::ignore_match::excludes(file, text, path) -> bool` и
асинхронная `attachments::exclusion(backend, folder) -> Vec<IgnoreFile>`: читает корневые
`.gitignore` и `.stignore` и проверяет **папку назначения**.

Поддерживается: комментарии и пустые строки, `!`, якорь `/`, завершающий `/`, `*`, `?`,
`[…]`, `**`; для `.stignore` — префиксы `(?i)` и `(?d)` и перечисление `{a,b}`. В
`.gitignore` выигрывает последнее совпавшее правило, в `.stignore` — первое; папка
исключена, если исключена она сама или любая папка над ней. Шаблоны переводятся в `regex`.

Не поддерживается и записано как ограничение: `#include` в `.stignore`, вложенные
`.gitignore` в подпапках, глобальные правила git, правила каталогов выше vault. Правила,
исключающие отдельные файлы (`*.png`), не учитываются: FR-020 говорит о папке.

Предупреждение показывается, когда файл правил существует и исключает папку — независимо от
того, включена ли история на этом устройстве: файл правил доставляется вместе с vault и
действует там, где история есть.

**Rationale**: готового сопоставления путей в ядре нет: `sync::ignore` ведёт блок
обязательных правил и сверяет их дословно. `git2` умеет отвечать «игнорируется ли путь», но
только на native и только при существующем репозитории — принцип II требует одной
реализации на оба таргета.

Кнопка «Открыть правила» открывает редактор правил фичи 012
(`ui/src/sync/IgnoreEditor.tsx`) на соответствующем файле.

## §13 Предпросмотр и предел 10 МБ

**Проблема**: `preview::resolve::read_dependency` читает связанный файл через
`backend.read_bytes`, а тот отказывает `TooLarge` для всего, что больше
`NOTE_SIZE_LIMIT_BYTES` (10 МБ). Изображение на 12 МБ сегодня вставилось бы без единого
вопроса (порог подтверждения — 20 МБ) и не показалось бы в предпросмотре — нарушение FR-008.

**Decision**: для файлов изображений (`vault::is_image_file`) `read_dependency` читает через
`read_bytes_any_size`. Для `.typ` и прочих связанных файлов предел остаётся.

**Rationale**: предел защищает редактор от заметки на десятки мегабайт; к картинке он
применялся по совпадению. Пользователь, подтвердивший вставку 34 МБ, обязан увидеть её в
документе.

**Alternatives considered**: опустить порог подтверждения до 10 МБ и отказывать выше —
противоречит спеке (порог 20 МБ, «уменьшать само не берётся», отказа по размеру нет).
Отклонено.

## §14 Команда и сочетание

**Decision**: `CommandId::InsertImage` (`"insert-image"`, «Вставить изображение…»),
умолчание `Mod+Alt+I` (общий бриф, решение 6). Добавляется в конец `COMMANDS`.

Проверено по `keybindings.rs`: `i` — обычная буква, `Shortcut::problem()` её не отвергает;
среди умолчаний на `Mod+Alt` заняты `s c h u g m`, `i` свободна. В `ui/src/editor/`
зашитых сочетаний с `Alt` нет (`defaultKeymap`, `historyKeymap`, `Tab`/`Escape` сниппета).
На macOS `Cmd+Alt+I` в браузере открывает инструменты разработчика — тот же случай, что
у прочих занятых браузером сочетаний: команда остаётся в палитре и меню, сочетание
переназначается в настройках.

Команда доступна, только когда открыта заметка Typst и vault доступен на запись; в vault
только на чтение пункт палитры показан недоступным с причиной (FR-024).

## §15 Ссылка вместо файла и сеть

**Decision**: приложение не ходит в сеть за изображениями ни при каком состоянии сети.
Перетаскивание без файлов, но с `text/html`, содержащим `<img`, — это картинка, брошенная
ссылкой: текст не меняется, показывается сообщение «перетащена ссылка, а не файл —
сохраните изображение и перетащите файл». Прочее перетаскивание без файлов (выделенный
текст) не перехватывается.

**Rationale**: спека относит «скачивание по адресу» к «вне скоупа», а в Edge Cases требует
только назвать причину. Скачивание из web-оболочки к тому же упёрлось бы в CORS и вело бы
себя по-разному на трёх клиентах. Самое консервативное прочтение — не скачивать никогда;
принцип VII выполняется тривиально. Вынесено в открытые вопросы.

## §16 Расхождения с макетом

Решает спека (design-typsidian).

1. **1c, «Нет доступа к камере…»** — не верстается: разрешение не запрашивается, состояния
   нет (§2).
2. **1b, «Пропущено — не изображения»** — текст «Пропущено — вид не поддерживается»:
   пропускаются и изображения неподдерживаемых видов (HEIC, BMP, TIFF), а спека говорит о
   «неподдерживаемом виде» (FR-006).
3. **1b, предупреждение «на других устройствах его не будет»** — текст зависит от файла
   правил: для правил истории — «не попадёт в историю», для правил доставки — «не будет
   доставлено на другие устройства»; при обоих — обе фразы.
4. **1a, статус-бар `NORMAL`** — индикатор режима редактора из общего шаблона, к фиче не
   относится и не добавляется.
5. **Добавлено сверх макета**: в итоговом отчёте — строки «сохранён как <имя>» при замене
   расширения (§4) и «заметка закрыта — сохранены, но не вставлены» (§10); сообщение о
   ссылке вместо файла (§15). Оформляются теми же панелями 1b.
6. **1c, поле с ошибкой** — в макете два поля рядом для показа состояний; в вёрстке поле
   одно, ошибка под ним.

## §18 Замечание о скриптах Spec Kit

Общий бриф предписывает запускать скрипты с `SPECIFY_FEATURE=016-attachments-paste`. По
коду `.specify/scripts/bash/common.sh` каталог фичи эта переменная не выбирает: он берётся
из `SPECIFY_FEATURE_DIRECTORY` либо из `.specify/feature.json`, причём первая переменная
вне режима `--paths-only` **переписывает** `feature.json`. Запуск `setup-plan.sh` с
`SPECIFY_FEATURE` указал на `specs/013-backlinks-mentions` (план там уже существовал,
скрипт ничего не изменил). Поэтому `plan.md` этой фичи создан напрямую по шаблону, а
`feature.json` не тронут.
