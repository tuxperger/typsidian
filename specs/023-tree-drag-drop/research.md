# Research: Перетаскивание в дереве файлов

Состояние кода на 2026-10-12, от которого отталкиваются решения:

- `VaultBackend::rename` (`packages/core/src/vault/backend.rs:329`) — единственная
  операция смены пути. На native (`native.rs:1354`) это `std::fs::rename`, папку он
  переносит, но `NoteIndex::rename` (`index.rs:95`) переставляет одну запись: заметки
  внутри папки остаются в индексе под старыми путями. На web (`web.rs:626`) это
  «прочитать текст → создать → записать → удалить» — только один текстовый файл.
- Состояние несохранённых правок (`ConflictRegistry`, `conflict.rs:76`) и таблица
  ссылок кэша (`cache.rs`, `rename_note`) адресуются путём заметки.
- Ссылки `[[имя]]` разрешаются относительно папки заметки-источника, `[[/путь]]` — от
  корня vault (`graph/mod.rs:73`). Кэш хранит уже разрешённые цели.
- Пометки разделов переезжают префиксом (`sections.rs:103`) — готово.
- Дерево (`ui/src/vault-tree/buildTree.ts`) строится из списка заметок: папка существует
  в дереве, только если в ней или глубже есть заметка или доска.
- JS-тестов в репозитории нет; интерфейс проверяется сценарием headless-браузера.

## §1. Отдельная операция переноса, а не вызов `rename` из интерфейса

**Decision**: в трейт `VaultBackend` добавляется `move_entry(from, to_folder, …)`; общая
часть (проверки, план, обновление индекса, правок, кэша, разделов, событий) — в новом
модуле `vault/relocate.rs`, одинаковая для обоих backend. `rename` остаётся для
переименования заметки и не меняется.

**Rationale**: интерфейс, собирающий перенос папки из `rename` по одному файлу,
дублировал бы правила допустимости и порядок обновления состояния (принцип I), а
текущий `rename` для папки оставляет индекс несогласованным.

**Alternatives considered**: расширить `rename` до папок — смешивает проверку имени
заметки (`valid_note_name`) с переносом и меняет поведение существующих вызовов;
перенос папки циклом `rename` в UI — логика вне ядра, нет общей точки отката.

## §2. Что именно переезжает: план переноса

**Decision**: чистая функция `plan_move` строит `MovePlan` — список пар «откуда → куда»
верхнего уровня:

1. сам элемент: `from` → `to_folder/имя`;
2. для одиночной заметки — её собственные папки снимков, если они существуют:
   прежняя `<заметка>.assets` рядом (002) и `<папка>/assets/<заметка>/` при
   расположении «рядом с заметкой» (006). Пути берутся из `boards::placement` /
   `boards::snapshot`, а не собираются заново.

Для папки пункт 2 не нужен: всё лежит внутри неё.

**Rationale**: FR-018a; правило расположения снимков уже живёт в `boards/`, вторая его
копия разошлась бы с первой.

**Alternatives considered**: переписывать путь вставки в тексте заметки — запрещено
FR-019; переносить и общие папки ассетов корня/раздела — они общие для многих заметок.

## §3. Допустимость цели

**Decision**: `plan_move` отклоняет перенос причинами `MoveRefusal`: `SamePlace`
(пустое действие, FR-005), `IntoItself` (FR-003), `NameConflict { name }` (FR-004,
включая конфликт папки снимков), `NotFound`, `TargetNotFound`, `AccessDenied`,
`ServiceFolder`. Занятость имени проверяется по диску тем же способом, что в
`create`/`rename` (001 §FR-012), а не по индексу: в цели может лежать файл, которого
дерево не показывает.

Для подсветки во время жеста интерфейс один раз на захват спрашивает
`move_targets(from)` — список папок, которые могут принять элемент (без `SamePlace`,
`IntoItself`, служебной папки). Проверка под указателем — принадлежность множеству.

**Rationale**: FR-012 требует не подсвечивать недопустимое, а вызов ядра на каждое
движение указателя на desktop — это IPC. Конфликт имён в список не входит: он
сообщается после броска (FR-012) и требует обращения к диску.

**Alternatives considered**: проверять `startsWith` в интерфейсе — вторая копия правила.

## §4. Разрываемые ссылки

**Decision**: `move_impact(from, to_folder)` возвращает `MoveImpact { broken: Vec<Note> }`
— заметки, у которых после переноса хотя бы одна сейчас рабочая ссылка перестанет
находить адресата. Считается так: строится отображение путей всех переезжающих
заметок; для кандидатов (переезжающие заметки и источники обратных ссылок на них)
читается текст, сырые цели `extract_links` разрешаются дважды — в положении «до» и
«после» (источник и цель оба пропускаются через отображение); ссылка разрывается, если
«до» цель существовала, а «после» — нет. Ядро расчёта — чистая функция
`broken_by_move(sources, existing, mapping)`.

**Rationale**: FR-016/FR-017. Кэш хранит разрешённые цели, а после переноса меняется
само разрешение (относительные ссылки), поэтому нужны сырые цели. Читаются только
кандидаты, не весь vault.

**Alternatives considered**: `backlinks(from)` как при переименовании — не видит
собственных относительных ссылок перенесённой заметки и ложно срабатывает на ссылки
между заметками одной переносимой папки.

## §5. Исполнение на native

**Decision**: каждая пара плана — один `std::fs::rename`. Если вторая пара (папка
снимков) отказала, первая возвращается обратным `rename`; исход — `Io` без изменений.
Затем под замками в существующем порядке index → cache обновляются: индекс (перенос
всех записей с префиксом), `ConflictRegistry` (буферы, конфликты, «удалено с
правками»), кэш ссылок (переезд записей и переразбор ссылок перенесённых заметок),
разделы (`move_sections`). Публикуются `NoteRenamed` на каждую заметку и один
`LinksInvalidated`.

**Rationale**: атомарно и мгновенно на одной файловой системе при любом размере папки
(SC-005); индекс обновлён до того, как наблюдатель `notify` доставит события, — тот же
приём, которым сегодня `rename` не выглядит внешним изменением (FR-008). Проверяется
тестом: после `move_entry` и прохода сверки в очереди событий нет
`NoteDeleted`/`NoteDeletedWithUnsavedEdits`/`BulkChange*`.

**Alternatives considered**: копирование с удалением — медленно и неатомарно без нужды;
при `EXDEV` (папка-симлинк на другой том) перенос отклоняется как `Io`, запасного
копирования нет.

## §6. Исполнение на web

**Decision**: у File System Access API нет переноса папок, поэтому на web перенос —
«скопировать всё в цель → убедиться → удалить источник», байтами
(`read_bytes_any_size`/`write_bytes`, `ensure_folder`), по одному файлу. Сбой или
отмена на этапе копирования удаляют скопированное в цели — источник не тронут,
перенос «откачен целиком». Сбой на этапе удаления источника оставляет полную копию в
цели и остаток в источнике: исход `Partial { left: Vec<PathBuf> }`, индекс
перечитывается с диска (FR-007).

Ход и отмена: `move_entry` принимает `MoveControl` — счётчик «сделано/всего» и флаг
отмены; на web это объект с колбэком прогресса и флагом, который интерфейс держит у
себя (вызов ядра занят `&mut self`, второй вызов «отмени» в него не войдёт).

**Rationale**: принцип X — массовая операция отменяема, неблокирующая (между файлами
управление возвращается циклу событий), с прогрессом; отмена не оставляет частично
записанных файлов.

**Alternatives considered**: `FileSystemHandle.move()` — для папок вне OPFS не
реализован; использовать только там, где есть, значит два поведения на одном таргете.

## §7. Отмена последнего переноса

**Decision**: `MoveOutcome::Done` несёт `undo: MoveRequest` — готовый обратный запрос
(элемент на новом месте → прежняя папка). Интерфейс хранит его, пока видно сообщение,
и отправляет тем же `move_entry` без предупреждения о ссылках. Занятое прежнее место
даёт обычный `NameConflict` (FR-025).

**Rationale**: обратный перенос — тот же перенос; отдельной истории операций нет
(Assumptions спеки). Предупреждение не нужно: отмена восстанавливает ссылки.

## §8. Жест: Pointer Events, а не HTML5 Drag and Drop

**Decision**: перетаскивание строится на `pointerdown/move/up` с захватом указателя.
Мышь и перо начинают перенос после сдвига на 4 px, палец — после удержания 400 мс без
сдвига больше 8 px. Ярлык у указателя — свой элемент, цель определяется через
`elementFromPoint` по атрибуту `data-drop-folder` на строках.

**Rationale**: HTML5 DnD не даёт долгого нажатия на сенсорном экране (US5), не даёт
оформить ярлык по макету и в webview Tauri перехватывается системным приёмом файлов
(`dragDropEnabled`), который понадобится фиче 016. Один механизм на три оболочки.

**Alternatives considered**: HTML5 DnD + отдельный сенсорный путь — два механизма с
разным поведением; библиотека (dnd-kit) — новая зависимость ради одного дерева.

**Числа жеста** (из макета, в одном месте — `useTreeDrag.ts`): порог сдвига 4 px,
удержание 400 мс, раскрытие свёрнутой папки 600 мс, полоса прокрутки у края 28 px,
сообщение об итоге 8 с. Это параметры жеста, а не правила предметной области.

## §9. Что следует за путём в интерфейсе

**Decision**: `MoveOutcome` несёт `moved: Vec<PathChange>` — пары по каждой заметке и
доске и по каждой папке. `Workspace` применяет их одной функцией: открытая заметка или
доска получает новый путь без перечитывания файла и без пересоздания редактора
(буфер, каретка, прокрутка остаются); раскрытость папок дерева и выделение
переадресуются. Раскрытость папок для этого поднимается из локального состояния
`FolderRow` в общее множество путей в `useVaultTreeActions`.

**Rationale**: FR-020. Сейчас раскрытость — `useState` внутри строки папки и теряется
при любом перестроении дерева; после переноса строка папки — другой узел React.

**Alternatives considered**: ключ узла по стабильному идентификатору — у папок его нет.

## §10. «Переместить в…»

**Decision**: окно `MoveToDialog` в ряду с палитрой команд (те же классы
`ts-palette*`). Список и фильтр даёт ядро: `move_targets(from, query)` возвращает
строки `MoveTarget { path, name, parent, is_section, name_match }` в порядке показа —
корень первым, далее по пути; фильтр — подстрока без учёта регистра по имени и пути.
В палитре ⌘K — команда «Переместить в…» для открытого файла; сочетания по умолчанию
нет, новая `CommandId` не заводится: палитра уже показывает действия без `CommandId`
— способ сверяется первой задачей интерфейса, иначе добавляется `CommandId::MoveEntry`
с пустым сочетанием.

**Rationale**: FR-021…FR-023; фильтрация в ядре — по образцу 015 (принцип I).

## §11. Расхождения макета и существующего кода

- **Decision**: диалог предупреждения — существующий `BacklinksConfirmDialog` с новым
  текстом; макет рисует его так же. Расхождений со спекой макет не вводит.
- **Decision**: прогресс переноса — в нижней строке боковой панели
  (`ts-sidebar__footer`), как на макете; на native он не успевает показаться.
- Макет временный (не Claude Design): при перерисовке в Claude Design сверяется
  вёрстка, а не спека.
