# Research: Режим показа слайдов

**Feature**: 019-slides-mode | **Date**: 2026-10-15

## §1. Сопоставление каретки и страницы

**Decision**: при сборке для каждой страницы собирается диапазон текста заметки, попавшего на
неё: обход кадра страницы, у каждого глифа `TextItem` — его `Span`; спаны главного файла
переводятся в байтовые диапазоны через мир сборки (`world.range`) и сводятся к `[start, end)`
страницы, затем к месту `SlidePlace`: смещение UTF-16 (`text_offsets.rs`) для сравнения с
кареткой и строка/колонка — переход в редакторе (`revealPlace`) работает строкой и колонкой. Страница без текста главного файла
(картинка, текст из `#include`) получает `None`. Слайд под кареткой — страница с наибольшим
`start ≤ caret` среди страниц с диапазоном, при равенстве — первая; каретка у слайда — `start`
этой страницы, а у страницы без диапазона — `start` ближайшей предыдущей.

**Rationale**: 005 сопоставления не даёт (005 spec «Вне скоупа»: «синхронная прокрутка и
переход от места в документе к тексту»), а текстовый слой 005 спанов не хранит. Спаны глифов —
то же, на чём `typst-ide` строит `jump_from_cursor`, но без зависимости от `typst-ide` и
без хранения кадров: на выходе 2 числа на страницу. Сравнение по `start` устойчиво для
пошаговых слайдов: у всех шагов одного слайда одинаковый текст и одинаковый `start`, и
выбирается первый шаг — так и ожидается при запуске «с места каретки».

**Alternatives considered**: `typst_ide::jump_from_cursor` — новый крейт и хранение
`PagedDocument` между сборкой и запросом (в web сборка идёт в воркере, документ в главный
поток не приходит); поиск по тексту в текстовом слое (как `locate_heading` 015) — неточен на
повторяющихся заголовках слайдов («Итоги», «Вопросы»).

## §2. Заметки докладчика и номер слайда

**Decision**: интроспектор собранного документа опрашивается на элементы `metadata` с меткой
`<pdfpc>`; у каждого — страница из `introspector.position(location).page`. Используются
значения-словари с ключом `t`:

| `t` | `v` | Что берётся |
|---|---|---|
| `"Note"` | строка или содержимое | заметка докладчика страницы; у содержимого — `plain_text()`; несколько — через пустую строку |
| `"LogicalSlide"` | целое | номер логического слайда страницы |
| `"NewSlide"`, `"Idx"`, `"Overlay"`, прочие | — | не используются |

Значение, не подходящее под таблицу, пропускается молча. У страницы без `LogicalSlide` номер
слайда не известен: подпись показывает номер страницы (spec Edge Cases).

**Rationale**: именно этой разметкой polylux (`pdfpc.speaker-note`) и touying
(`speaker-note`) выгружают заметки для pdfpc (`typst query --field value <pdfpc>`); оба
пакета ставят метку на каждую страницу слайда. Приложение не привязывается к пакету
(spec Assumptions): документ без пакета, но с такой разметкой, ведёт себя так же. Тесты
пишут разметку руками (`#metadata((t: "Note", v: "…")) <pdfpc>`) — пакеты не нужны и сети в
тестах нет. Сверка с настоящими пакетами — ручной шаг quickstart.md §4.

**Alternatives considered**: `#pdfpc` JSON-файл рядом с PDF — требует экспорта; разбор
вызова `speaker-note` в исходнике — привязка к именам функций пакетов и не видит заметок из
шаблонов.

## §3. Где собираются сведения

**Decision**: `CompiledDocument` получает поле `slides: Vec<PageSlideInfo>` — по одной записи
на страницу, в том же порядке, что `pages`. Заполняется в `compile_with` при `Render::Pages`,
пока документ и мир ещё живы; при `Render::Pdf` (009) не собирается. У неудавшейся сборки —
пусто, как и `pages`.

**Rationale**: в web документ живёт только в воркере 005; всё нужное показу должно приехать
готовым вместе со страницами. Отдельное поле, а не поля `RenderedPage`: страница 005 — единица
показа предпросмотра и сравнения по `digest`, а сведения о слайде к ней не относятся.

**Alternatives considered**: поля в `RenderedPage` — меняют контракт 005 и его тесты без нужды.

## §4. Состояние показа и листание

**Decision**: `ShowState { page, total, started_at_ms }` — значение, которое окно редактора
держит и передаёт в ядро вместе с действием: `navigate(state, slides, action) → state`.
Действия: `Next`, `Previous`, `First`, `Last`, `GoToSlide(n)`, `GoToPage(i)`. Границы: на
последней странице `Next` ничего не меняет, на первой — `Previous`. `GoToSlide(n)` ведёт на
первую страницу логического слайда `n`, а без логических номеров — на страницу `n`; `n` больше
числа слайдов — на последний, `0` — на первый.

**Rationale**: образец 015 и 009 — значение держит окно, поверхность ядра без состояния
одинакова в wasm и Tauri.

## §5. Перенос номера через пересборку

**Decision**: `carry(state, slides) → state`: страница сохраняется по индексу; если страниц
стало меньше — последняя (US3 сценарий 2). Привязки к тексту слайда нет.

**Rationale**: спека требует «номер не сбрасывается» (FR-007), а не «тот же текст». Правка
обычно меняет текущий слайд — поиск по тексту увёл бы показ с него.

## §6. Клавиши показа

**Decision**: таблица `show_keymap() → ShowKeymap` (по `KeyboardEvent.key`): `ArrowRight`, `ArrowDown`,
`Space`, `PageDown`, `Enter` (без набранного номера) → `Next`; `ArrowLeft`, `ArrowUp`,
`PageUp`, `Backspace` (без набранного номера) → `Previous`; `Home` → `First`; `End` → `Last`.
Цифры копятся в набор номера в окне (A3), `Enter` при наборе → `GoToSlide`, `Escape` при
наборе — отмена набора, без набора — выход. Набор сбрасывается через 3 с.

**Rationale**: кликеры шлют `PageUp`/`PageDown` (а некоторые — `ArrowLeft`/`ArrowRight` или
`B`/`.`); ставить их в одно место с остальными сочетаниями (`keybindings.rs`) — принцип I.
Показ — отдельное окно без редактора, поэтому клавиши не конфликтуют с CodeMirror.

## §7. Кто владеет показом

**Decision**: окно редактора (`useShowSession`). Оно держит `ShowState`, последний удачный
`CompiledDocument` показываемой заметки (из `useCompiledDocument` 005 — `shown`, `isStale`,
`diagnostics`), вызывает ядро и рассылает окнам сообщение `state`. Окна показа и докладчика
(`useShowWindow`) только рисуют и шлют `action`. Сессия привязана к заметке, с которой начат
показ: переключение редактора на другую заметку не меняет показ, но пересборок больше нет —
показ остаётся на последней сборке без пометки об ошибке.

**Rationale**: синхронность FR-005 получается даром — у обоих окон один источник; в окнах не
нужен второй экземпляр ядра со шрифтами.

## §8. Окна на рабочем столе и в web

**Decision**:

- **Web**: `window.open('/show?session=<id>&role=show', …)` — тот же origin, сообщения через
  `BroadcastChannel('typsidian-show-<id>')`. Полноэкранный режим — `requestFullscreen()` по
  первому жесту в окне показа или кнопке панели; без права — плашка A6. Окно не открылось
  (блокировщик) — тост в редакторе с кнопкой «Открыть ещё раз».
- **Рабочий стол**: `new WebviewWindow('show', { url: 'show.html?…' })`, сообщения через
  `emitTo`/`listen`. Есть второй монитор (`availableMonitors()`): окно показа ставится на
  монитор, отличный от текущего, и разворачивается `setFullscreen(true)`; вид докладчика —
  на текущем. Монитор один — окно показа на весь экран, вид докладчика — обычным окном.
  Capabilities: окна `show`, `presenter`; права `core:webview:allow-create-webview-window`,
  `core:window:allow-set-fullscreen`, `core:window:allow-set-position`,
  `core:window:allow-close`, `core:window:allow-set-focus`, `core:window:allow-available-monitors`,
  `core:event:allow-emit-to`.
- **Закрытие окна показа** крестиком ОС — то же, что выход (spec Edge Cases): окно шлёт
  `closed` из `beforeunload`/`onCloseRequested`, редактор переходит к месту слайда.

**Rationale**: clarify 2026-10-15 — отдельное окно, которое можно вынести на проектор.
`emitTo` — документированный путь Tauri между окнами; `BroadcastChannel` между вебвью Tauri
не гарантирован.

**Ограничение web, проверено сценарием**: браузер даёт открыть одно окно на одно нажатие.
«Сразу с видом докладчика» в web открывает окно показа, а вид докладчика — тостом «Открыть
ещё раз» в редакторе или кнопкой «Докладчик» в окне показа (там окно открывается прямо в
обработчике нажатия). На рабочем столе ограничения нет: оба окна создаёт Tauri.

**Alternatives considered**: Window Management API (`getScreenDetails`) в web — только
Chromium и спрашивает разрешение; оставлено на будущее.

## §9. Android

**Decision**: показ — `ShowOverlay` поверх рабочей области в том же окне, `ShowChannel`
реализуется в памяти (без окон). Касание левой зоны (30 %) — назад, правой — вперёд, свайп —
так же; касание середины на 3 с показывает «Выйти» и счётчик (A8). Полноэкранный режим —
`requestFullscreen()` и `screen.orientation.lock('landscape')` по возможности; отказ не
мешает показу. Системная «Назад» — выход: при старте показ кладёт запись в историю (`history.pushState`),
`popstate` завершает показ, поэтому «Назад» не закрывает приложение. Вида докладчика нет (clarify 2026-10-15), кнопка
не показывается (FR-009).

**Rationale**: второй экран Android — нативный `Presentation` API, вне скоупа (spec Assumptions).

**Порог пересмотра**: если WebView Tauri не даёт `requestFullscreen` и системные панели
остаются видны — отдельная задача на плагин immersive-режима в `apps/mobile`.

## §10. Пересылка страниц

**Decision**: сообщение `deck` несёт список отпечатков страниц и SVG только тех страниц,
которых окно ещё не получало (окно отвечает `have` со списком отпечатков после
подключения). Окно хранит SVG по отпечатку и выбрасывает те, которых нет в последнем списке.

**Rationale**: SVG 100 слайдов с глифами-контурами — десятки мегабайт; гнать их по событиям
Tauri на каждую правку нарушило бы SC-004. `digest` 005 для этого и заведён.

## §11. Бюджеты

| Шаг | Бюджет |
|---|---|
| Сбор `slides` в сборке, 100 страниц | ≤5 % времени сборки |
| `page_at_caret`, `navigate`, `carry` | ≤1 мс |
| Первый `deck` в новое окно, 100 страниц | ≤1,2 с (SC-001 — 2 с вместе с открытием окна) |
| Действие → новый слайд на экране | ≤100 мс (SC-002): ядро ≤1 мс, канал ≤20 мс, вставка SVG |

**Decision (замер T030, `packages/core/benches/slides_scale.rs`)**: порог «сбор ≤5 % сборки»
**не выполнен**, и с большим запасом. Документ — 100 страниц 16:9, заголовок, четыре пункта,
`<pdfpc>`-заметка и `LogicalSlide` на каждой; native, release, 15 прогонов после прогрева
(3 прогона), медиана:

| Величина | Медиана | Мин — макс |
|---|---|---|
| Полная сборка `compile_note` со сбором | 21,13 с | 20,66 — 21,57 с |
| Сбор `collect` отдельно (на собранном документе) | 20,66 с | 20,54 — 21,06 с |
| Доля сбора | 97,8 % | — |

«Сборка без сбора» отдельно не снималась (флага в `compile_with` нет, поведение не
менялось): сам сбор меряется функцией `time_slides_collect` под `test-support`, доля —
отношение; сборка Typst без сбора — остаток ≈0,5 с.

**Причина**: `first_byte` на каждый глиф вызывает `world.range(span)`, а он идёт через
`World::source`, и `PreviewWorld::source` каждый раз копирует текст и заново разбирает
`Source::new` — то есть целый документ заново на каждый глиф (порядка 10⁴ разборов
на 100 страниц). Это ошибка реализации сбора, а не цена самой идеи.

**Вывод и предложение** (код не менялся): вариант из Complexity Tracking «собирать только
при открытом показе» не нужен как первая мера; сначала исправить `collect`: взять `Source`
главного файла один раз (`world.source(main)` уже есть у вызывающего) и переводить спан
в диапазон через `source.range(span)`, не через `world.range`; после этого повторить бенч —
ожидается доля порядка единиц процентов или меньше. Если после исправления доля всё ещё
>5 %, тогда переходить на сбор только при открытом показе. До исправления SC-001/SC-004
фичи на 100 страницах не выполнимы (в wasm медленнее ещё). Нужна отдельная задача на
исправление и повторный замер.

**Decision (исправление, 2026-10-16)**: `collect` переделан, порог **выполнен**. Предложенный
выше шаг — `Source` один раз и `Source::range` — дал 0,33 с сборки и 71 % на сбор: сам
`Source::range` ищет узел от корня, и на каждый глиф это долгий проход. Окончательно —
одним обходом дерева разбора главного файла строится таблица «спан узла → начало в
байтах» (`node_starts`), и каждый глиф находится за O(1). Тот же бенч, те же условия:

| Величина | Медиана | Мин — макс |
|---|---|---|
| Полная сборка `compile_note` со сбором | 99,5 мс | 97,4 — 101,9 мс |
| Сбор `collect` отдельно | 3,3 мс | 3,1 — 3,5 мс |
| Доля сбора | 3,3 % (бюджет 5 %) | — |

Поведение сбора не изменилось: `slides_native` и `slides_wasm` (24 теста) зелёные.
Вариант «собирать только при открытом показе» не нужен. Сборка в wasm на 100 страницах
отдельно не мерилась.

## §12. Сочетание

**Decision**: `CommandId::StartShow` — `Mod+Alt+P`: среди умолчаний с Alt заняты
`s c h u g m w . , \ [ ]`, `p` свободно; кириллическая раскладка — через `Shortcut::code`
(`KeyP`). Команда — «с текущего слайда»; «с начала» и «с видом докладчика» — пункты меню
кнопки и палитры.

## §13. Расхождения макета и спеки

Макет вводит пункт «Сразу с видом докладчика» (A1), ленту слайдов в виде докладчика (A7) и
автоскрытие панели показа через 2 с (A2). Все три — внутри FR-001, FR-003, FR-005;
спека не меняется.
