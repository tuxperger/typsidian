# Research: Application Settings

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-08-09

Решения Phase 0. Каждый параграф: что выбрано, почему, что отвергнуто.

---

## §1. Где живёт хранилище настроек на каждом таргете

**Decision**: Native — файл `settings.json` в каталоге конфигурации приложения по правилам
платформы, полученном через крейт `directories` (Linux `$XDG_CONFIG_HOME/typsidian`, macOS
`~/Library/Application Support/typsidian`, Windows `%APPDATA%\typsidian`). Web — файл
`settings.json` в OPFS (Origin Private File System) через `navigator.storage.getDirectory()`.

*Расширение — следствие §2 (пересмотрено 2026-09-09); само место хранения не менялось.*

**Rationale**: FR-011 требует хранилище вне любого vault, FR-036 показывает его расположение
пользователю. Раз путь стал видимым элементом интерфейса, он обязан быть тем, который
пользователь ожидает увидеть на своей ОС. Существующий модуль `vault::last_vault` собирает путь
руками из `HOME/.config` — на macOS и Windows это неверное место (см. §10).

**Alternatives rejected**:
- Ручная сборка `HOME/.config/...` (как сейчас в `last_vault`) — неверна на двух из трёх
  десктопных платформ, а путь теперь показывается пользователю.
- `localStorage` в вебе — не файл, не поддаётся тем же операциям чтения/записи, что native, и
  сломал бы единый публичный API хранилища (принцип II).
- IndexedDB **как хранилище значений настроек** — непрозрачно, противоречит духу FR-036
  («покажи, где лежит») и лишает пользователя возможности править файл руками (FR-013).

**Оговорка (следствие §10)**: этот отказ касается только *значений настроек*. Ссылки на папки
vault в вебе (`FileSystemDirectoryHandle`) физически невозможно сериализовать ни в TOML, ни в
JSON, поэтому для них заводится отдельный реестр в IndexedDB, ключом которого служит `VaultId`.
Значения настроек по-прежнему целиком в `settings.json` на обоих таргетах; реестр хранит только
непрозрачные ссылки на папки, не показываемые пользователю и не являющиеся настройками.

## §2. Формат файла настроек

> **Пересмотрено 2026-09-09: формат — JSON (`settings.json`).** Решение развёрнуто по прямому
> указанию владельца проекта. Аргумент ниже не снят и не опровергнут — он оплачен: комментариев
> в файле больше нет, потому что JSON их не поддерживает, а порядок ключей теперь задаёт
> приложение (алфавитный, свойство `BTreeMap` под `serde_json::Map`), а не пользователь.
>
> Что уцелело из требования: неизвестные ключи по-прежнему не являются ошибкой разбора и
> **переживают запись приложения** — дописанное руками не выбрасывается (FR-013). Сломанный
> синтаксис по-прежнему называется ошибкой, а не подменяется молча умолчаниями.
>
> **Переноса с прежнего формата нет — по прямому решению владельца проекта (2026-09-09).**
> `settings.toml`, написанный прежней версией, новой не читается: приложение поднимается на
> значениях по умолчанию и создаёт `settings.json` рядом. Прежний файл при этом **не трогается**
> — ни удаления, ни переименования, — так что пользователь может перенести значения руками.
> Названо здесь прямо, потому что это наблюдаемая потеря настроек при обновлении, а не
> внутренняя деталь. Ценой закрыты обе зависимости, `toml` и `toml_edit`: после отказа от
> переноса ими в проекте не пользуется никто.
>
> **`preserve_order` у `serde_json` включать нельзя**: `serde_json` в проекте общий, а
> `boards::digest` рассчитывает на сортировку ключей `Map` — именно она даёт канонический
> порядок при нормализации доски (фича 002, research.md §5). Feature изменила бы хэш каждой
> доски и уронила бы эталонный `REFERENCE_DIGEST`.

**Decision (исходное)**: TOML. Запись — через `toml_edit`, сохраняющий комментарии, порядок
ключей и форматирование; чтение — через `toml` + `serde`.

**Rationale**: FR-036 прямо приглашает пользователя открыть этот файл, а FR-013 делает его
правку руками равноправной правке через панель. Значит, файл — пользовательский артефакт, а не
внутренний дамп. Приложение перезаписывает его при каждом изменении настройки; обычная
serde-сериализация уничтожила бы комментарии и порядок, то есть молча стирала бы то, что
пользователь написал сам. `toml_edit` правит только затронутые значения.

**Alternatives rejected**:
- JSON — комментариев нет вовсе, а именно они делают файл пригодным для ручной правки.
- Обычный крейт `toml` на запись — round-trip теряет комментарии и порядок ключей.
- YAML — неоднозначный синтаксис, отдельный класс ошибок при ручной правке.

## §3. Обнаружение внешних изменений хранилища (FR-013, SC-014)

**Decision**: Native — `notify` + `notify-debouncer-full` (уже в зависимостях ради vault),
наблюдение за каталогом настроек. Web — периодическая сверка файла в OPFS по тому же приёму,
что `WebBackend` применяет к vault; интервал ≤1 с, чтобы уложиться в SC-014 (≤2 с). Сверка
дешёвая: сначала размер и время изменения, содержимое читается только при расхождении.

**Rationale**: обе механики уже доказаны в фиче 001 на том же классе задач; второй способ
решать ту же задачу не нужен. Порог SC-014 совпадает с SC-004 фичи 001, поэтому и бюджет
одинаковый.

**Честное ограничение веба**: OPFS недоступен ни файловому менеджеру, ни стороннему редактору,
поэтому «внешнее изменение» в вебе на практике означает только запись из другой вкладки того же
происхождения. FR-013 при этом выполняется буквально: механизм обнаружения есть и работает,
просто источников изменения в вебе меньше. Это не подгонка под платформу, а разное множество
источников при одном контракте.

## §4. Согласованность между окнами и вкладками (FR-006)

**Decision**: отдельного канала обмена между окнами нет. Согласованность обеспечивается тем же
механизмом, что и §3: окно записывает файл, остальные видят изменение наблюдателем (native) или
сверкой (web) и применяют его.

**Rationale**: это ровно то решение, которое фича 001 приняла для vault (её FR-034: другое окно
приложения — такой же внешний источник, как сторонняя программа). Отдельный канал вроде
`BroadcastChannel` или событий Tauri создал бы второй источник истины, способный разойтись с
файлом; при расхождении пришлось бы решать, кто прав, — задача, которой сейчас нет.

**Alternatives rejected**: `BroadcastChannel` (web) / IPC-события (Tauri) как первичный канал —
второй источник истины ради экономии максимум одной секунды задержки.

## §5. Атомарная запись и защита от полузаписи

**Decision**: Native — запись во временный файл в том же каталоге, `fsync`, затем `rename`
поверх целевого. Web — `FileSystemWritableFileStream`, который по спецификации фиксирует
изменения только при `close()`.

**Rationale**: файл настроек перезаписывается целиком при каждом изменении. Обрыв на середине
записи оставил бы обрезанный JSON — то есть повреждённое хранилище (§6) на ровном месте. Оба
механизма дают одну и ту же наблюдаемую гарантию «либо старое содержимое, либо новое», разными
средствами за одной абстракцией — как того требует принцип II.

**Побочная выгода**: атомарность записи бесплатно закрывает требование FR-037 «сброс
применяется целиком либо не применяется вовсе» — весь набор значений уходит на диск одним
`rename`, промежуточного состояния на диске не существует (см. §9).

## §6. Повреждённое или нечитаемое хранилище (FR-013)

**Decision**: при неуспешном разборе файла приложение поднимается на значениях по умолчанию и
сообщает об этом. Испорченный файл не перезаписывается: при первой же записи он переименовывается
рядом в `settings.json.invalid-<UTC-метка>`, о чём пользователь уведомляется, и только после
этого создаётся новый.

**Rationale**: FR-013 запрещает молчаливое затирание. Переименование рядом сохраняет
пользователю возможность вытащить из испорченного файла то, что он там писал, и при этом не
блокирует работу приложения.

**Alternatives rejected**:
- Отказывать в записи, пока пользователь не починит файл руками — приложение фактически
  теряет настраиваемость из-за одной опечатки.
- Перезаписать поверх — прямое нарушение FR-013.

## §7. Шов к мосту редактирования (FR-025, FR-034, FR-035)

**Decision**: в ядре объявляется трейт `EditorModeBridge` с тремя наблюдаемыми состояниями
(`FullBackend`, `SimplifiedEmulation`, `PlainInput`) и реализация `NullBridge`, которая всегда
сообщает о недоступности полноценного режима. Контракт — `contracts/editor-mode-bridge.md`.
Настройки потребляют только этот трейт и ничего не знают о msgpack-rpc.

**Rationale — главное обстоятельство этой фичи**: моста к Neovim в кодовой базе **не
существует**. В `packages/core` есть только `vault` и `graph`; ни одного упоминания nvim в коде
нет (в `flake.nix` neovim присутствует лишь как инструмент dev-окружения). Раздел «Кейбиндинги»
описывает наблюдение и переключение подсистемы, которая ещё не построена. Трейт-шов позволяет
реализовать и полностью протестировать всю фичу 004 до появления моста, а появление моста не
меняет публичный API настроек — только добавляет вторую реализацию трейта рядом с `NullBridge`.

Такое разделение согласуется с принципом V: сам мост — отдельная зона повышенного риска со
своим `/speckit-clarify`; настройки лишь отражают его состояние.

`PlainInput` — третье состояние, введённое кларификацией 2026-08-09: наступает само при отказе
полноценного режима, выход из него только по явному действию пользователя. Веб-клиент не может
порождать внешние процессы, поэтому там `NullBridge` остаётся постоянной реализацией, и
полноценный режим честно показан недоступным.

**Alternatives rejected**:
- Ждать моста и планировать 004 после него — блокирует три из четырёх разделов настроек, ни
  один из которых от моста не зависит.
- Спрятать состояние моста за `Option<bool>` без явного трейта — не выражает третьего
  состояния и заставит менять API настроек, когда мост появится.

## §8. Отслеживание изменений конфига полноценного режима (FR-026)

**Decision**: переиспользовать существующий `FileStamp` (mtime + size + BLAKE3-хэш содержимого)
из `vault::index`. Для этого `FileStamp` поднимается в общий модуль `core::stamp` и
ре-экспортируется из `vault::index`, чтобы не ломать существующий код. Применённый конфиг
хранит свой `FileStamp`; расхождение с текущим файлом даёт признак «изменён, не применён».

**Rationale**: FR-026 нужна ровно та же семантика «файл действительно изменился», что и в
обнаружении конфликтов vault. Вторая реализация была бы вторым источником истины (принцип I).

**Побочная выгода**: хэш содержимого прямо отвечает на краевой случай из spec.md — «конфиг
изменён на диске, а затем возвращён к прежнему содержимому до применения». Метка времени
показала бы ложное расхождение, хэш совпадёт, и индикатор корректно погаснет сам.

## §9. Транзакционное применение изменений и сброс (FR-029…FR-031, FR-037)

**Decision**: ядро предоставляет чистую функцию планирования
`settings::apply::plan(changes, context) -> ApplyPlan`, где `ApplyPlan` — одно из:
`Applied`, `RequiresNoteSave { path }`, `Rejected { reason }`. Решение о том, нужно ли
принудительное сохранение и допустимо ли переключение, принимается в ядре; сохранение заметки
выполняет вызывающая сторона существующим примитивом `VaultBackend::write`, после чего
повторяет вызов. Сброс к умолчаниям строит полный набор изменений и проходит тот же путь.

**Rationale**: правила FR-029…FR-031 — это бизнес-логика, и ей место в ядре (принцип I). Но
сохранение заметки требует `VaultBackend`, а связывать хранилище настроек с vault-бэкендом
означало бы сцепить две независимые подсистемы. Разделение «ядро решает, вызывающая сторона
исполняет возвращённую инструкцию» повторяет приём, уже принятый в фиче 001 для подтверждения
удаления через `backlinks()` — там пост-дизайн-проверка отдельно зафиксировала, что вызов
примитива ядра по его же указанию не является бизнес-логикой в UI.

Атомарность сброса (FR-037) обеспечивается §5: весь набор значений уходит одним атомарным
`rename`, поэтому «частично сброшенного» состояния на диске не бывает по построению.

**Alternatives rejected**:
- Передавать `&mut VaultBackend` внутрь применения настроек — жёсткая сцепка двух подсистем и
  `dyn`-объект там, где кодовая база сознательно обходится без `dyn`.
- Оставить решение о сохранении на UI — перенос бизнес-логики в UI, прямое нарушение
  принципа I.

## §10. Идентичность записи о vault и судьба модуля `last_vault`

**Decision**: идентичность записи **непрозрачна**. Каждой записи при добавлении выдаётся
стабильный `VaultId`, не зависящий от платформы; он и хранится в `settings.json` вместе с
показываемым расположением и необязательной подписью пользователя (§14). Тождество папок
устанавливается платформой за общей абстракцией:

| | Native | Web |
|---|---|---|
| Ссылка на папку | `PathBuf` | `FileSystemDirectoryHandle` |
| Тождество | сравнение канонизированных путей (`std::fs::canonicalize`) | `handle.isSameEntry(other)` |
| Где живёт ссылка | `settings.json` | реестр в IndexedDB, ключ — `VaultId` (§1) |

**Rationale — вторая по значимости находка этой фичи**. Первоначальное решение «опознавать по
абсолютному пути» **неприменимо на веб-клиенте**: `showDirectoryPicker()` не отдаёт пути, и
`WebBackend` сегодня кладёт в `root_path` просто `PathBuf::from(handle.name)`
(`packages/core/src/vault/web.rs:341`), то есть имя папки. Идентичность по пути выродилась бы
там в идентичность по имени, и две разные папки `notes` схлопнулись бы в одну запись — то есть
пользователь потерял бы доступ к одному из своих vault. Это не отсутствие возможности, а
неверное поведение. `isSameEntry()` решает ровно эту задачу без путей.

**Ассоциированный тип вместо общего**: ссылка на папку объявляется ассоциированным типом
трейта (`type FolderRef`), а не общим конкретным типом. Форма API при этом одна на обоих
таргетах — вызывающий код получает ссылку от системного выбора папки и передаёт её обратно, не
разбирая её содержимого и не ветвясь по платформе. Сам выбор папки уже сегодня различается по
таргетам и выполняется в UI как жест пользователя (`ui/src/vault-tree/useVault.ts`), так что
новой платформенной развилки не добавляется.

**Стоимость**: `isSameEntry()` асинхронен, а сравнение идёт перебором по списку — при
добавлении папки выполняется до N асинхронных сравнений. При рабочей границе списка в 50
записей это несущественно; порогов производительности на список спецификация не задаёт.

**Перенос папки снаружи**: гарантируется только то, что уместно на обеих платформах —
приложение **никогда не разыскивает** новое расположение само. Сохранится ли связь, не
обещается: на native канонизированный путь перестаёт разрешаться и запись становится
недоступной, а в вебе сохранённый хендл, как правило, переживает перенос, но это поведение
браузера и файловой системы, которым мы не управляем. Спецификация (FR-023) сформулирована
именно как «не гарантируется», чтобы приёмочный тест не падал из-за платформы вместо дефекта.
Если связь утрачена — запись помечается недоступной и добавляется заново.

**Судьба `last_vault`**: модуль `vault::last_vault` **упраздняется**, его роль поглощается
списком известных vault. Содержимое `last_vault.txt` импортируется при первом запуске как
единственная запись, файл удаляется, модуль изымается из `packages/core/src/vault/mod.rs`
**и снимается его вызов `crate::vault::last_vault::remember(root_path)` в
`packages/core/src/vault/native.rs:577`** — без этого сборка не пройдёт. Дополнительный довод
к упразднению: `last_vault` объявлен под `cfg(not(target_arch = "wasm32"))` и веб-реализации не
имеет, то есть уже сегодня нарушает принцип II.

**Alternatives rejected**:
- Путь как единственный признак идентичности — неприменим в вебе, см. выше; именно эта
  формулировка была снята кларификацией 2026-08-09.
- Метка-файл внутри vault для опознания при переносе — прямо запрещено FR-020 и противоречит
  принципу VI: vault остаётся обычной папкой без артефактов приложения.
- Отказ от списка нескольких vault в вебе — раздел Vault потерял бы там половину смысла, а
  принцип II требует одинакового поведения, а не урезания одного из таргетов.
- Оставить `last_vault` рядом со списком — второй источник истины.

## §11. Диапазон размера шрифта редактора (FR-016)

**Decision**: целые значения от 8 до 32 включительно, по умолчанию 14.

**Rationale**: FR-016 требует объявленного диапазона, иначе требование непроверяемо — это был
единственный пункт, оставшийся Outstanding после `/speckit-clarify`. Нижняя граница — предел
читаемости на обычной плотности пикселей, верхняя покрывает потребности слабовидящих, не ломая
раскладку панелей. Закрытый целочисленный диапазон делает FR-016 однозначно тестируемым:
7 и 33 отклоняются с объяснением, 8 и 32 принимаются.

## §12. Журналы: объём и запрет содержимого заметок (FR-041, FR-043)

**Decision**: ротация двух файлов по 1 МиБ (суммарно ≤2 МиБ). В журнал записываются только
события с перечислимым типом и пути относительно корня vault; содержимое заметок и досок и
абсолютные пути не записываются никогда. Запрет проверяется тестом: на подготовленном vault с
заметками-маркерами прогоняется сценарий, после чего журнал сканируется на присутствие
маркерного текста.

**Rationale**: FR-041 — прямое следствие принципа IX конституции. Запрет, проверяемый только
ревью, со временем протекает; тест-сканер переводит его в исполняемую гарантию. Относительные
пути вместо абсолютных — чтобы журнал, отправленный пользователем в поддержку вручную (FR-042
разрешает только явную передачу), не раскрывал имя пользователя и структуру его диска.

## §13. Раскрытие хранилища средствами ОС (FR-036)

**Decision**: трейт хранилища сообщает и расположение, и признак возможности раскрытия
(`can_reveal`). Native — раскрытие в файловом менеджере системы; web — `can_reveal = false`,
расположение показывается как справочный текст без действия.

**Rationale**: принцип II требует одинакового публичного API на всех таргетах, а не одинаковых
возможностей платформы. Признак возможности — это значение в API, поэтому API остаётся одним;
отсутствующий на вебе метод, наоборот, развалил бы контракт. UI ветвится по значению признака,
а не по таргету.

**Alternatives rejected**: метод `reveal()`, существующий только под native — ветвление по
платформе просачивается в вызывающий код (запрещено архитектурными ограничениями конституции).

## §14. Подпись записи о vault (FR-018)

**Decision**: у записи есть необязательная подпись, задаваемая пользователем при добавлении
или позже. Если она задана — показывается вместо расположения; само расположение остаётся
доступным пользователю. Подпись **не участвует** в установлении тождества папок (§10) и не
обязана быть уникальной.

**Rationale**: прямое следствие §10. Раз в вебе показывается только имя папки, две разные
папки `notes` дадут две корректно различные записи, которые выглядят одинаково — список из
неразличимых строк превращает переключение vault в угадывание. Подпись — единственный из
рассмотренных вариантов, дающий осмысленное различие.

**Alternatives rejected**:
- Ничего не добавлять — две неразличимые строки в списке, пользователь выбирает наугад.
- Автоматический различающий признак (дата добавления, порядковый номер) — делает строки
  формально разными, но не помогает понять, какая из них какая.

Требование неуникальности подписи намеренное: если пользователь подписал две записи одинаково,
это его выбор, а тождество папок от подписи всё равно не зависит.

## §15. Доступность `FakeBridge` интеграционным тестам

**Decision**: `FakeBridge` объявляется под `#[cfg(any(test, feature = "test-support"))]`, а
фича `test-support` включается в dev-dependencies `packages/core/Cargo.toml`.

**Rationale**: тесты фичи живут в `packages/core/tests/` — это **интеграционные** тесты,
которые линкуются с крейтом как с внешней зависимостью, собранной **без** `cfg(test)`. Тип под
голым `#[cfg(test)]` был бы им не виден, и весь набор тестов режима редактирования не
скомпилировался бы. Существующие тесты фичи 001 лежат там же, поэтому приём распространяется на
всю кодовую базу единообразно.

**Alternatives rejected**:
- Голый `#[cfg(test)]` — не компилируется, см. выше.
- Безусловно публичный `FakeBridge` — тестовая заглушка попала бы в поставляемый API.
- Дублирование заглушки в каждом тестовом файле — вторая и третья реализация одного контракта.

## Открытый пункт, вынесенный за границы фичи

**Отмена переключения vault на середине.** Принцип X требует, чтобы массовые операции были
отменяемыми. Переключение на большой vault запускает обход до 10 000 заметок (бюджеты SC-002
фичи 001). Сам обход уже неблокирующий и прогрессивный — это машинерия 001, и новой массовой
операции фича 004 не добавляет, поэтому гейт принципа X пройден. Но отмены переключения,
начатого по ошибке, спецификация не требует и здесь её нет: пользователь дожидается окончания
обхода. Зафиксировано как осознанное ограничение, кандидат в отдельную фичу.

## Результат проверки FR-017 (T107, 2026-09-10)

Требование: «изменение темы и размера шрифта MUST отражаться в уже открытых
редакторе и preview немедленно, без их переоткрытия». Когда список задач
писался, проверить его было негде — обстоятельство 3 в шапке `tasks.md`:
каталог `ui/src/editor/` был пуст. Теперь оба потребителя существуют, и итог
такой.

**Размер шрифта — выполняется.** `applyAppearanceToDocument` ставит
`--typsidian-editor-font-size` на `<html>`, правило `.ts-editor .cm-editor`
в `ui/src/styles/app.css` его читает. Связь идёт каскадом, поэтому редактор для
смены размера не перерисовывается вовсе — «без переоткрытия» выполняется по
построению, а не потому, что кто-то не забыл перечитать настройку. До первой
загрузки настроек действует запасное значение `--text-sm`.

**Тема — выполняется для интерфейса и намеренно не действует на полотно
редактора.** Атрибут `data-theme` на `<html>` переключает токены всего
интерфейса, включая панель предпросмотра. Само полотно CodeMirror остаётся
тёмным при любой теме (`--steel-950`): так его задаёт макет, и это осознанное
расхождение, а не необработанный случай. Если светлое полотно понадобится, это
отдельное решение по макету, а не дефект FR-017.

**Чего требование не означает.** Размер шрифта редактора не применяется к
предпросмотру: там кегль задаёт сам документ, свёрстанный Typst, и подмена его
настройкой интерфейса означала бы, что предпросмотр показывает не то, что
получится при печати.

**Что остаётся непроверенным автоматикой** — что человек видит изменение
немедленно и укладывается в бюджет SC-002 (≤200 мс). Это ручной прогон, T098.
