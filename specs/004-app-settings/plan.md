# Implementation Plan: Application Settings

**Branch**: `004-app-settings` | **Date**: 2026-08-09 (ревизия 2 после `/speckit-analyze`) | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/004-app-settings/spec.md`

## Summary

Панель настроек с четырьмя разделами (Vault, Внешний вид, Кейбиндинги, Дополнительно), в
которой любое изменение вступает в силу немедленно, без перезапуска и без кнопки «сохранить».
Значения хранятся одним JSON-файлом на устройстве вне какого-либо vault (research.md §2, пересмотрено 2026-09-09); файл наблюдается, и
правка руками равноправна правке через панель — то же правило «диск источник истины», что
фича 001 приняла для vault. Вся логика — новый модуль `packages/core/src/settings/` за трейтом
`SettingsStore` с двумя реализациями (файл в каталоге конфигурации ОС на native, OPFS в вебе),
по образцу уже работающего `VaultBackend`.

Три обстоятельства определили форму плана.

**Первое: моста к Neovim в кодовой базе не существует** — раздел «Кейбиндинги» наблюдает
подсистему, которая ещё не построена, поэтому она вводится как трейт-шов `EditorModeBridge` с
заглушкой `NullBridge`, что позволяет реализовать и протестировать всю фичу до появления моста
(research.md §7).

**Второе: идентичность записи о vault не может опираться на путь.** В браузере абсолютного пути
не существует — `showDirectoryPicker()` отдаёт только имя папки, и `WebBackend` сегодня кладёт в
`root_path` именно `PathBuf::from(handle.name)` (`vault/web.rs:341`). Идентичность по пути
схлопнула бы там две разные папки `notes` в одну запись, лишив пользователя доступа к одному из
его vault. Поэтому идентичность непрозрачна: `VaultId` наружу, сравнение канонизированных путей
на native и `isSameEntry()` в вебе за ассоциированным типом `FolderRef` (research.md §10). Этот
дефект был внесён первой ревизией плана и вскрыт `/speckit-analyze`.

**Третье: существующий модуль `vault::last_vault`** уже хранит «последний открытый vault» в
собственном файле и только под native — он поглощается списком известных vault и упраздняется
вместе с его вызовом в `vault/native.rs:577`, иначе в приложении будет два расходящихся
источника истины, а сборка не пройдёт (research.md §10).

## Technical Context

**Language/Version**: Rust (stable, зафиксирован через `flake.nix`/fenix) — вся логика фичи.
TypeScript `strict` — только UI-слой панели, потребляющий контракт из
`contracts/frontend-settings.md`.

**Primary Dependencies**:
- `directories` — каталог конфигурации по правилам платформы, только native (research.md §1).
- `serde_json` — чтение и запись файла настроек (research.md §2, пересмотрено 2026-09-09);
  оба таргета; **уже в зависимостях** ради нормализации досок. Отдельного крейта под формат
  настроек не требуется: переноса с прежнего TOML нет, и `toml`/`toml_edit` из зависимостей
  убраны.
- `notify` + `notify-debouncer-full` — наблюдение за файлом настроек на native; **уже в
  зависимостях** ради vault, новых крейтов не требуется.
- OPFS через `web-sys` (`StorageManager`, `FileSystemWritableFileStream`) — хранилище и
  атомарная запись в вебе; требует добавления features к существующей зависимости `web-sys`.
- IndexedDB через `web-sys` — **только** реестр ссылок на папки vault
  (`FileSystemDirectoryHandle`), которые невозможно сериализовать в JSON. Значения настроек в
  IndexedDB не хранятся (research.md §1, §10).
- `blake3` — хэш содержимого для `FileStamp`; **уже в зависимостях**.
- `serde` + `tsify-next` — граница ядро↔UI, типы порождаются из Rust (принцип IV); **уже в
  зависимостях**.

**Storage**: единственный файл `settings.json` в каталоге конфигурации приложения (native) или
в OPFS (web) — вне любого vault (FR-011). Пользовательские заметки этой фичей не затрагиваются;
внутри vault не создаётся никаких служебных файлов (FR-020, принцип VI). Журналы — ротация двух
файлов по 1 МиБ рядом с настройками (research.md §12).

**Testing**: `cargo test` (native) и `wasm-bindgen-test` (`wasm32-unknown-unknown`) — обе
обязательны для каждой единицы логики (принцип I, принцип II NON-NEGOTIABLE). Состояния моста
редактирования проверяются через `FakeBridge`, покрывающий все три состояния и отказные
переходы, — реального моста для тестов не требуется (research.md §7). `FakeBridge` объявляется
под `#[cfg(any(test, feature = "test-support"))]` с включением фичи в dev-dependencies: тесты
живут в `packages/core/tests/` и являются интеграционными, поэтому голый `#[cfg(test)]` был бы
им не виден (research.md §15).

**Target Platform**: `wasm32-unknown-unknown` (веб-клиент) и нативная сборка (desktop/mobile).
На вебе полноценный режим редактирования постоянно недоступен (нельзя порождать внешние
процессы) и раскрытие хранилища средствами ОС невозможно — оба случая выражены значениями в
API, а не отсутствием методов (research.md §13).

**Project Type**: Rust-workspace ядро (`packages/core`), потребляемое общим UI-кодом (`ui/`).

**Performance Goals** (из spec.md Success Criteria):
- Тема и размер шрифта видны в открытом редакторе ≤200 мс (SC-002).
- Отзывчивость ввода ≤100 мс, в том числе при открытии панели и применении настроек (SC-009).
- Внешнее изменение файла настроек отражается ≤2 с (SC-014).
- Переключение на доступный vault укладывается в бюджет повторного открытия из фичи 001
  (SC-007).

**Constraints**:
- Полностью офлайн (FR-008, SC-013); диагностика и журналы не покидают устройство (FR-042,
  принцип IX).
- Паритет native/`wasm32-unknown-unknown` обязателен (принцип II, NON-NEGOTIABLE); различия
  платформ — только внутри реализаций трейтов.
- UI не дублирует логику (принцип I): решение о принудительном сохранении и о допустимости
  переключения принимает ядро, UI исполняет возвращённую инструкцию (research.md §9).
- Хранилище настроек — вне vault; внутри vault не появляется служебных файлов (FR-011, FR-020).
- Файл настроек — пользовательский артефакт: дописанные пользователем ключи при записи
  сохраняются (research.md §2, пересмотрено — комментариев в JSON нет, порядок ключей задаёт
  приложение).
- Содержимое заметок и досок не попадает в журналы; запрет проверяется тестом (FR-041,
  research.md §12).

**Scale/Scope**: значения настроек единичны по объёму. Список известных vault — рабочая
граница 50 записей (спецификация верхнего предела не задаёт; порогов производительности на
список нет). Журналы ограничены 2 МиБ суммарно.

**Structure Decision**: `settings/` — самостоятельный подмодуль `core`, симметричный
существующему `vault/`: тот же приём «один трейт, две реализации за `cfg`», те же соглашения по
ошибкам (`thiserror` + `serde` + `tsify`) и та же схема тестов на двух таргетах. Сцепки с
`vault/` нет: единственное общее — `FileStamp`, который ради этого поднимается в
`core::stamp` и ре-экспортируется из `vault::index`, чтобы существующий код не ломался
(research.md §8). Настройки не вызывают `VaultBackend`: там, где требуется сохранить заметку,
ядро возвращает инструкцию, а исполняет её вызывающая сторона (research.md §9).

## Замечания к декомпозиции

Пункты, которые `/speckit-analyze` нашёл пропущенными в первой ревизии задач. Записаны здесь,
чтобы перегенерация `tasks.md` их не потеряла повторно:

1. **FR-028** — выбор и смена пути к конфигу как действие пользователя в UI; в первой ревизии
   задачи не было вовсе.
2. **FR-033** — обработка несуществующего или нечитаемого пути конфига: сообщить причину и не
   показывать конфиг применённым.
3. **FR-020, US2 AS9** — тест «две разные папки с одинаковым именем дают две записи». Это
   единственная проверка, ловящая регрессию идентичности в вебе; без неё дефект вернётся молча.
4. **FR-018** — задание и снятие подписи записи, показ подписи вместо расположения.
5. **FR-011** — тест «потеря настроек не влияет на содержимое vault»; требование есть,
   проверки не было.
6. **SC-003, SC-004** — измеримые критерии без проверочной задачи в Phase 7.
7. **`FakeBridge`** — под `#[cfg(any(test, feature = "test-support"))]`, не под голым
   `#[cfg(test)]` (research.md §15).
8. **Упразднение `last_vault`** — включая снятие вызова в `packages/core/src/vault/native.rs:577`,
   иначе сборка не пройдёт (research.md §10).
