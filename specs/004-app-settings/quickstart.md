# Quickstart: Application Settings

**Feature**: `specs/004-app-settings/spec.md` | **Plan**: `plan.md`

Сценарии для проверки, что фича действительно работает сквозь ядро и обе реализации
хранилища — не полный набор тестов (он в `tasks.md`/реализации), а быстрый прогон golden path
и ключевых отказных путей.

## Предпосылки

- Собранное ядро под нативный таргет (`cargo build -p typsidian-core`) и под
  `wasm32-unknown-unknown` (`wasm-pack build packages/core --target web`) — принцип II
  конституции требует оба таргета для готовности фичи.
- Тестовый vault из фичи 001 (папка с ~20 заметками во вложенных подпапках) и вторая такая же
  папка — для сценариев переключения.
- Для веб-сценариев — браузер с поддержкой OPFS и File System Access API (Chromium-based).
- Реальный мост к Neovim **не требуется**: сценарии режима редактирования прогоняются на
  `FakeBridge`, покрывающем все три состояния (contracts/editor-mode-bridge.md).

## Сценарий 1 — Немедленное применение без кнопки «сохранить» (US1, FR-002…FR-005)

1. Открыть настройки, переключить тему → приложение перерисовано немедленно, ≤200 мс (SC-002).
2. Изменить размер шрифта редактора → текст в открытом редакторе меняет размер сразу (FR-017).
3. Убедиться, что кнопки «сохранить» или «применить» в панели нет (FR-003).
4. Ввести размер шрифта `7` и `33` → оба отклонены с объяснением; `8` и `32` приняты
   (FR-016, research.md §11).
5. Перезапустить приложение → выбранные значения в силе (FR-007).

## Сценарий 2 — Файл настроек как пользовательский артефакт (FR-013, FR-036, SC-014)

1. В разделе Дополнительно посмотреть расположение хранилища; на native открыть его в
   файловом менеджере, на вебе убедиться, что расположение показано справочным текстом без
   действия (FR-036, research.md §13).
2. Открыть `settings.json` сторонним редактором, **дописать свой ключ** верхнего уровня
   (например `"my_future_option": {"nested": true}`) и сохранить.
3. Ожидаемо: изменение подхватывается приложением ≤2 с (SC-014).
4. Изменить любую настройку через панель → открыть файл снова: **дописанный ключ на месте**
   (research.md §2, пересмотрено). Это ключевая проверка: обычная serde-сериализация здесь
   провалится. Комментариев в JSON нет — проверять в этом шаге нечего, и притворяться иначе
   нельзя.
5. Испортить файл (сломать синтаксис JSON) → приложение переходит на значения по умолчанию и
   сообщает об этом; **испорченный файл не перезаписан** (FR-013).
6. Изменить настройку через панель → испорченный файл переименован рядом
   (`settings.json.invalid-<метка>`), пользователь уведомлён куда (research.md §6).
7. Починить исходный файл руками → приложение возвращается к нему без перезапуска.

## Сценарий 2а — Обновление с версии, писавшей `settings.toml` (research.md §2, пересмотрено)

Переноса нет: это решение, а не пропуск, и проверять надо именно его.

1. Положить в каталог настроек `settings.toml` от прежней версии; `settings.json` при этом
   быть не должно.
2. Запустить приложение → оно поднимается на **значениях по умолчанию**: прежние настройки не
   подхватываются. Это ожидаемый исход, а не дефект.
3. Проверить каталог: появился `settings.json` с умолчаниями, а `settings.toml` лежит рядом
   **нетронутым** — приложение не вправе стирать файл пользователя, и перенести значения руками
   должно быть возможно.
4. Изменить настройку через панель → изменение уходит в `settings.json`; `settings.toml` не
   трогается ни при одной операции.

## Сценарий 3 — Согласованность между окнами (FR-006)

1. Открыть приложение в двух окнах (на вебе — в двух вкладках).
2. Переключить тему в окне 1.
3. Ожидаемо: окно 2 применяет её без перезапуска — через тот же механизм наблюдения за файлом,
   отдельного канала между окнами не существует (research.md §4).

## Сценарий 4 — Vault: список, идентичность, переключение (US2, FR-018…FR-024)

1. Раздел Vault показывает расположение текущего vault: полный путь на native, имя папки в
   вебе (FR-018).
2. Добавить вторую папку → появилась в списке.
3. **Добавить ту же папку повторно → вторая запись не появляется** (FR-020, research.md §10).
4. **Ключевая проверка регрессии.** Подготовить две **разные** папки с одинаковым именем
   (например, `~/work/notes` и `~/personal/notes`), добавить обе → **должно появиться две
   самостоятельные записи**, каждая открывается в свой vault (FR-020, US2 AS9). В вебе именно
   этот шаг ловит дефект, ради которого идентичность сделана непрозрачной: сравнение по имени
   схлопнуло бы записи в одну.
5. Задать одной из этих двух записей собственную подпись → она показывается вместо
   расположения, записи стали различимы, тождество папок от подписи не изменилось
   (FR-018, US2 AS10).
6. Переключиться на второй vault → дерево показывает его заметки; тема, размер шрифта и режим
   редактирования **не изменились** (FR-010, SC-007). В вебе переключение может переспросить
   разрешение на доступ к папке — это штатный путь, а не ошибка.
7. Внести несохранённые правки в заметку и переключить vault → предупреждение заранее, потеря
   только по явному подтверждению (FR-022, SC-008).
8. Переименовать папку известного vault снаружи → приложение **не разыскивает** её по новому
   расположению; если связь утрачена, запись помечена недоступной и добавляется заново
   (FR-023). Сохранение связи не проверяется как гарантия: на native она теряется, в вебе
   обычно переживает перенос — это платформенное поведение, а не требование (research.md §10).
9. Убрать vault из списка → папка и заметки на диске нетронуты (FR-024).
10. Проверить, что **внутри обеих папок vault не появилось ни одного служебного файла**
    приложения (FR-020, принцип VI).

## Сценарий 5 — Три состояния режима редактирования (US3, FR-025…FR-035)

Прогоняется на `FakeBridge`.

1. Раздел Кейбиндинги показывает активное состояние явно (FR-025).
2. Перевести `FakeBridge` в отказ при открытой заметке с правками → ожидаемо: текст и позиция
   курсора сохранены, заметка редактируется как обычный текст без vim-раскладки, заметное
   сообщение о причине (FR-035).
3. **Убедиться, что состояние стало `PlainInput`, а не `SimplifiedEmulation`** — автоматический
   откат на эмуляцию запрещён (FR-035, contracts/editor-mode-bridge.md §1).
4. Подождать → самопроизвольного восстановления не происходит; возврат только по явному
   действию пользователя (FR-035).
5. Указать несуществующий путь к конфигу → сообщение, конфиг не показан применённым (FR-033).
6. Перевести `FakeBridge` в «полноценный режим недоступен» → показана причина, упрощённая
   эмуляция **не** выдаётся за полноценный режим (FR-034).
7. На веб-сборке: полноценный режим постоянно недоступен с честной причиной (research.md §7).

## Сценарий 6 — Устаревание конфига (FR-026)

1. Активен полноценный режим (`FakeBridge`), конфиг применён.
2. Изменить файл конфига сторонним редактором → раздел показывает «изменён, не применён»;
   работающий режим продолжает использовать прежний конфиг (FR-026).
3. Применить по явному действию → признак расхождения исчезает.
4. **Изменить файл и вернуть прежнее содержимое до применения** → признак расхождения гаснет
   сам: сравнение идёт по хэшу содержимого, а не по времени изменения (research.md §8). Это
   проверка краевого случая из spec.md.
5. Удалить файл конфига → показано, режим продолжает работать на ранее применённом (FR-026).

## Сценарий 7 — Смена режима с открытой заметкой (FR-029…FR-032, SC-006)

1. Открыть заметку с несохранёнными правками, сменить режим → заметка сохранена, **об этом
   сообщено**, режим сменился (FR-029).
2. Сделать vault недоступным на запись, повторить → сохранение не удалось, **режим не сменился**,
   причина показана, правки не потеряны (FR-030).
3. Создать неразрешённый конфликт редактирования (по сценарию 4 фичи 001), сменить режим →
   переключение не выполняется, записи в файл не происходит, объяснено что сначала нужно
   разрешить конфликт (FR-031).
4. Закрыть все заметки, сменить режим → происходит немедленно, без шага сохранения (FR-032).

## Сценарий 8 — Дополнительно: обслуживание и диагностика (US4, FR-036…FR-043)

1. Изменить несколько настроек, выполнить сброс к умолчаниям с подтверждением → значения
   вернулись (FR-037).
2. **Список известных vault сохранён, ни один файл внутри vault не изменён** (FR-038, SC-011).
3. Повторить сброс при неразрешённом конфликте по открытой заметке → **ни одна настройка не
   изменилась**, сброс отменён целиком, причина объяснена (FR-037, кларификация 2026-08-09).
4. Посмотреть диагностику: состояние моста, версия, сведения об окружении (FR-039).
5. **Тест-сканер журналов**: прогнать сценарии 1–7 на vault, где заметки содержат уникальные
   строки-маркеры, затем просканировать журналы на присутствие этих строк → совпадений быть не
   должно (FR-041, research.md §12).
6. Убедиться, что абсолютных путей в журналах нет — только относительно корня vault.
7. Проверить, что при работе приложения не происходит ни одного сетевого обращения (FR-042,
   SC-013).

## Сценарий 9 — Миграция с `last_vault` (research.md §10)

1. На сборке без файла настроек создать `~/.config/typsidian/last_vault.txt` с путём к
   тестовому vault (состояние «до обновления»).
2. Запустить приложение → путь импортирован как единственная известная запись и как текущий
   vault; `last_vault.txt` удалён.
3. Убедиться, что второго источника истины не осталось: изменение текущего vault отражается
   только в `settings.json`.

## Проверка паритета таргетов (принцип II конституции)

Каждый сценарий выше прогоняется как минимум один раз на native-сборке и один раз на
web-сборке. Фича не считается готовой, пока оба прогона не дают одинаковый наблюдаемый
результат в терминах FR/SC.

Расхождения, допустимые по research.md §3, §7, §10 и §13, и **только они**:

| Расхождение | Основание |
|---|---|
| `can_reveal = false` в вебе: расположение показано, действия раскрытия нет | research.md §13 |
| Полноценный режим редактирования постоянно недоступен в вебе | research.md §7 |
| Единственный источник внешнего изменения настроек в вебе — другая вкладка | research.md §3 |
| Показываемое расположение: полный путь на native, имя папки в вебе | research.md §10, FR-018 |
| Перенос папки vault: на native связь теряется, в вебе обычно переживает — ни то ни другое не гарантируется | research.md §10, FR-023 |
| Переключение vault в вебе может переспросить разрешение на доступ к папке | research.md §10 |

Любое иное расхождение поведения между таргетами — дефект, а не особенность платформы.

**Что расхождением не является и проверяется одинаково на обоих таргетах**: две разные папки с
одинаковым именем дают две записи (шаг 4 сценария 4), одна и та же папка не заводится дважды,
подпись не влияет на тождество, служебные файлы внутри vault не появляются.
