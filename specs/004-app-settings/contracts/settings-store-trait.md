# Contract: `SettingsStore` (внутренний контракт ядра)

**Feature**: `specs/004-app-settings/spec.md` | **Plan**: `../plan.md`

Единственная точка доступа к хранилищу настроек. Один трейт, две реализации —
`NativeStore` (файл в каталоге конфигурации ОС) и `WebStore` (OPFS), — по образцу уже
работающего `VaultBackend` (принцип II конституции, NON-NEGOTIABLE). Условная компиляция
допустима только **внутри** реализаций; вызывающий код не ветвится по платформе.

## Форма трейта

| Операция | Обязательство |
|---|---|
| `open()` | Открыть или создать хранилище. Нечитаемый файл — не ошибка: возвращается `StorageState::DefaultsAfterUnreadable`, а не отказ (FR-013) |
| `load()` | Прочитать текущие значения с диска |
| `apply(changes)` | Записать набор изменений **атомарно**: либо весь набор, либо ничего (FR-037, research.md §5) |
| `capabilities()` | Расположение хранилища, `can_reveal`, доступность на запись (FR-036, research.md §13) |
| `reveal()` | Раскрыть хранилище средствами ОС; при `can_reveal = false` возвращает отказ, а не отсутствует как метод |
| `poll_events()` | Забрать накопившиеся события изменения хранилища с прошлого вызова (FR-013) |

`poll_events()` повторяет приём `VaultBackend::poll_events()` из фичи 001: pull-опрос вместо
push-потока, чтобы не требовать object-safe `Stream`.

## Реестр папок vault

Отдельная часть контракта, без которой FR-020 нереализуем. Ссылка на папку объявляется
**ассоциированным типом** `FolderRef`: `PathBuf` на native, `FileSystemDirectoryHandle` на web
(research.md §10). Вызывающий код получает её от системного выбора папки и передаёт обратно, не
разбирая содержимого.

| Операция | Обязательство |
|---|---|
| `find_existing(candidate: &FolderRef)` | Вернуть `VaultId`, если кандидат — **та же самая папка**, что уже в списке. Native сравнивает канонизированные пути; web вызывает `isSameEntry()`. Сравнение имён и показываемых расположений запрещено (FR-020) |
| `add(candidate: FolderRef, location: String)` | Выдать новый `VaultId` и сохранить ссылку в реестре таргета |
| `resolve(id: VaultId)` | Вернуть `Resolved(FolderRef)`, `NeedsPermission` или `Missing` |
| `set_label(id, Option<String>)` | Задать или снять подпись записи; подпись не участвует в тождестве и не обязана быть уникальной (FR-018) |
| `forget(id: VaultId)` | Убрать запись и ссылку из реестра, **не трогая папку на диске** (FR-024) |

`NeedsPermission` — не ошибка: на платформах, где постоянный доступ к папке требует разрешения
пользователя, оно переспрашивается по его жесту. Фича 001 уже зафиксировала это в своих
Assumptions, и отказ в разрешении ошибкой не считается.

`find_existing` асинхронен и сравнивает кандидата перебором по списку — до N асинхронных
сравнений на одно добавление. При рабочей границе в 50 записей это несущественно.

## Обязательства реализаций

**Общие для обеих**:

1. **Атомарность записи.** Наблюдаемое состояние файла — либо прежнее целиком, либо новое
   целиком. Обрыв записи не оставляет обрезанный TOML (research.md §5).
2. **Сохранение пользовательского форматирования.** Комментарии и порядок ключей, написанные
   пользователем руками, переживают запись приложения (research.md §2). Запись меняет только
   затронутые значения.
3. **Никаких записей внутрь vault.** Хранилище лежит вне любого vault; служебные файлы в папке
   заметок не создаются ни при каких операциях (FR-011, FR-020, принцип VI).
4. **Нечитаемый файл не затирается молча.** Перед первой записи поверх испорченного файла он
   переименовывается рядом, и пользователь уведомляется (FR-013, research.md §6).
5. **Одинаковая валидация.** Диапазон размера шрифта `8..=32` и правила ведения списка vault
   (одна и та же папка не заводится дважды, подпись в тождестве не участвует) проверяются в
   общем коде, а не в каждой реализации, — как `is_valid_note_name` в `vault::backend`
   (принцип II: реализации не расходятся по платформе). Платформенным остаётся **только**
   сравнение самих папок.
6. **Никаких меток в vault.** Тождество папок устанавливается средствами платформы; служебные
   файлы-метки внутри vault не создаются ни при каких операциях (FR-020, принцип VI).
7. **Розыск запрещён.** Перенесённая или переименованная снаружи папка не разыскивается по
   новому расположению ни на одной платформе; при утрате связи запись становится
   `Unavailable` (FR-023).

**Только `NativeStore`**: наблюдение за файлом через `notify` с дебаунсингом; раскрытие в
файловом менеджере системы; `can_reveal = true`. `FolderRef = PathBuf`, ссылки хранятся в
`settings.toml` рядом с записями.

**Только `WebStore`**: периодическая сверка файла в OPFS с интервалом ≤1 с (бюджет SC-014);
`can_reveal = false`. Единственный возможный источник внешнего изменения — другая вкладка того
же происхождения (research.md §3). `FolderRef = FileSystemDirectoryHandle`, ссылки хранятся в
реестре IndexedDB под ключом `VaultId` — сериализовать их в TOML невозможно (research.md §1).

## События

`SettingsEvent` — то, что `poll_events()` возвращает вызывающей стороне:

| Событие | Когда |
|---|---|
| `ValuesChangedExternally { changed }` | Файл изменён вне текущего окна (FR-013, FR-006) |
| `StorageUnreadable` | Файл повреждён, нечитаем или удалён (FR-013) |
| `StorageRecovered` | Ранее нечитаемый файл снова разбирается (пользователь починил руками) |
| `StorageBecameReadOnly` | Каталог потерял доступ на запись (FR-014) |
| `InvalidFileSetAside { moved_to }` | Испорченный файл переименован рядом перед первой записью |

Разбор событий на стороне UI — `frontend-settings.md`.

## Что трейт НЕ делает

- **Не вызывает `VaultBackend`.** Там, где смена режима требует сохранить открытую заметку,
  ядро возвращает инструкцию `ApplyPlan::RequiresNoteSave`, а исполняет её вызывающая сторона
  (research.md §9). Сцепки двух подсистем нет.
- **Не знает о msgpack-rpc.** Состояние режима редактирования приходит из отдельного трейта —
  `editor-mode-bridge.md`.
- **Не решает, что показать пользователю.** Формулировки сообщений — забота UI; трейт отдаёт
  перечислимые события и причины.
