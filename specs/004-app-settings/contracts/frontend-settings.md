# Contract: Ядро → UI (панель настроек)

**Feature**: `specs/004-app-settings/spec.md` | **Plan**: `../plan.md`

Контракт границы WASM/JS для панели настроек. Все типы порождаются из Rust-определений
(принцип IV конституции) — здесь описана форма контракта, не итоговый `.d.ts`. Симметричен
`specs/001-vault-manager/contracts/frontend-events.md`.

## События

UI забирает `SettingsEvent` опросом (`poll_events()`, см. `settings-store-trait.md`). Каждый
вариант — самостоятельный кейс в `switch`; TS `strict` обязан обработать их исчерпывающе
(`never` в `default`).

| Событие | UI обязан |
|---|---|
| `ValuesChangedExternally` | Применить новые значения и обновить панель без перезапуска (FR-013). Это же покрывает согласованность между окнами (FR-006) |
| `StorageUnreadable` | Показать, что работа идёт на значениях по умолчанию, и что испорченный файл не тронут (FR-013) |
| `StorageRecovered` | Снять предупреждение, показать восстановленные значения |
| `StorageBecameReadOnly` | Предупредить, что изменения действуют до конца сессии и не переживут перезапуск (FR-014) |
| `InvalidFileSetAside` | Сообщить, куда перенесён испорченный файл (research.md §6) |
| `EditorModeChanged` | Перерисовать раздел Кейбиндинги по новому состоянию; при `PlainInput` — заметное сообщение с причиной (FR-035) |
| `EditorConfigDiskStateChanged` | Показать «изменён, не применён» с действием применения (FR-026); не применять самостоятельно |

## Запросы UI → ядро

| Действие пользователя | Вызов | Обязательство UI |
|---|---|---|
| Смена темы, размера шрифта | `apply(changes)` | Никакой кнопки «сохранить» (FR-003); значение вне `8..=32` отклоняется ядром, UI показывает причину (FR-016) |
| Добавить папку как vault | `find_existing(ref)` → `add(ref, location)` | Выбор папки — жест пользователя, выполняется в UI (как `showDirectoryPicker` в `useVault.ts`). Ссылку на папку UI передаёт ядру **не разбирая** её; повторное добавление той же папки ядро само сведёт к существующей записи (FR-020) |
| Задать подпись записи | `set_label(id, label)` | Показывается вместо расположения; UI не проверяет уникальность — подпись её не требует (FR-018) |
| Переключить vault | `resolve(id)` → `apply(changes)` | `NeedsPermission` разрешается переспросом по жесту пользователя, отказ ошибкой не считается. Предупреждения о несохранённых правках и конфликтах — существующая машинерия фичи 001, не переизобретается (FR-022) |
| Переключить режим редактирования | `apply(changes)` → разбор `ApplyPlan` | См. ниже |
| Применить изменённый конфиг | `apply_config(path)` | Только по явному действию (FR-026) |
| Сброс к умолчаниям | `apply(reset_changes)` | Подтверждение — в UI; атомарность и предусловия — в ядре (FR-037) |
| Раскрыть хранилище | `reveal()` | Действие показывается только при `capabilities().can_reveal` (FR-036) |

## Разбор `ApplyPlan` — единственное место, где UI делает больше одного шага

```text
apply(changes) ─▶ Applied              ─▶ перерисовать панель
               ─▶ RequiresNoteSave{p}  ─▶ VaultBackend::write(p, ...)
                                          ├─ успех ─▶ сообщить о сохранении (FR-029), повторить apply
                                          └─ отказ ─▶ показать причину; режим НЕ менять (FR-030)
               ─▶ Rejected{reason}     ─▶ показать причину; НИ ОДНА настройка не меняется
```

Это исполнение инструкции, вернувшейся из ядра, а не самостоятельное решение: UI не проверяет
сам, есть ли конфликт и нужно ли сохранять. Тот же приём зафиксирован в пост-дизайн-проверке
фичи 001 для `backlinks()`.

## Требования к типам

- `EditorMode` — **трёхвариантный** размеченный union, не булев флаг. Пропуск варианта
  `PlainInput` в `switch` обязан быть ошибкой компиляции TS `strict` (FR-025).
- `RejectReason` и `OutageReason` — перечисления; UI сопоставляет им формулировки, но не
  придумывает новых состояний.
- Расхождение показанного значения с фактическим запрещено (FR-004, SC-005): UI рендерит то,
  что вернуло ядро, и не хранит собственную оптимистичную копию значения до подтверждения.

## Что UI НЕ делает

- Не решает, нужно ли принудительное сохранение и допустимо ли переключение (принцип I).
- Не пишет в файл настроек напрямую и не разбирает его формат.
- Не ветвится по таргету: различия платформ приходят значениями в `StoreCapabilities` и
  `availability()` (research.md §13).
- Не сравнивает папки сам и не судит о том, та ли это папка: передаёт полученную ссылку в
  `find_existing()` и доверяет ответу ядра (FR-020, принцип I).
- Не хранит настройки в собственном состоянии дольше одного кадра отрисовки — источник истины
  файл, а не компонент.
