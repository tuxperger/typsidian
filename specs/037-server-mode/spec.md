# Feature Specification: Серверный режим web

**Feature Branch**: `037-server-mode`

**Created**: 2026-10-24

**Status**: Implemented

**Priority**: P1

**Summary**: Web-версию можно открыть на собственном сервере: вход по паролю или через провайдера входа, свои vault на сервере, та же работа с заметками, что с папкой на устройстве.

**Input**: User description: "Сервер Typsidian (self-hosted) и вход: пользователь ставит сервер у себя, администратор заводит аккаунты командой сервера; вход по логину и паролю и через внешнего провайдера OIDC; у пользователя несколько своих vault на сервере (создать, переименовать, удалить), без общего доступа; все операции с заметками vault выполняются на сервере; изменения vault приходят в открытую вкладку; сессии можно завершить, в том числе на всех устройствах; vault на сервере — обычные папки файлов."

## Термины

- **Сервер** — установка Typsidian на машине пользователя или его команды (self-hosted),
  к которой web-версия обращается по сети (конституция VI, XI).
- **Администратор** — тот, кто поставил сервер и управляет аккаунтами с машины сервера.
- **Аккаунт** — пользователь сервера: логин, пароль и (или) привязка к провайдеру входа.
- **Vault на сервере** — папка файлов на сервере, принадлежащая одному аккаунту.
- **Сессия** — вход с одного браузера; у аккаунта может быть несколько сессий.

## Clarifications

### Session 2026-10-24

Модель (self-hosted), оба режима web, вход паролем и через провайдера, несколько своих
vault без общего доступа — решения пользователя от 2026-10-24. Остальное закрыто по
конституции (VI, VII, IX, XI) без вопроса пользователю.

- Q: Сколько живёт вход? → A: Сессия продлевается при каждом действии и истекает после
  30 дней без действий; срок задаёт администратор в настройках сервера. Закрытие вкладки
  вход не завершает.
- Q: Чем входит пользователь — логином или почтой? → A: Логином, который задал
  администратор. Пользователь провайдера сопоставляется аккаунту по привязке, которую
  задаёт администратор (идентификатор пользователя у провайдера); почта для сопоставления
  не используется — её может сменить сам пользователь у провайдера.
- Q: Сколько попыток входа? → A: После 5 неверных паролей подряд для одного логина вход
  с этим логином закрывается на нарастающее время (1, 2, 4… минут, до часа); сообщение
  называет время. Верный вход сбрасывает счётчик.
- Q: Пароль — требования? → A: Не короче 12 знаков; пароль задаёт администратор или сам
  пользователь при смене (нужен текущий пароль).
- Q: Где vault аккаунта на диске сервера? → A: Под папкой данных сервера, отдельная папка на
  аккаунт; имя папки vault — его имя. Путь папки данных задаёт администратор.
- Q: Удаление vault — куда? → A: Как удаление заметки: папка уходит в корзину сервера
  (папка удалённого рядом с данными), откуда администратор может вернуть её; из интерфейса
  — только с подтверждением, где названо число заметок.
- Q: Что делают функции, отличающиеся на web с папкой на устройстве? → A: Работают как на
  рабочем столе — их выполняет сервер: установка шаблонов (007), экспорт пишет в папку
  экспорта vault на сервере, файл экспорта можно скачать. Синхронизация и история git (011)
  на сервере — фича 038 (см. Assumptions).
- Q: Что видно в журнале сервера? → A: Входы и выходы, отказы доступа, ошибки — с логином,
  адресом и временем; без текста заметок, имён заметок, паролей и токенов (XI).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Войти и работать с заметками на сервере (Priority: P1)

Администратор поставил сервер и завёл аккаунт «anna». Анна открывает адрес сервера в
браузере, на стартовом экране выбирает «Сервер», вводит логин и пароль, видит список своих
vault, открывает «Диссертация» и работает как с папкой на устройстве: дерево, правка с
автосохранением, предпросмотр, поиск, связи, экспорт. Закрыв вкладку и открыв её снова,
Анна остаётся во входе и видит те же заметки.

**Why this priority**: без входа и работы с заметками серверного режима нет.

**Independent Test**: на чистом сервере завести аккаунт, войти в браузере, создать vault,
создать заметку, написать текст, перезагрузить страницу — текст на месте; на диске сервера
файл заметки лежит в папке этого vault.

**Acceptance Scenarios**:

1. **Given** аккаунт заведён, **When** пользователь вводит верный логин и пароль, **Then**
   он видит список своих vault.
2. **Given** неверный пароль, **Then** вход не выполнен, сообщение не уточняет, что именно
   неверно (логин или пароль).
3. **Given** открыт vault, **When** пользователь правит заметку, **Then** правка сохраняется
   на сервере так же, как сохраняется в папке на устройстве (автосохранение, конфликты 001).
4. **Given** vault открыт, **Then** доступны те же возможности, что с папкой на устройстве:
   дерево, правка, предпросмотр, поиск, связи, граф, экспорт, снимки, задачи, закладки.
5. **Given** пользователь вошёл, **When** он закрывает и снова открывает вкладку, **Then**
   вход сохранён, пока сессия не истекла или не завершена.
6. **Given** web-версия, **Then** стартовый экран предлагает оба способа: «Папка на
   устройстве» (как раньше) и «Сервер»; выбор с папкой на устройстве работает без сервера.

### User Story 2 - Свои vault на сервере (Priority: P2)

Анна создаёт vault «Черновики», переименовывает его в «Статьи» и удаляет ненужный «Тест»
после подтверждения. Другой пользователь сервера vault Анны не видит и открыть не может, даже
зная его имя.

**Why this priority**: без нескольких vault и изоляции серверный режим не годится для
команды.

**Independent Test**: два аккаунта; первый создаёт vault; второй не видит его в списке и
получает отказ при попытке открыть его прямой ссылкой.

**Acceptance Scenarios**:

1. **Given** пользователь вошёл, **When** он создаёт vault с именем, **Then** vault появляется
   в списке и открывается пустым.
2. **Given** vault, **When** пользователь его переименовывает, **Then** имя меняется, заметки
   на месте.
3. **Given** vault, **When** пользователь удаляет его и подтверждает, **Then** vault исчезает
   из списка; без подтверждения ничего не удаляется.
4. **Given** чужой vault, **When** пользователь обращается к нему любым способом, **Then**
   отказ, и ни имя, ни содержимое чужого vault не раскрываются.

---

### User Story 3 - Вход через провайдера входа (Priority: P2)

Команда пользуется своим провайдером входа (Keycloak, Authentik и подобные). Администратор
указывает его в настройках сервера; на экране входа появляется «Войти через …». Анна входит
через провайдера и попадает в свои vault. Аккаунт, привязанный к провайдеру, может не иметь
пароля.

**Independent Test**: настроенный провайдер; вход через него для аккаунта, у которого есть
привязка, — успешен; для неизвестного провайдеру пользователя — отказ с понятным сообщением.

**Acceptance Scenarios**:

1. **Given** провайдер настроен, **Then** экран входа показывает кнопку входа через него.
2. **Given** пользователь провайдера сопоставлен аккаунту, **When** он входит, **Then** он
   видит vault этого аккаунта.
3. **Given** пользователь провайдера не сопоставлен ни одному аккаунту, **Then** вход не
   выполнен с объяснением «аккаунт не заведён — обратитесь к администратору».

---

### User Story 4 - Изменения приходят сами (Priority: P2)

Анна открыла заметку в двух вкладках (или на ноутбуке и телефоне). Правка, сохранённая в
одной, появляется в другой без перезагрузки — так же, как внешнее изменение файла в папке на
устройстве (001), включая конфликт, если обе правили одно место.

**Acceptance Scenarios**:

1. **Given** две вкладки с одним vault, **When** в одной создана, переименована или
   сохранена заметка, **Then** в другой дерево и заметка обновляются за секунды.
2. **Given** несохранённые правки во второй вкладке, **Then** работает разрешение
   конфликта 001, правки не теряются.
3. **Given** изменение файла vault прямо на диске сервера (администратором, git, Syncthing),
   **Then** открытые вкладки узнают о нём так же.

---

### User Story 5 - Сессии и выход (Priority: P3)

Анна видит в настройках список своих входов (браузер, время последнего действия), завершает
чужой ноутбук или все сессии сразу. Смена пароля завершает остальные сессии.

**Acceptance Scenarios**:

1. **Given** несколько сессий, **Then** пользователь видит их список с текущей отмеченной.
2. **When** пользователь завершает сессию, **Then** вкладка с ней при следующем действии
   попадает на экран входа, несохранённые правки не теряются молча.
3. **When** пользователь выходит «на всех устройствах» или меняет пароль, **Then** все прочие
   сессии завершены.

---

### User Story 6 - Администратор управляет аккаунтами (Priority: P1)

Администратор на машине сервера заводит аккаунт, задаёт или сбрасывает пароль, привязывает
пользователя провайдера, блокирует и удаляет аккаунт. Открытой регистрации нет.

**Acceptance Scenarios**:

1. **Given** сервер, **When** администратор заводит аккаунт с паролем, **Then** с ним можно
   войти.
2. **When** администратор блокирует аккаунт, **Then** его сессии завершены и вход
   невозможен; vault на диске не тронуты.
3. **When** администратор удаляет аккаунт, **Then** vault аккаунта удаляются только при явном
   указании, иначе остаются на диске.
4. **Given** экран входа, **Then** зарегистрироваться самому нельзя.

### Edge Cases

- Связь с сервером пропала во время правки — правка не теряется: заметное сообщение «нет
  связи с сервером», несохранённый текст остаётся в редакторе, сохраняется после
  восстановления связи (конституция VII).
- Серия неверных паролей — вход для этого логина и адреса временно замедляется или
  блокируется; сообщение говорит, когда можно повторить.
- Имя vault с недопустимыми для папки знаками или занятое — отказ с причиной до создания.
- Путь к заметке с `..` или абсолютный — отказ; файлы вне vault недостижимы.
- Сессия истекла во время работы — экран входа; после входа пользователь возвращается в тот
  же vault, несохранённые правки не потеряны.
- Большой vault (5 000 заметок) — список и дерево открываются не дольше, чем с папкой на
  устройстве на том же сервере.
- Функции, которые на web с папкой на устройстве недоступны или отличаются (установка
  шаблонов), в серверном режиме работают так, как на рабочем столе: выполняет их сервер.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Web-версия MUST предлагать два режима: папка на устройстве (как раньше) и
  сервер; режим с папкой MUST работать без сервера.
- **FR-002**: Вход MUST выполняться по логину и паролю и, если настроен, через провайдера
  входа; самостоятельной регистрации MUST NOT быть.
- **FR-003**: После входа пользователь MUST видеть только свои vault и MUST мочь создать,
  переименовать и удалить (с подтверждением) свой vault.
- **FR-004**: Доступ к чужому vault MUST быть невозможен любым способом и MUST NOT раскрывать
  его имя или содержимое.
- **FR-005**: Работа с заметками в vault на сервере MUST давать те же возможности и те же
  гарантии сохранности, что с папкой на устройстве (001–035).
- **FR-006**: Изменения vault (из другой вкладки, устройства или прямо на диске сервера)
  MUST приходить в открытые вкладки без перезагрузки.
- **FR-007**: Пользователь MUST видеть свои сессии и мочь завершить любую или все;
  смена пароля MUST завершать прочие сессии.
- **FR-008**: Администратор MUST управлять аккаунтами с машины сервера: завести, задать или
  сбросить пароль, привязать пользователя провайдера, заблокировать, удалить.
- **FR-009**: Vault на сервере MUST быть обычными папками файлов (конституция VI).
- **FR-010**: Потеря связи с сервером MUST показываться заметно и MUST NOT терять
  несохранённые правки (конституция VII).
- **FR-011**: Требования безопасности конституции XI MUST соблюдаться: изоляция, хранение
  паролей, защищённые сессии, защита от подделки запросов, ограничение попыток входа,
  журналы без текста заметок и секретов.
- **FR-012**: Одинаковые тексты интерфейса для обоих режимов — из переводов; экраны входа и
  списка vault доступны с клавиатуры и на узком экране.

### Key Entities

- **Аккаунт**: логин, отображаемое имя, хэш пароля (может отсутствовать), привязки к
  провайдеру входа, состояние (активен, заблокирован).
- **Сессия**: аккаунт, когда создана, последнее действие, описание браузера; завершается.
- **Vault на сервере**: владелец, имя, папка на диске сервера.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: От открытия адреса сервера до открытой заметки — не больше 4 действий
  пользователя (выбрать «Сервер», войти, открыть vault, открыть заметку).
- **SC-002**: 100% обращений к чужому vault и к путям вне vault получают отказ (проверяется
  тестами на каждую операцию).
- **SC-003**: Правка из одной вкладки видна в другой не позже чем через 3 с.
- **SC-004**: При обрыве связи 0 потерянных правок: после восстановления связи текст на
  сервере совпадает с текстом в редакторе.
- **SC-005**: Набор текста в заметке на сервере не медленнее, чем с папкой на устройстве
  (задержка ввода не растёт: подсветка и дополнение работают в браузере).

## Assumptions

- Сервер ставит и обслуживает пользователь или его команда; проект не предоставляет
  облачного хостинга (конституция VI).
- Защищённое соединение (HTTPS) обеспечивает обратный прокси перед сервером; сервер требует,
  чтобы обращения шли по защищённому соединению, кроме локальной отладки.
- Общий доступ к vault и совместная правка — вне этой фичи (конституция XI требует отдельной
  поправки).
- Офлайн-работа серверного режима сверх честной деградации (FR-010) — вне этой фичи.
- Desktop и Android серверный режим не получают в этой фиче.
- Синхронизация git и Syncthing (011) в серверном режиме — фича 038: ей нужны секреты
  (токены, ключи) и настройки устройства на сервере, у каждого аккаунта свои. В 037 раздел
  «Синхронизация» говорит, что она недоступна; vault на сервере остаётся обычной папкой, и
  администратор может вести её git снаружи — изменения приходят во вкладки сами (US4 AS3).
- Импорт из папки Obsidian (021) на сервере недоступен: папку-источник нечем выбрать
  (research.md §4).
