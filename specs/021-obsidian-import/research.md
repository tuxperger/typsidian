# Research: Импорт из Obsidian

**Feature**: 021-obsidian-import | **Date**: 2026-10-15

## §1. Разбор Markdown

**Decision**: `pulldown-cmark` с `ENABLE_TABLES`, `ENABLE_FOOTNOTES`, `ENABLE_TASKLISTS`,
`ENABLE_STRIKETHROUGH`, `ENABLE_MATH`, `ENABLE_YAML_STYLE_METADATA_BLOCKS`. Расширения
Obsidian, которых нет в крейте (`[[…]]`, `![[…]]`, `==выделение==`, `%%комментарий%%`,
`#тег` в тексте), распознаются в текстовых событиях до перевода (§3).

## §2. Перевод в Typst

| Markdown | Typst |
|---|---|
| `#`…`######` | `=`…`======` |
| `**x**`, `*x*`, `~~x~~`, `==x==` | `*x*`, `_x_`, `#strike[x]`, `#highlight[x]` |
| код строкой / блоком с языком | `` `x` `` / ```` ```lang ```` |
| списки, вложенные, нумерованные | `-`, `+` с отступом |
| флажки `- [ ]`, `- [x]` | `- ☐`, `- ☑` |
| таблица | `#table(columns: n, [..], …)` с заголовком `table.header` |
| цитата | `#quote(block: true)[…]` |
| сноска | `#footnote[…]` на месте ссылки |
| `---` | `#line(length: 100%)` |
| `[t](https://…)` | `#link("https://…")[t]` |
| картинка | `#image("путь вложения")` (§4) |
| HTML, вставка заметки, блок плагина, mermaid, неизвестное | исходный текст в `#raw(block: true, "…")` + запись в отчёте |

Весь пользовательский текст экранируется по правилам разметки Typst (`*`, `_`, `#`, `$`,
`@`, `<`, `` ` ``, `\`, `[`, `]`), чтобы заметка гарантированно собиралась (FR-008).

## §3. Особенности Obsidian

`[[Имя]]`, `[[Имя|текст]]`, `[[Имя#Раздел]]`, `[[Имя#^блок]]` → ссылка vault (§6, §10);
`![[картинка.png]]` и `![[картинка.png|300]]` → `#image(…, width: 300pt)`; `![[Заметка]]`
(встраивание) → ссылка + запись «встраивание заменено ссылкой»; `%%…%%` → комментарий Typst
`/* … */`; YAML-шапка → свойства 020, если модуль `properties` есть в ядре, иначе — блок
`/* properties: … */` в начале и запись в отчёте не делается (US2 сценарий 4).

## §4. Вложения

Картинка копируется по правилам вложений vault (006 `placement`, 016): в папку ассетов
заметки; путь в `#image` — `markup_path` 006. Один файл, на который ссылаются несколько
заметок, копируется один раз (по первой).

## §5. Формулы

`$…$` и `$$…$$` → `mitex::convert_math`. Результат проверяется пробной сборкой формулы в
`PreviewWorld`; ошибка или паника (перехвачена) → исходная запись в `#raw` и запись в отчёте.

## §6. Имена и ссылки

Дерево сохраняется; `.md` → `.typ`. Недопустимые знаки (`: * ? " < > | \`) и конечные
точки/пробелы → `-`; совпадения после замены — суффикс ` (2)`. Ссылка без пути разрешается
как в Obsidian: точное совпадение пути → единственная заметка с таким именем → ближайшая
по дереву (наименьшая общая глубина), неоднозначность — в отчёт. Нет цели — ссылка
сохраняется как есть и пишется в отчёт.

## §7. Пакет

`ImportState` держит окно (образец `BatchState` 009): план (список файлов, имена, карта
ссылок) строится первым шагом по одному обходу источника; затем шаг = один файл: перевод →
атомарная запись (`write` 009 через `tmp/`) → строка журнала. Отмена проверяется между
шагами (≤2 с — шаг на файл ≤5 МБ). Совпадение имени назначения: «пропустить» или «рядом» с
суффиксом ` (импорт)`.

## §8. Журнал и продолжение

`.typsidian/imports/<id>.json`, `id` — хэш пути источника и места назначения: список
перенесённых исходных путей с назначениями. Повторный запуск с теми же источником и
назначением читает журнал и пропускает перенесённое (FR-011); карта ссылок строится заново
целиком, поэтому ссылки между старыми и новыми заметками сходятся.

## §9. Источник только для чтения

Источник — `VaultBackend` той же реализации, что vault, обёрнутый в `ReadOnly<B>`: методы
записи возвращают ошибку, а не пишут (FR-002 обеспечен типом). Web — `showDirectoryPicker`
в режиме `read`; нет API — импорт недоступен с причиной (C5). Служебные `.obsidian/`,
`.trash/` исключаются.

## §10. Ссылка с текстом

`graph::link_sites` принимает `[[путь|текст]]`: `raw` — до первой `|`, новое поле `label`.
`resolve_link_target`, индекс, граф и перенос 023 работают по `raw`; перенос переписывает
только часть пути, сохраняя `|текст`. В документе запись выводится как есть (как и
`[[путь]]` сегодня).

## §11. Решения при реализации ядра (2026-10-15)

**§5 — `mitex` (T001, T017)**. Decision: крейт `mitex` 0.2.4 собирается под `wasm32-unknown-unknown` и под
native без правок и тянет только чистый Rust (`logos`, `rowan`, `rkyv`, `ena`…; из «системных» — `rustix` и
`linux-raw-sys`, это привязки к системным вызовам без нативных библиотек, `nix-env-agent` не нужен). Свой
перевод LaTeX не писался. Но вывод `mitex` рассчитан на пакет Typst `@preview/mitex` (вспомогательные
`mitexsqrt`, `pmatrix`, `textmath`, `operatorname`, `mitexmathbf`…), без него формула не соберётся. Поэтому
`import/math.rs` заменяет вспомогательные вызовы встроенными средствами Typst (`sqrt`/`root`, `mat(delim: …)`,
`op("…")`, строки вместо `#textmath[…]`), разбирает результат как математику Typst и проверяет, что каждое имя
длиннее одной буквы есть в стандартной библиотеке Typst; не прошло — `None`, формула остаётся `#raw` и идёт в отчёт.
Полная пробная сборка формулы в `PreviewWorld` не делается: каждая сборка заново разбирает встроенные шрифты
(9,6 МБ), на заметках с сотнями формул это секунды; её роль выполняют проверка имён и тесты, собирающие все
образцы настоящей сборкой (SC-001). Паника `mitex` перехватывается `catch_unwind` (на wasm32 с `panic=abort`
перехват недействует; на образцах паник нет). Подключение крейтов потребовало правки одной строки
`sync/syncthing.rs` (`== Some(id.as_str())`): `rkyv` добавляет реализации `PartialEq<ArchivedOption>`, и
`Some(id)` перестал выводиться.

**§9 — источник только для чтения (T007, T012)**. Decision: `ReadOnly<B>` реализован, но «второй `NativeBackend`
как у vault» неисполним: `NativeBackend::open` заводит в папке `.typsidian/`, SQLite-кэш и слежение, а
`WebBackend::from_handle` — служебную папку, то есть само открытие изменило бы источник (FR-002, SC-005). Поэтому
добавлены конструкторы без побочных эффектов: `NativeBackend::open_read_only(path)` и (внутри ядра)
`WebBackend::for_reading`; оба дают `AccessState::ReadOnly`, пустой индекс и ничего не создают. Обход источника —
новый метод `VaultBackend::list_source_files` (все файлы с размерами, скрытые записи — только счётчик
`excluded`): `list()` отдаёт лишь `.typ` и доски, Markdown в нём нет. Для web — класс `ImportSource`
(`fromHandle(name, handle)`), который держит `ReadOnly<WebBackend>`; для native — состояние оболочки
`ImportSource` с `ReadOnly<NativeBackend>`.

**§7 — состояние пакета (T011)**. Decision: план (файлы, имена назначения, карта ссылок) хранится в ядре под
ключом пакета (`ImportState.id`, уникален на каждый `import_begin`), а `ImportState` — счётчики, последний
файл и хвост из 20 проблемных строк. Пересылка всего плана на каждом шаге стоила бы сериализации списка в
тысячи записей 2 000 раз. Потерянный план (перезагрузка страницы) — `ImportError::SessionLost`; новый
`import_begin` читает журнал и продолжает. Отмены в ядре нет: окно перестаёт звать `import_step` и зовёт
`import_finish`; отмену ядро узнаёт по `next < total`. Порядок шагов: сначала все заметки, затем прочие
файлы; картинка, на которую сослалась заметка, к своей очереди уже скопирована и шагом не повторяется.

**§8 — журнал (T020)**. Decision: `.typsidian/imports/<id>.json`, `id` — FNV-1a от пути источника и
назначения. К полям из data-model добавлены `attachments` (источник → назначение скопированных вложений:
общая картинка после продолжения не копируется второй раз), `skipped` (окончательно пропущенные файлы) и
`started_ms`/`total` (для экрана C4). Журнал пишется раз в 16 шагов, на последнем шаге и в `import_finish`
(запись целиком на каждом шаге — квадратичный объём): при внезапном обрыве до 15 последних заметок будут
переписаны, при политике «рядом» они могут лечь копиями «(импорт)». Записи журнала, назначение которых из vault
исчезло, при продолжении отбрасываются (удалённое пользователем переносится заново). Время `at` в обзоре — то,
что окно передало в `ImportJob.started_ms`: часов в ядре под wasm нет.

**§12. Заметка отчёта и тексты**. Decision: тексты отчёта приходят из переводов окна в `ImportJob.texts`
(`ReportTexts`, поля со значениями по умолчанию на английском); имя файла отчёта — `texts.file_name` +
` (2)` при занятом имени. Новых `AppMessage` нет: исходы шагов — типизированные значения (`Outcome`,
`LossKind`, `SkipReason`).

**§13. Дополнения к таблице §2/§3**. Выноски `> [!тип] Заголовок` → `#quote(block: true)[*Заголовок* …]`;
`<br>` → перенос строки; комментарий HTML `<!-- -->` → комментарий Typst без потери; ссылка Markdown на файл
`.md` → ссылка vault; неподдерживаемые Typst форматы картинок (`bmp`, `tiff`…) → исходный текст и потеря
`Embed`; YAML, который не вписался в свойства 020 (вложенные словари), → комментарий `/* properties: … */` и
потеря `Properties`; вызов Typst (`#strike[…]`, `#link(…)[…]`, `#footnote[…]`, `#image(…)`) перед `.` или
`(` отделяется `\u{200b}`, иначе Typst прочёл бы их продолжением вызова. Имя файла с `#`, `$`, `@`, `_`,
`~`, `[`, `]`, `=` в начале пути ссылки заменяется на `-`, когда `[[путь]]` перестаёт читаться как текст
разметки (разбор ссылок 001 не знает экранирования). Новые виды потерь: `Properties`, `Syntax` (страховка:
итог разбирается синтаксическим анализатором Typst, при ошибке заметка остаётся исходным текстом целиком).
Причины пропуска `Unreadable`, `WriteFailed`.

## §12. Замер SC-004 (T023)

**Decision**: SC-004 по пути ядра выполнен с огромным запасом; порог плана «шаг >50 мс на
файле 1 МБ в wasm → отдельный воркер» нативно **превышен**, в wasm не проверен.

Замер — путь ядра нативно (`packages/core/benches/import_scale.rs`, release), а **не окно
рабочего стола**: Tauri-окно здесь запустить нельзя, поэтому ручной сценарий
quickstart.md §3 (правка другой заметки во время импорта, «Продолжить», `diff -r`) остаётся
непроверенным. Источник — вывод `scripts/dev/gen-obsidian.sh` (2 000 заметок, 20 папок,
200 картинок, YAML-шапка у каждой третьей, вики-ссылки, формулы, таблицы), приёмник —
`NativeBackend` во временной папке, полный цикл `import_begin` → `import_step` × 2 200 →
`import_finish`.

| Величина | Результат | Бюджет |
|---|---|---|
| `import_begin` (план) | 24,6 мс | — |
| Шаги, сумма (2 200 шагов) | 449 мс; среднее 0,20 мс, медиана 0,19 мс, p99 0,64 мс | — |
| `import_finish` (журнал, отчёт) | 11,8 мс | — |
| Весь цикл | 486 мс | ≤2 мин (SC-004) |
| Максимум шага = отклик отмены | 1,47 мс | ≤2 с (SC-004) |
| Шаг на заметке 1 МБ | 228 мс | ≤50 мс (порог плана для wasm) |

Итог прогона: 200 чисто, 2 000 с потерями, 0 пропущено (у каждой сгенерированной заметки
есть конструкция с потерей — это не влияет на время).

**Вывод**: на 2 000 заметок цикл укладывается в SC-004 на три порядка (0,5 с против 2 мин;
1,5 мс против 2 с), отмена между шагами мгновенна. Нативно шаг на заметке в 1 МБ стоит
228 мс — выше порога плана в 50 мс; в wasm он будет не быстрее, значит для таких файлов
вынос шага в отдельный воркер остаётся нужным (или разбор крупного Markdown по частям).
Среди обычных заметок (≈1–2 КБ) шаг на четыре порядка меньше порога. Замер в wasm и в окне
рабочего стола не делался — не проверено.
