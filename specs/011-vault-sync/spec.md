# Feature Specification: Синхронизация vault — история версий и доставка между устройствами

**Feature Branch**: `011-vault-sync`

**Created**: 2026-10-03

**Status**: Draft

**Priority**: P2

**Summary**: История версий и удалённый репозиторий (как синхронизация с GitHub в typst.app) плюс совместная работа с Syncthing: файлы между устройствами доставляет Syncthing, историю и резервную копию ведёт git, конфликты разрешаются в приложении.

**Input**: User description: "Синхронизация vault: интеграция с git (в духе GitHub/GitLab-синхронизации typst.app) и с Syncthing, причём так, чтобы оба способа работали вместе и дополняли друг друга. Git — история версий, удалённый репозиторий (GitHub/GitLab/любой git-remote), осознанные снимки (commit/push/pull) с сообщением, просмотр изменений и откат файла к прежней версии, разрешение конфликтов слияния в интерфейсе. Syncthing — непрерывная фоновая синхронизация файлов между устройствами пользователя без сервера; приложение распознаёт папку Syncthing (каталог .stfolder), показывает состояние синхронизации, находит конфликтные копии Syncthing (*.sync-conflict-*) и помогает их разрешить. Совместная работа: служебный каталог git не должен синхронизироваться через Syncthing (приложение предлагает/создаёт правила исключения .stignore), Syncthing отвечает за быструю доставку файлов между устройствами, git — за историю и резервную копию на удалённом сервере; конфликтные копии Syncthing можно сравнить с версией из истории git; одно устройство может быть назначено ответственным за автоматические коммиты, чтобы не плодить расходящиеся истории. Пример реального vault — /home/apokryf/notes: это папка Syncthing без git-репозитория. Синхронизация должна работать офлайн-первым образом: заметки всегда редактируются локально, сбой сети не мешает работе. Секреты доступа (токены, ключи) не хранятся в файлах vault. Поведение на web, desktop и Android описывается с учётом того, что не каждая оболочка может запускать git или Syncthing."

## Clarifications

### Session 2026-10-03

- Q: Как git и Syncthing делят работу, когда vault на нескольких устройствах? → A: Модель
  «хранитель истории». Syncthing доставляет файлы, служебный каталог истории из доставки
  исключён; снимки и обмен с сервером делает одно устройство-хранитель (в том числе
  автоматически), остальные смотрят историю и откатывают файлы через удалённый репозиторий.
  Отвергнуты: «своя история на каждом устройстве с общим сервером» (снимки одних и тех же
  правок дублируются, получение упирается в изменения, уже доставленные Syncthing) и «либо
  git, либо Syncthing» (нет взаимодополнения) — FR-029…FR-033, Assumptions.
- Q: Как входить в удалённый репозиторий в первой версии? → A: Токен поверх защищённого
  соединения на всех оболочках и ключи на рабочем столе. Вход через учётную запись
  GitHub/GitLab в браузерном окне — отдельная будущая фича (FR-014a, Вне скоупа).
- Q: Что делать с обменом с GitHub/GitLab в web-версии, если сервер не разрешает обращения из
  браузера? → A: Обмен идёт напрямую с серверами, которые это разрешают, или через адрес
  посредника, который пользователь указывает сам. Собственного посредника у Typsidian нет
  (FR-037).
- Q: Читает ли приложение живое состояние Syncthing или работает только с файлами? → A: И то
  и другое: файлы (маркер, правила исключения, конфликтные копии) везде, а состояние папки — с
  разрешения пользователя там, где Syncthing локально доступен; хранитель с доступным
  состоянием откладывает автоснимок до окончания доставки (FR-022, FR-022a, FR-031).

## Термины

- **История** — журнал снимков содержимого vault, который ведёт система контроля версий
  (git). Хранится внутри папки заметок в служебном каталоге истории и читается любыми
  стандартными инструментами без Typsidian.
- **Снимок** — зафиксированное состояние набора файлов vault с сообщением, автором и
  временем (commit).
- **Удалённый репозиторий** — копия истории на сервере (GitHub, GitLab, собственный
  сервер), с которой история обменивается снимками: «отправить» (push) и «получить»
  (pull).
- **Доставка между устройствами** — непрерывная фоновая синхронизация файлов папки между
  устройствами пользователя без сервера, которую выполняет Syncthing — отдельная программа,
  которой Typsidian не управляет и которую не устанавливает.
- **Конфликтная копия** — файл, который Syncthing создаёт рядом с оригиналом, когда один и
  тот же файл изменён на двух устройствах одновременно; в имени есть метка
  `sync-conflict`, дата и идентификатор устройства.
- **Хранитель истории** — устройство, назначенное пользователем единственным, которое
  делает снимки и отправляет их в удалённый репозиторий, когда vault одновременно
  доставляется Syncthing.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Включить историю и делать снимки (Priority: P1)

Пользователь открывает vault, у которого нет истории (например, `/home/apokryf/notes`), и
включает её из приложения. Дальше в любой момент видит, какие файлы изменились с последнего
снимка, и делает снимок с сообщением — целиком или только выбранных файлов. Если в папке
уже есть история, созданная вне Typsidian, приложение подхватывает её как есть. Всё
работает без сети.

**Why this priority**: История — основа всего остального: без неё нет ни отката, ни
удалённой копии, ни сравнения конфликтных копий с общей версией. И она полезна сама по
себе, даже на одном устройстве без сети.

**Independent Test**: Открыть vault без истории, включить её, изменить две заметки,
увидеть их в списке изменений, сделать снимок одной из них с сообщением, убедиться, что
стандартный инструмент git вне приложения видит этот снимок и одно оставшееся изменение.

**Acceptance Scenarios**:

1. **Given** vault без истории, **When** пользователь включает историю, **Then** система
   создаёт историю, показывает предлагаемые правила исключения (производные кэши, служебные
   файлы устройства, конфликтные копии) и после подтверждения делает первый снимок всех
   заметок.
2. **Given** в папке уже есть история, созданная вне приложения, **When** пользователь
   открывает vault, **Then** приложение показывает её состояние (ветка, число
   неснятых изменений) и ничего в ней не меняет без действия пользователя.
3. **Given** история включена и изменены файлы, **When** пользователь открывает панель
   синхронизации, **Then** видит список изменённых, новых и удалённых файлов и может
   открыть сравнение для каждого.
4. **Given** список изменений, **When** пользователь выбирает часть файлов, вводит
   сообщение и делает снимок, **Then** в снимок попадают только выбранные файлы, остальные
   остаются в списке изменений.
5. **Given** нет сети, **When** пользователь делает снимок, **Then** снимок создаётся так
   же, как с сетью.
6. **Given** в редакторе есть несохранённые правки, **When** пользователь делает снимок,
   **Then** правки сначала сохраняются на диск, и в снимок попадает то, что пользователь
   видит.

### User Story 2 - История заметки и откат к прежней версии (Priority: P1)

Пользователь открывает историю текущей заметки: список снимков, где она менялась, с датой,
автором и сообщением. Выбирает снимок — видит, чем та версия отличается от текущей, и может
вернуть заметку к ней целиком. Откат — обычное изменение файла: его можно отменить и
он сам попадает в список изменений.

**Why this priority**: «Вернуть, как было вчера» — главная причина, по которой люди
включают историю. Без просмотра и отката история — невидимый архив.

**Independent Test**: Сделать три снимка с разным содержимым заметки, открыть её историю,
сравнить первую версию с текущей, откатить к первой — содержимое совпадает с первой
версией, в списке изменений заметка отмечена изменённой.

**Acceptance Scenarios**:

1. **Given** заметка менялась в нескольких снимках, **When** пользователь открывает её
   историю, **Then** видит снимки, затрагивающие эту заметку, от новых к старым, включая
   снимки, сделанные до её переименования.
2. **Given** выбран снимок, **When** пользователь открывает сравнение, **Then** видит
   построчную разницу между версией в снимке и текущим содержимым.
3. **Given** выбран снимок, **When** пользователь откатывает заметку, **Then** содержимое
   заметки заменяется версией из снимка, открытый редактор и предпросмотр показывают её, а
   действие можно отменить обычной отменой.
4. **Given** заметка удалена, **When** пользователь открывает историю vault и находит
   снимок, где она была, **Then** может восстановить её на прежнее место.

### User Story 3 - Удалённый репозиторий: резервная копия и обмен (Priority: P1)

Пользователь подключает удалённый репозиторий (GitHub, GitLab или любой другой сервер) к
существующему vault либо создаёт новый vault, скачав его из удалённого репозитория. Затем
отправляет снимки на сервер и получает оттуда чужие — как в синхронизации с GitHub в
typst.app. Если сети нет, отправка откладывается и не мешает работе. Если на сервере и
локально изменён один и тот же фрагмент, пользователь разрешает конфликт прямо в
приложении.

**Why this priority**: Удалённая копия — это и резервная копия, и способ работать с vault
на устройстве, где нет Syncthing (например, в браузере), и способ поделиться заметками.

**Independent Test**: Подключить пустой удалённый репозиторий, отправить снимки, скачать
этот репозиторий как новый vault в другую папку, изменить в обоих одну строку по-разному,
отправить из одного, получить в другом — приложение показывает конфликт и позволяет выбрать
или совместить версии; после разрешения отправка проходит.

**Acceptance Scenarios**:

1. **Given** vault с историей, **When** пользователь указывает адрес удалённого
   репозитория и данные доступа, **Then** система проверяет доступ и сообщает, удался ли
   он, не сохраняя данные доступа в файлах vault.
2. **Given** подключённый удалённый репозиторий, **When** пользователь выполняет
   «отправить», **Then** все локальные снимки оказываются на сервере, а панель показывает,
   что локальная история и удалённая совпадают.
3. **Given** на сервере есть снимки, которых нет локально, **When** пользователь выполняет
   «получить» и локальных пересечений нет, **Then** файлы vault обновляются, открытые
   заметки обновляются так же, как при внешнем изменении файла (001 §FR про внешние
   изменения).
4. **Given** локально и на сервере изменён один и тот же фрагмент, **When** пользователь
   выполняет «получить», **Then** система показывает список конфликтующих файлов и для
   каждого — обе версии и общую исходную, позволяя выбрать одну, совместить вручную или
   отменить получение целиком, вернув vault к состоянию до него.
5. **Given** нет сети или сервер недоступен, **When** пользователь выполняет «отправить»
   или «получить», **Then** система за ограниченное время сообщает, что сервер недоступен,
   оставляет все локальные данные нетронутыми, а локальные снимки — готовыми к отправке.
6. **Given** у пользователя есть удалённый репозиторий, **When** он создаёт vault из
   удалённого репозитория, **Then** система скачивает историю в выбранную пустую папку и
   открывает её как vault.
7. **Given** в настройках vault включена автоматическая отправка, **When** сделан снимок и
   есть сеть, **Then** снимок отправляется без отдельного действия; при ошибке пользователь
   видит её в индикаторе синхронизации, а не во всплывающем окне, мешающем работе.

### User Story 4 - Syncthing: состояние и конфликтные копии (Priority: P2)

Пользователь открывает vault, который доставляет между устройствами Syncthing (как
`/home/apokryf/notes`). Приложение узнаёт об этом и показывает в индикаторе синхронизации:
папка обслуживается Syncthing и, если Syncthing на этом устройстве доступен, — актуальна
она, идёт синхронизация, приостановлена или есть ошибки. Конфликтные копии, созданные
Syncthing, не засоряют дерево заметок, поиск и граф: приложение собирает их в список
конфликтов и помогает разрешить каждый.

**Why this priority**: Syncthing уже используется на практике, а конфликтные копии сейчас
выглядят как самостоятельные заметки, дублируют ссылки и копятся незаметно.

**Independent Test**: Положить в vault файл с именем конфликтной копии существующей
заметки — он не появляется в дереве как обычная заметка, появляется в списке конфликтов;
разрешить конфликт, выбрав одну версию, — конфликтная копия исчезает, заметка содержит
выбранную версию.

**Acceptance Scenarios**:

1. **Given** в корне vault есть маркер папки Syncthing, **When** пользователь открывает
   vault, **Then** индикатор синхронизации показывает, что папка доставляется Syncthing.
2. **Given** Syncthing на этом устройстве запущен и пользователь разрешил приложению
   читать его состояние, **When** открыт vault, **Then** индикатор показывает состояние
   папки (актуальна / синхронизация с процентом / приостановлена / ошибка) и число
   подключённых устройств и обновляет его без действий пользователя.
3. **Given** Syncthing недоступен или доступ к нему не настроен, **When** открыт vault,
   **Then** индикатор показывает, что состояние неизвестно, и работа с заметками не
   страдает.
4. **Given** в vault появилась конфликтная копия заметки, **When** приложение её
   обнаруживает, **Then** копия не показывается в дереве заметок, не индексируется для
   поиска и графа, а в списке конфликтов появляется запись с именем заметки, временем и
   устройством-источником.
5. **Given** запись в списке конфликтов, **When** пользователь открывает её, **Then** видит
   сравнение текущей версии и конфликтной копии и может оставить текущую, взять копию или
   совместить вручную; после решения конфликтная копия удаляется.
6. **Given** конфликтная копия есть у файла, не являющегося заметкой (доска, вложение),
   **When** пользователь открывает запись, **Then** может выбрать одну из версий целиком.

### User Story 5 - Git и Syncthing вместе (Priority: P2)

У пользователя несколько устройств, файлы между ними доставляет Syncthing, а историю и
резервную копию на сервере ведёт git. Приложение настраивает их так, чтобы они не мешали
друг другу: служебный каталог истории и производные кэши не доставляются Syncthing (иначе
история портится, а кэши порождают бесконечные конфликты). Одно устройство пользователь
назначает хранителем истории: только оно делает снимки и обменивается с сервером, при
желании — автоматически. Остальные устройства просто получают файлы через Syncthing, а
историю могут смотреть и откатывать заметки — откат доставляется Syncthing обратно и
попадает в следующий снимок хранителя. При конфликтной копии Syncthing приложение
показывает не две, а три версии — две спорные и последнюю общую из истории, — что позволяет
совместить правки, а не выбирать одну.

**Why this priority**: Это и есть то «дополняют друг друга», ради чего фича: Syncthing
доставляет мгновенно и без сервера, git даёт историю, откат и резервную копию. Без
согласования они ломают друг друга: Syncthing разносит частично записанный служебный
каталог истории, а несколько устройств, делающих снимки одних и тех же файлов, плодят
расходящиеся истории.

**Independent Test**: На vault с маркером Syncthing включить историю — приложение
предлагает правила исключения для Syncthing и после подтверждения записывает их, не трогая
уже существующие правила пользователя. Назначить устройство хранителем, включить
автоснимки — после правки и паузы появляется снимок. На втором устройстве (второй экземпляр
с другим идентификатором устройства) снимки не делаются, а действие «сделать снимок»
объясняет, кто хранитель.

**Acceptance Scenarios**:

1. **Given** vault доставляется Syncthing и у него включается история, **When** система
   готовит историю, **Then** до создания истории предлагает добавить в правила исключения
   Syncthing служебный каталог истории и производные кэши приложения, показывая точный
   текст добавляемых правил; существующие правила пользователя сохраняются.
2. **Given** в правилах исключения Syncthing нет служебного каталога истории, а история в
   vault есть, **When** пользователь открывает vault, **Then** приложение предупреждает,
   что история может испортиться при доставке, и предлагает исправить правила в одно
   действие.
3. **Given** vault доставляется Syncthing и имеет историю, **When** пользователь назначает
   это устройство хранителем истории, **Then** назначение записывается в vault и через
   Syncthing становится видно на остальных устройствах.
4. **Given** устройство — хранитель и включены автоснимки, **When** пользователь (или
   Syncthing с другого устройства) изменил файлы и прошла пауза без новых изменений,
   **Then** система делает снимок с автоматическим сообщением, перечисляющим изменённые
   заметки, и, если включена автоматическая отправка, отправляет его.
5. **Given** устройство — не хранитель, **When** пользователь пытается сделать снимок или
   отправить, **Then** система объясняет, какое устройство хранитель, и позволяет либо
   отменить, либо сделать это устройство хранителем.
6. **Given** устройство — не хранитель и служебного каталога истории на нём нет, **When**
   пользователь открывает историю заметки, **Then** система показывает историю из
   удалённого репозитория (если он доступен) и позволяет откатить заметку; откатанный файл
   доставляется Syncthing, а хранитель включает его в свой следующий снимок.
7. **Given** конфликтная копия Syncthing у заметки, которая есть в истории, **When**
   пользователь открывает конфликт, **Then** видит три версии — текущую, конфликтную копию
   и последнюю версию из истории, общую для обеих, — и может совместить правки обеих
   сторон относительно общей версии.
8. **Given** хранитель получил с сервера снимки (например, сделанные в браузере), **When**
   файлы vault обновились, **Then** Syncthing доставляет их на остальные устройства так же,
   как правки пользователя.

### User Story 6 - Синхронизация в каждой оболочке (Priority: P3)

На каждой оболочке пользователь получает столько синхронизации, сколько эта оболочка
позволяет, и ясно видит, чего нет и почему. Рабочий стол — всё. Android — история,
удалённый репозиторий и распознавание Syncthing (сам Syncthing — отдельное приложение).
Браузер — история и снимки в открытой папке, а обмен с удалённым репозиторием — с
серверами, которые разрешают обращения из браузера, или через посредника, адрес которого
пользователь указал сам.

**Why this priority**: Без явной деградации пользователь web-версии увидит неработающие
кнопки и решит, что синхронизация сломана.

**Independent Test**: Открыть один и тот же vault в каждой оболочке: недоступные действия
не спрятаны молча, а отмечены с объяснением; доступные работают одинаково.

**Acceptance Scenarios**:

1. **Given** оболочка не может читать состояние Syncthing, **When** пользователь открывает
   индикатор, **Then** видит, что папка обслуживается Syncthing, и объяснение, почему
   подробное состояние недоступно.
2. **Given** браузер, удалённый сервер, не разрешающий обращения из браузера, и посредник
   не указан, **When** пользователь пытается отправить или получить, **Then** система
   сообщает об этом ограничении и предлагает указать посредника, не теряя локальных
   снимков; **Given** посредник указан, **Then** обмен проходит через него.
3. **Given** любая оболочка, **When** пользователь делает снимок, смотрит историю или
   разрешает конфликт, **Then** результат одинаков и читается стандартными инструментами
   git на любой другой оболочке.

### Edge Cases

- **Vault — часть более крупного репозитория** (папка заметок лежит внутри чужой истории).
  Приложение показывает, что история принадлежит внешней папке, и не включает свою поверх;
  снимки затрагивают только файлы внутри vault.
- **Состояние истории посреди операции** (незавершённое слияние, перебазирование,
  отделённая ветка), оставленное внешним инструментом. Приложение не делает снимков и не
  получает изменений, пока пользователь не завершит или не отменит операцию; показывает,
  что именно не завершено.
- **Огромные или двоичные файлы** (PDF, картинки, доски). Снимок их включает, сравнение
  показывает «двоичный файл изменён» с размерами вместо построчной разницы.
- **Сеть пропала посреди отправки или получения.** Операция завершается сообщением об
  ошибке за ограниченное время; vault остаётся в состоянии до операции или после неё
  целиком, а не посередине.
- **Отправка отклонена сервером, потому что там есть новые снимки.** Система предлагает
  сначала получить, а не перезаписывать удалённую историю. Принудительной перезаписи
  удалённой истории в интерфейсе нет.
- **Истёк или отозван токен доступа.** Сообщение называет причину и ведёт к замене данных
  доступа; локальные снимки не теряются.
- **Два устройства считают себя хранителями** (назначения изменены одновременно и
  Syncthing создал конфликтную копию файла назначения). Оба устройства перестают делать
  автоснимки и просят пользователя выбрать хранителя заново.
- **Хранитель выключен надолго.** Остальные устройства продолжают работать, правки
  доставляются Syncthing; индикатор показывает, когда хранитель делал последний снимок.
- **Конфликтная копия конфликтной копии** или копия, исходного файла для которой уже нет.
  Запись в списке конфликтов предлагает сохранить копию как обычный файл или удалить её.
- **Пользователь сам удалил служебный каталог истории.** Приложение показывает, что
  истории больше нет, и предлагает либо создать новую, либо скачать её заново из
  удалённого репозитория.
- **Массовая операция**: первый снимок большого vault, получение тысяч изменённых файлов,
  отказ от получения. Показывается прогресс, остальное приложение работает, отмена
  оставляет vault в состоянии до операции (принцип X).
- **Редактируемая заметка изменена получением с сервера.** Работает тот же выбор, что и
  для любого внешнего изменения (001): оставить свою версию, принять внешнюю, сравнить.

## Requirements *(mandatory)*

### Functional Requirements

**История и снимки**

- **FR-001**: Пользователь MUST иметь возможность включить историю для vault без истории.
  Перед созданием система MUST показать предлагаемые правила исключения и дождаться
  подтверждения.
- **FR-002**: История MUST храниться внутри папки заметок в формате, который читают и
  изменяют стандартные инструменты git без Typsidian (принцип VI). История, созданная вне
  приложения, MUST подхватываться без преобразования.
- **FR-003**: Правила исключения истории по умолчанию MUST исключать производные кэши
  приложения, состояние, принадлежащее устройству, и конфликтные копии Syncthing, и MUST
  включать заметки, доски, вложения и настройки уровня vault.
- **FR-004**: Система MUST показывать список изменений с последнего снимка: новые,
  изменённые, удалённые и переименованные файлы, — и сравнение для каждого.
- **FR-005**: Пользователь MUST иметь возможность сделать снимок всех изменений или
  выбранных файлов с сообщением. Пустое сообщение MUST заменяться автоматическим,
  перечисляющим изменённые заметки.
- **FR-006**: Перед снимком система MUST сохранять на диск несохранённые правки открытых
  заметок, попадающих в снимок.
- **FR-007**: Автор снимка MUST браться из настроек устройства (имя и адрес), а если их
  нет — из глобальных настроек git устройства; если нет и их, система MUST попросить
  указать автора один раз.
- **FR-008**: Все операции с локальной историей (включение, снимок, просмотр, сравнение,
  откат) MUST работать без сети.

**Просмотр и откат**

- **FR-009**: Пользователь MUST иметь возможность открыть историю текущей заметки — снимки,
  её затрагивающие, с учётом переименований — и историю всего vault.
- **FR-010**: Для любого снимка MUST показываться построчная разница версии файла в нём с
  текущей версией и с предыдущим снимком.
- **FR-011**: Пользователь MUST иметь возможность вернуть файл к версии из снимка и
  восстановить удалённый файл. Откат MUST быть обычным изменением файла: он отменяется
  отменой редактора и не переписывает историю.
- **FR-012**: Интерфейс MUST NOT предлагать действий, переписывающих или удаляющих уже
  сделанные снимки.

**Удалённый репозиторий**

- **FR-013**: Пользователь MUST иметь возможность подключить к vault удалённый репозиторий
  по адресу, сменить его и отключить, а также создать новый vault, скачав удалённый
  репозиторий в пустую папку.
- **FR-014**: Данные доступа (токены, ключи, пароли) MUST храниться в защищённом хранилище
  устройства и MUST NOT записываться ни в один файл внутри vault, в сообщения об ошибках и
  в журналы.
- **FR-014a**: Способы доступа к удалённому репозиторию: токен поверх защищённого
  соединения — во всех оболочках; ключи — на рабочем столе (с использованием ключей и
  агента, уже настроенных на устройстве). Адрес удалённого репозитория, требующий
  недоступного в оболочке способа, MUST отклоняться при подключении с объяснением.
- **FR-015**: Пользователь MUST иметь возможность выполнить «отправить» и «получить»; панель
  MUST показывать, сколько снимков не отправлено и сколько не получено (по последним
  известным сведениям, с временем их обновления).
- **FR-016**: Если получение пересекается с локальными изменениями, система MUST показать
  каждый конфликтующий файл с тремя версиями (своя, удалённая, общая исходная) и дать
  выбрать одну, совместить вручную или отменить получение целиком с возвратом vault к
  состоянию до него.
- **FR-017**: Пока есть неразрешённые конфликты получения, система MUST NOT делать снимки
  и отправлять, а заметки с конфликтом MUST быть отмечены в дереве.
- **FR-018**: Если сервер отклоняет отправку из-за новых удалённых снимков, система MUST
  предложить сначала получить. Принудительная перезапись удалённой истории MUST NOT
  предлагаться.
- **FR-019**: Пользователь MUST иметь возможность включить для vault автоматическую
  отправку после снимка и автоматическое получение при открытии vault и с заданным
  интервалом. По умолчанию оба выключены.
- **FR-020**: Сетевые операции MUST завершаться сообщением за ограниченное время при
  отсутствии сети или ответа сервера, MUST NOT блокировать редактирование и MUST оставлять
  vault в состоянии целиком до или целиком после операции (принципы VII, X).

**Syncthing**

- **FR-021**: Система MUST распознавать, что папка vault доставляется Syncthing, по
  маркеру папки Syncthing в её корне, без связи с самим Syncthing.
- **FR-022**: Если на устройстве доступен Syncthing и пользователь разрешил приложению
  читать его состояние, индикатор MUST показывать состояние этой папки (актуальна,
  синхронизация с прогрессом, приостановлена, ошибка) и число подключённых устройств и
  обновляться без действий пользователя. Данные доступа к Syncthing подчиняются FR-014.
- **FR-022a**: На рабочем столе система SHOULD находить параметры локального доступа к
  Syncthing этого пользователя сама и предлагать подключиться к ним одним подтверждением;
  ручной ввод адреса и ключа MUST оставаться доступным. Чтение состояния MUST быть только
  чтением (FR-023).
- **FR-023**: Система MUST NOT устанавливать, запускать, останавливать Syncthing, менять
  список его устройств и папок. Единственное, что она пишет от имени Syncthing, — файл
  правил исключения в корне vault, и только с подтверждения пользователя (FR-027).
- **FR-024**: Конфликтные копии Syncthing MUST NOT показываться в дереве как обычные
  заметки, MUST NOT индексироваться для поиска, ссылок и графа и MUST собираться в список
  конфликтов с именем исходного файла, временем и устройством-источником.
- **FR-025**: Для каждой конфликтной копии пользователь MUST иметь возможность сравнить её
  с текущей версией и оставить текущую, взять копию, совместить вручную или сохранить
  копию как отдельный файл. После решения копия MUST удаляться (кроме случая «сохранить
  как отдельный файл»).

**Совместная работа git и Syncthing**

- **FR-026**: Если vault доставляется Syncthing, система MUST проверять, исключены ли из
  доставки служебный каталог истории и производные кэши приложения, и при их отсутствии
  предупреждать пользователя.
- **FR-027**: Система MUST предлагать дописать недостающие правила исключения Syncthing в
  одно действие, показав точный текст. Существующие правила пользователя MUST сохраняться
  без изменений, повторное применение MUST NOT дублировать правила.
- **FR-028**: Включение истории в vault, доставляемом Syncthing, MUST начинаться с шага
  FR-027 — история MUST NOT создаваться раньше, чем пользователь согласился на правила
  исключения или явно от них отказался.
- **FR-029**: Пользователь MUST иметь возможность назначить текущее устройство хранителем
  истории vault. Назначение MUST храниться в vault (доставляется вместе с ним) и
  показываться на всех устройствах с именем устройства-хранителя.
- **FR-030**: Пока у vault есть хранитель, устройство, не являющееся им, MUST NOT делать
  снимки и обмениваться с удалённым репозиторием без явного подтверждения пользователя,
  объясняющего последствия; автоснимки на нём MUST NOT выполняться.
- **FR-031**: На хранителе пользователь MUST иметь возможность включить автоснимки: снимок
  после паузы без изменений файлов vault (пауза настраивается, по умолчанию 5 минут) с
  автоматическим сообщением. Изменения, доставленные Syncthing, MUST учитываться так же,
  как сделанные на этом устройстве. Если состояние Syncthing читается и папка ещё
  синхронизируется, автоснимок MUST откладываться до её актуальности, чтобы не снимать
  наполовину доставленные изменения.
- **FR-032**: Если устройств-хранителей оказалось больше одного или файл назначения в
  конфликте, автоснимки MUST останавливаться на всех устройствах до повторного выбора.
- **FR-033**: Устройство без локального служебного каталога истории MUST иметь
  возможность смотреть историю заметок и откатывать их, используя удалённый репозиторий,
  если он подключён к vault и доступен; откат записывается в файл vault как обычное
  изменение.
- **FR-034**: Для конфликтной копии Syncthing у файла, присутствующего в истории, система
  MUST показывать третью версию — последнюю из истории, общую для обеих, — и предлагать
  автоматическое совмещение непересекающихся правок с показом результата до применения.
- **FR-035**: Индикатор синхронизации MUST сводить в одно место: доставляется ли vault
  Syncthing и его состояние, состояние истории (неснятые изменения, неотправленные и
  неполученные снимки, конфликты), кто хранитель и когда был последний снимок.

**Оболочки**

- **FR-036**: Действия, недоступные в текущей оболочке, MUST быть видимы и отмечены с
  объяснением причины, а не скрыты молча.
- **FR-037**: Локальная история, снимки, просмотр, откат и разрешение конфликтов MUST
  работать во всех трёх оболочках одинаково. Обмен с удалённым репозиторием MUST работать
  на рабочем столе и Android. В браузере — напрямую с серверами, разрешающими обращение из
  браузера, либо через адрес посредника, который пользователь указывает в настройках vault
  на этом устройстве; без посредника для остальных серверов — понятный отказ с объяснением,
  что такое посредник. Typsidian MUST NOT поставлять и подставлять посредника по умолчанию:
  содержимое заметок уходит только туда, куда указал пользователь.
- **FR-038**: Отключение синхронизации (истории, удалённого репозитория, чтения состояния
  Syncthing) MUST оставлять приложение полностью работоспособным и MUST NOT удалять
  историю или файлы vault (принцип VI).
- **FR-039**: Все тексты интерфейса фичи MUST идти через локализацию (010), включая
  сообщения об ошибках сети, доступа и конфликтов.

### Key Entities

- **История vault** — журнал снимков, ветка, состояние «неснятых изменений», связь с
  удалённым репозиторием. Принадлежит папке заметок.
- **Снимок** — набор файлов, сообщение, автор, время, предок(и).
- **Изменение** — файл, вид изменения (новый, изменён, удалён, переименован), версии до и
  после.
- **Удалённый репозиторий** — адрес, имя, счётчики неотправленного/неполученного, время
  последнего обмена, ссылка на данные доступа в хранилище устройства (сами данные — вне
  vault).
- **Конфликт** — файл и спорящие версии: для получения — своя, удалённая, общая; для
  Syncthing — текущая, конфликтная копия, общая из истории (если есть), время и
  устройство-источник.
- **Правила исключения** — для истории и для Syncthing; часть, предлагаемая приложением, и
  часть, написанная пользователем.
- **Хранитель истории** — устройство (идентификатор, имя), время назначения, время
  последнего снимка; хранится в vault.
- **Состояние Syncthing для папки** — распознана ли, доступна ли связь с Syncthing,
  состояние, прогресс, число устройств.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь включает историю для существующего vault и делает первый снимок
  меньше чем за 1 минуту, не выходя из приложения и без командной строки.
- **SC-002**: Список изменений и состояние истории для vault из 5 000 заметок появляются
  меньше чем за 2 секунды после открытия панели.
- **SC-003**: Откат заметки к версии недельной давности занимает не больше 4 действий от
  открытой заметки.
- **SC-004**: При отсутствии сети любая операция обмена с сервером завершается сообщением
  не позже чем через 30 секунд; редактирование в это время не прерывается ни на одном шаге.
- **SC-005**: В vault, доставляемом Syncthing, после включения истории служебный каталог
  истории и кэши не доставляются на другие устройства в 100% случаев, и за неделю
  обычной работы с двух устройств не возникает ни одной конфликтной копии служебных файлов.
- **SC-006**: Все конфликтные копии Syncthing в vault видны в списке конфликтов, и ни одна
  не попадает в дерево заметок, поиск или граф.
- **SC-007**: Конфликт, в котором две стороны правили разные абзацы одной заметки,
  разрешается совмещением без ручного редактирования текста в 100% случаев, когда у файла
  есть общая версия в истории.
- **SC-008**: Любой снимок, сделанный в Typsidian, читается и отображается стандартными
  инструментами git без ошибок и предупреждений; ни один файл vault не содержит данных
  доступа.

## Assumptions

- Пользователь сам устанавливает и настраивает Syncthing (устройства, папки); Typsidian
  только распознаёт папку, читает состояние с разрешения пользователя и ведёт правила
  исключения. Парное подключение устройств Syncthing — вне скоупа.
- Чтение состояния Syncthing возможно только там, где Syncthing работает на том же
  устройстве и предоставляет локальный доступ; на Android и в браузере, где это
  невозможно, действует FR-022 в части «состояние неизвестно».
- Модель «хранитель истории» выбрана вместо «у каждого устройства своя история»
  (Clarifications): служебный каталог истории не доставляется Syncthing, поэтому на одном
  устройстве (хранителе) история живёт локально, а остальные получают её через удалённый
  репозиторий (FR-033). Хранитель необязателен: vault без Syncthing работает с историей
  на каждом устройстве как обычный репозиторий с отправкой и получением.
- Одна ветка: интерфейс работает с текущей веткой и не предлагает создавать, переключать и
  сливать ветки. Ветки, созданные вне приложения, не ломают его: показывается текущая.
- Способы доступа к серверу — FR-014a; вход через учётную запись GitHub/GitLab в
  браузерном окне (как в typst.app) в эту фичу не входит.
- Удалённый репозиторий — обычный git-сервер; специальных возможностей конкретных хостингов
  (запросы на слияние, задачи, создание репозитория из приложения) фича не использует.
- Служебное место vault (006) содержит и общие для устройств настройки, и производные кэши;
  правила исключения отделяют вторые от первых.
- Синхронизация настроек устройства между устройствами по-прежнему вне скоупа (004).

## Вне скоупа

- Собственный сервер синхронизации Typsidian, аккаунты, облако.
- Совместное редактирование одной заметки в реальном времени.
- Управление ветками, запросами на слияние, тегами.
- Установка, запуск и настройка самого Syncthing, сопряжение устройств.
- Шифрование содержимого удалённого репозитория.
- Вход через учётную запись GitHub/GitLab в браузерном окне (OAuth) — кандидат в
  отдельную фичу.
- Собственный посредник Typsidian для обмена из браузера.
