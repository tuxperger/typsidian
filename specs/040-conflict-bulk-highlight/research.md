# Research: 040 — массовое разрешение и подсветка конфликтов

## §1. Откуда берётся происхождение участков

- **Decision**: общий проход `merge3` выносится во внутреннюю функцию, которая отдаёт
  `Vec<Segment>`: `Agreed { text, origin }` и `Disputed { base, ours, theirs }`. Соседние
  `Agreed` склеиваются только при равном `origin`. `merge3` строит из участков прежний
  `MergeResult` (без изменения его формы), `merge_view` — `MergeView`.
- **Rationale**: FR-006. Подсветка и спорные участки получаются одним проходом и не могут
  разойтись. Форма `MergeResult` и его потребители (резервный выбор «везде своё», тесты 011)
  не меняются.
- **Alternatives**: поле `origin` в `Hunk::Same` меняет сериализацию и ломает склейку
  участков в `MergeResult`. Второй независимый diff для подсветки может разойтись с
  совмещением на соседних правках.

## §2. Пометки строк в колонках

- **Decision**: колонка своей версии помечает строки, которые изменила своя сторона
  (`Ours`), колонка их версии — изменённые их стороной (`Theirs`). Колонка общей версии
  помечает строки, которые тронула только своя сторона (`Ours`), только их (`Theirs`) или
  обе (`Both`). Без общей версии своя и их колонки сравниваются друг с другом: строки,
  которых нет в другой версии, получают пометку своей стороны. Удаление видно по общей
  колонке, у вставки в пустое место пометка в колонке стороны.
- **Rationale**: так нарисовано в макете (1a). Одинаковая правка обеих сторон в колонке
  стороны помечается её цветом; `Both` в результате и в общей колонке говорит о том же.
- **Alternatives**: помечать в колонке стороны и «чужие» правки (по смыслу diff с другой
  стороной) — колонка перестаёт отвечать на вопрос «что сделала эта сторона».

## §3. Сборка результата и ручная правка

- **Decision**: чистая функция `merge_annotate(segments, picks, edited) -> Annotated
  { text, lines }`. Без правки собирает текст из участков и выбранных сторон: `Pick::Both`
  ставит сначала свою часть, затем их; строки получают `Ours`/`Theirs` по половине и
  `origin` для общих участков. С правкой сравнивает собранный текст и правленый построчно
  (Myers, как `merge3`). Равные строки сохраняют пометку, вставленные и заменённые получают
  `Manual`. UI вызывает её при смене выбора сразу, а при наборе текста — через 250 мс после
  последнего нажатия.
- **Rationale**: принцип I. Сборка, которая сейчас живёт в `MergeEditor.tsx`, и diff правки
  — логика, а не отрисовка. Задержка не даёт гонять сравнение на каждое нажатие через IPC
  или HTTP (серверный режим).
- **Alternatives**: оставить сборку в UI, а в ядро отдавать только diff — сборка
  останется второй реализацией. Отдавать ядру только правку без выбора — тогда ядру нужен
  был бы контекст сессии, а функция чистая.

## §4. Пачка решений

- **Decision**: `Session::resolve_many(backend, ctx, ids, BulkResolution) -> BulkReport`.
  Конфликты сначала читаются один раз через `conflicts()`. Дальше по очереди
  `resolve(id, …)`: `KeepOurs`, `TakeTheirs` или `Merged { text }` для `AcceptClean`, где
  `auto_merge` чистый. Нечистые и двоичные при `AcceptClean` попадают в `skipped`. Сбой
  одного файла записывается в `failed` с причиной `SyncError` и не прерывает остальные.
  Перед каждым файлом проверяется отмена (`fresh_cancel`); ход пишется в `ProgressSink`
  как `Operation::Resolve`. После отмены необработанные идут в `skipped`, `cancelled =
  true`. Последний решённый конфликт получения завершает получение внутри `resolve_pull`,
  как сейчас.
- **Rationale**: FR-013 — «тот же результат, что одиночное решение»: путь буквально тот же.
  Принцип X: ход и отмена между целыми файлами; частично записанных файлов нет, потому что
  каждый `resolve` пишет файл целиком.
- **Alternatives**: цикл `resolve` в UI — логика пачки и подсчёт отчёта оказались бы в UI
  (принцип I), а в серверном режиме каждый файл ходил бы отдельным запросом.

## §5. Поле результата

- **Decision**: небольшой экземпляр CodeMirror (`@codemirror/view` + `state`, без языка
  Typst) с `Decoration.line` по пометкам и колонкой-маркером слева (`<`, `>`, `±`, `✎`).
  Пометки, пришедшие от ядра для старой версии текста, применяются к строкам, которые в
  тексте есть; лишние строки до ответа ядра считаются `Manual`.
- **Rationale**: уточнение 2 (редактирование прямо в поле с подсветкой). `textarea` не
  умеет фон по строкам. CodeMirror уже в зависимостях.
- **Alternatives**: наложение `pre` под прозрачный `textarea` — ломается на переносе
  длинных строк и при прокрутке.

## §6. Цвета

- **Decision**: роли в `app.css`: `--ts-merge-ours` и `-bg` — смесь `--blue-600`/`--blue-100`;
  `--ts-merge-theirs` и `-bg` — `--amber-600`/`--amber-100`; `--ts-merge-manual` —
  `--orange-400`; «обе» — градиент двух фонов. Те же смеси 600/100 одного семейства, что
  подсветка 024. Цвета заданы для тёмной поверхности: диалоги приложения тёмные в любой
  теме (`.ts-dialog` — `--steel-900`), поэтому в `[data-theme]` не переопределяются. Пара
  синий/янтарный различима при дейтеранопии и протанопии; маркер и легенда дублируют цвет
  (FR-005).
- **Rationale**: оранжевый в «Спецформе» — акцент и «выбрано», красный/зелёный — статусы и
  плохо различимы при дальтонизме.

## §7. Узкая ширина

- **Decision**: ниже 860px колонки версий показываются вкладками («Ваша», «Общая», «Их» /
  «Копия»), половины спорного участка встают одна под другую (макет 3). Вкладка
  «Результат» на телефоне не отдельная: поле результата идёт под участками, как на широком
  экране. В макете она есть, это намеренное упрощение.
- **Rationale**: результат и выбор участков должны быть видны вместе, иначе массовая
  кнопка меняет то, чего пользователь не видит.

## §8. Подтверждения

- **Decision**: подтверждения встроены в окно строкой над результатом (1b) или над списком
  (2b), без вложенных диалогов: системный `confirm` в части оболочек недоступен, а второй
  модальный слой поверх `.ts-dialog` в проекте нигде не используется.

## §9. Намеренные расхождения с макетом

- **Decision**: у спорного участка нет подписи «строка N» / «строки N–M» (макет 1a), а у
  строк половин участка нет номеров. Номер строки участка зависит от выбора в предыдущих
  участках, а его подсчёт в интерфейсе стал бы второй сборкой результата (принцип I).
  Участок узнаётся по номеру и по тексту обеих половин. Вкладки «Результат» на телефоне нет
  (§7).
- **Rationale**: принцип I важнее подписи; ядро могло бы отдавать номера, но для
  навигации хватает перехода «участок N из M».

## §10. Пределы после ревью безопасности

- **Decision**: построчное сравнение (Myers без срока, O((N+M)·D)) идёт только для
  версий не длиннее `LINE_LIMIT` = 10 000 строк и 2 МБ. Длиннее — `view: None` (выбор
  целиком), а правка результата сверх предела помечается `Manual` без сравнения. Пачка
  принимает не больше 10 000 уникальных id, повторы считаются один раз. Пачка строит список
  конфликтов без пометок строк. «Принять совмещённые» для копии Syncthing перечитывает
  оригинал и копию: если они изменились после построения списка, конфликт попадает в
  `skipped`. Сервер вычищает свои пути и из успешного отчёта `sync_resolve_many`.
- **Rationale**: `sync_merge_annotate` — первая серверная команда с квадратичным diff по
  тексту клиента. Без предела один запрос держал бы рабочий поток сервера. Срок (`deadline`)
  у `similar` опирается на `Instant`, которого нет на `wasm32-unknown-unknown`, поэтому
  предел задаётся размером (принцип II).
- **Alternatives**: `spawn_blocking` на сервере держит поток так же долго, только другой;
  предел нужен в любом случае.
