# Quickstart: проверка фичи Vault Service Layout

**Фича**: `006-vault-service-layout` | **Дата**: 2026-09-07

Как убедиться, что фича работает. Не инструкция по реализации — сценарии проверки со
ссылками на [contracts/](./contracts/) и [data-model.md](./data-model.md).

## Предусловия

Весь инструментарий существует только внутри dev-shell:

```bash
nix develop
```

Тестовый vault: `~/media/notes`. Слепок «до» пригодится для проверки SC-007:

```bash
find ~/media/notes -maxdepth 1 -name '.*' -o -maxdepth 1 -name '*.assets' | sort > /tmp/before.txt
```

## Автоматические проверки

Гейт принципа II — оба таргета, иначе фича не считается готовой:

```bash
cargo test -p typsidian-core
cargo test -p typsidian-core --target wasm32-unknown-unknown
cargo build -p typsidian-core --target wasm32-unknown-unknown
```

Гейт принципа IV. **Порядок существен**: типы границы порождаются из Rust, поэтому после правки
ядра нужны обе пересборки — иначе `ui` зелёный, а `apps/desktop` красный на устаревшем
`ui/dist`, и выглядит это как ошибка типов, которой нет:

```bash
pnpm build:wasm        # packages/core -> ui/src/wasm-core
pnpm -C ui build       # ui/src -> ui/dist
pnpm typecheck         # рекурсивно по всем пакетам
```

Ожидаемые новые наборы (по паре на единицу логики, принцип I):

| Набор | Что закрывает |
|-------|---------------|
| `placement_native.rs` / `placement_wasm.rs` | таблица из [asset-placement.md](./contracts/asset-placement.md) |
| `vault_settings_native.rs` / `vault_settings_wasm.rs` | слои, маршрутизация записи, испорченный файл |
| `packages_native.rs` / `packages_wasm.rs` | таблица из [package-resolve.md](./contracts/package-resolve.md) |

## Сценарий 1 — расположение вставок (US1, P1)

1. Настройки → Vault → расположение файлов вставок → **в корне папки заметок**.
2. Открыть заметку во вложенной папке, вставить доску.

Ожидается: рядом с заметкой не создано ничего; файл лежит в `~/media/notes/assets/<имя
заметки>/board-….svg`; в тексте заметки — `#image("../assets/<имя>/board-….svg")`; предпросмотр
показывает доску.

3. Вставить в ту же заметку вторую доску → второй файл рядом с первым, первый не перезаписан.
4. Переключить на **рядом с заметкой**, вставить третью → она ложится в `assets/` рядом с
   заметкой, а две прежние остались на месте и продолжают показываться (FR-007).
5. Отредактировать доску из шага 2 и обновить её вставку → переписан **тот же** файл в корневой
   `assets/`, новый по текущей политике не создан (FR-008).

## Сценарий 2 — разделы (US2, P2)

1. Правый клик по папке `Работа` в дереве → «Пометить как раздел». Пометка видна.
2. Политика → **в корне раздела**. Вставить доску в `Работа/Проекты/Идея.typ`.

Ожидается: `Работа/assets/Идея/board-….svg`.

3. Пометить ещё и `Работа/Проекты`, вставить снова → файл уходит в
   `Работа/Проекты/assets/…` (ближайший предок побеждает, FR-016).
4. Переименовать `Работа` из дерева → пометка едет за папкой, новые вставки продолжают
   попадать в тот же раздел (FR-018).
5. Заметка вне помеченных папок → вставка ложится в корень vault, ошибки нет (FR-006).
6. Перезапустить приложение → пометки на месте (FR-015).
7. Снять пометку с `Работа` → уже созданные файлы вставок остались на своих местах и
   продолжают показываться; переехала только точка, куда попадут новые (FR-017).

## Сценарий 3 — служебное место (US3, P2)

```bash
ls -a ~/media/notes
```

Ожидается: `.typsidian/` есть, `.typsidian-cache.sqlite` **исчез** (FR-021). Сравнение с
`/tmp/before.txt` показывает: в корне не появилось ничего, кроме `.typsidian/` и — при
соответствующей политике — `assets/` (SC-007).

```bash
ls -a ~/media/notes/.typsidian     # vault.json, cache.sqlite
```

Папки `preview/` там быть **не должно**: она зарезервирована в раскладке, но не создаётся
(research §2).

Проверка восстановимости (FR-023):

```bash
rm -rf ~/media/notes/.typsidian
```

Перезапустить приложение. Ожидается: vault открывается, дерево то же, все заметки, доски и
вставки на месте; приложение сообщает, что настройки уровня vault и локальные шаблоны утрачены
(FR-024), а не молча откатывается к умолчаниям.

Обратная проверка того же требования — **ложного сообщения быть не должно**. Открыть папку,
которую на этом устройстве ещё не открывали:

```bash
mkdir -p /tmp/vault-проба && touch /tmp/vault-проба/Проба.typ
```

Ожидается: папка открывается, `.typsidian/` создаётся, сообщения об утрате настроек **нет** —
терять было нечего (FR-024).

Проверка read-only (FR-025):

```bash
chmod -w ~/media/notes && rm -rf ~/media/notes/.typsidian
```

Ожидается: vault открывается на чтение, `.typsidian/` не создаётся, причина недоступности
настроек названа. Вернуть: `chmod +w ~/media/notes`.

## Сценарий 4 — слои настроек (US4, P3)

1. При открытом `~/media/notes` включить тёмную тему.
2. Проверить, что значение ушло в vault и **не** ушло в устройство:

```bash
grep theme ~/media/notes/.typsidian/vault.json          # "theme": "dark"
grep theme ~/.config/typsidian/settings.json            # прежнее значение (FR-029)
```

3. Открыть другой vault, которого раньше не настраивали → тема из значений устройства, а не
   тёмная (FR-030).
4. Вернуться в `~/media/notes` → тёмная снова.
5. Настройки → «сделать значениями по умолчанию» → значение появляется в `settings.json`
   устройства (FR-031).
6. Перенести папку на другую машину (или сымитировать, подложив несуществующий
   `editor_config_path`) → приложение называет причину, режим не переключается молча, заметка
   остаётся редактируемой (FR-027).
7. Сменить тему из панели → применяется сразу, без перезапуска и без кнопки «сохранить»
   (FR-033).
8. Отредактировать `~/media/notes/.typsidian/vault.json` руками при работающем приложении →
   изменение **не** подхватывается немедленно; оно вступает в силу при следующем открытии этой
   папки. Это закреплённое поведение (FR-040), а не дефект: см. «Известные ограничения» ниже.

## Сценарий 5 — внешние шаблоны (US5, P3)

```bash
mkdir -p ~/media/notes/.typsidian/packages/preview/codly/1.3.0
cp -r <распакованный пакет>/* ~/media/notes/.typsidian/packages/preview/codly/1.3.0/
```

Заметка:

```typst
#import "@preview/codly:1.3.0": *
#show: codly-init
```

Ожидается: предпросмотр собирается (FR-036).

Проверка отказов:

```bash
mv ~/media/notes/.typsidian/packages/preview/codly/1.3.0 \
   ~/media/notes/.typsidian/packages/preview/codly/1.2.0
```

Ожидается: диагностика называет `@preview/codly:1.3.0` и перечисляет имеющуюся `1.2.0`
(FR-038) — не общее «не удалось собрать».

```bash
rm -rf ~/media/notes/.typsidian/packages/preview/codly
```

Ожидается: диагностика называет `@preview/codly:1.3.0` как отсутствующий шаблон (FR-037).

Проверка офлайна (FR-039): отключить сеть — поведение обоих отказов и сборка заметок без
подключений не меняются вовсе.

## Сценарий 6 — совместимость со старыми вставками (FR-009, FR-010)

На заметке, у которой в `~/media/notes` уже есть `<имя>.assets/` от прежней версии:

1. Открыть → вставка распознана, состояние актуальности определено, доска показана.
2. Отредактировать доску, обновить вставку → переписан **существующий** файл в старой папке, а
   не создан новый по новой раскладке (FR-008).
3. Вставить в ту же заметку новую доску → она ложится по новому правилу; обе вставки в одной
   заметке работают одинаково (FR-010).

## Известные ограничения

Не дефекты — принятые решения, см. таблицу в [plan.md](./plan.md):

- правка `.typsidian/vault.json` руками подхватывается при следующем открытии vault, а не сразу
  (закреплено требованием FR-040);
- `.typsidian/` создаётся при открытии vault, доступного на запись, — в том числе на web, где
  файла кэша нет;
- сообщение об утрате настроек не показывается при первом открытии папки на этом устройстве;
- первое открытие после обновления делает один дополнительный полный обход;
- при политике «в корне» адрес снимка у глубоко вложенной заметки содержит цепочку `../`;
- заметки-тёзки из разных папок делят подпапку; файлы при этом не сталкиваются.
