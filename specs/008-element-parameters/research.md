# Research: Element Parameters

**Фича**: `008-element-parameters` | **Дата**: 2026-09-26

Решения Phase 0. Каждое — ответ на вопрос, без которого план нельзя было написать.

## §1. Откуда берётся «полный набор аргументов элемента Typst» (FR-001, SC-001a)

**Decision** *(пересмотрено 2026-09-26 по решению владельца проекта)*: файла схемы
нет. Параметры читаются из самого Typst в момент обращения: `Func::params()` отдаёт
`NativeParamInfo { name, docs, input: CastInfo, default, positional, named, variadic,
required, settable }` (проверено в `typst-library-0.15.1/src/foundations/func.rs:674`) —
это и есть схема. Элемент называется ключом «синтаксис + путь функции»
(`call:figure`, `set:text`, `markup-heading:heading`, `call:figure>body=image`), спека
собирается при первом обращении и кэшируется на процесс. Какой элемент вставляет
запись каталога, ядро узнаёт, разобрав её шаблон парсером Typst (§2), — значения
шаблона становятся начальными значениями формы.

Подпись поля — имя параметра в Typst, подсказка — первый абзац его описания из
справочника (`docs`). Основные параметры — по правилу (FR-012b), а не руками.

В коде остаются правила, которых в описании Typst нет по природе, каждое с причиной
рядом: профиль разметки (§7), поправка вида `text.text` (описан строкой, принимает
`[…]`), позиционность `scale.factor` (в исходнике `#[positional]`, но `#[external]`
теряет это в `Func::params()`), вложенный элемент рисунка (`figure.body`) и префиксы меток `fig`/`tbl`/`lst`
(§6).

**Rationale**: полнота следует из построения — сверять нечего, и обновление Typst не
требует ни правки данных, ни генератора. Одна и та же функция правится везде, где она
встречается в заметке, а не только в записях из списка: «Параметры» работают для
любого вызова встроенной функции.

**Цена**: русских подписей больше нет — поля названы так, как их называет Typst
(`width`, `caption`). Это осознанный выбор владельца: подпись совпадает с тем, что
пользователь пишет в тексте и видит в справочнике. Изменения набора параметров при
обновлении Typst больше не видны в diff репозитория; круг «вставка → разбор → правка
без изменений» по всему каталогу UI ловит поломку вставки.

**Alternatives considered**:
- *Файл схемы с машинной частью из Typst и ручными подписями* (прежнее решение) —
  отвергнут владельцем: файл нужно сверять и дописывать после каждого обновления Typst.
- *Гибрид: параметры из Typst, подписи в файле-пометках* — отвергнут по той же причине:
  остаётся файл данных, который расходится с языком.
- *Схема в UI (TypeScript)* — отпадает по принципу I.

## §2. Как находить элемент под кареткой (FR-006, FR-011, FR-016)

**Decision**: парсер самого Typst — `typst::syntax::parse` + `LinkedNode::leaf_at`,
затем подъём по предкам до ближайшего узла, который схема знает: `FuncCall`
(`#figure(…)`, `table(…)` внутри аргумента), `SetRule` (`#set text(…)`), `Heading`,
блочный `Raw`, `Equation`. Ближайший предок и есть «непосредственно содержащий
каретку» элемент (FR-016).

**Rationale**: нынешний разбор рисунка и таблицы (`blockAtOffset` в
`ui/src/editor/typstElements.ts`) — регулярные выражения в интерфейсе. Он нарушает
принцип I и ломается ровно на тех случаях, которые перечислены в Edge Cases: скобка
в строке, вложенные `[…]` в подписи, экранированные кавычки. Парсер Typst эти
случаи разбирает по определению — это грамматика языка. Незакрытая скобка даёт
`SyntaxKind::Error` в поддереве — готовый признак «разметку нельзя разобрать
однозначно» (FR-011).

**Alternatives considered**: развивать регулярки в UI — отпадает (принцип I, Edge
Cases); свой мини-парсер аргументов в ядре — отпадает: второй разбор языка рядом с
первым, который уже есть в зависимостях.

## §3. Производительность поиска под кареткой (FR-021, SC-005)

**Decision**: полный разбор заметки по требованию, без кэша. Доступность
«Параметров» проверяется после паузы в движении каретки (150 мс); открытие формы и
контекстное меню разбирают сразу.

**Rationale**: замер (временный тест, удалён): заметка 10 000 строк / 198 КБ —
**3,7 мс** на полный `parse` + `leaf_at` в release native, 33 мс в debug. Замер под wasm (T050, 2026-09-26, chromium headless, release-модуль UI): `elementAt` целиком — **медиана 5,6 мс, максимум 6,6 мс** на заметке 10 001 строк / 198 КБ. В wasm
release ожидается кратно native — единицы миллисекунд. Это ниже порога
заметности, а пауза 150 мс убирает разбор с пути набора целиком.

**Alternatives considered**: инкрементальный `Source::edit` с кэшем в ядре —
отпадает: состояние в статических функциях wasm-границы и в командах Tauri, а
выигрыш не нужен при 3,7 мс.

## §4. Как применять правку, не трогая лишнего (FR-008, FR-009, FR-012, FR-012a)

**Decision**: правка — **список точечных замен** (`TextEdit { from, to, insert }`),
а не пересборка элемента целиком. Изменился параметр — заменяется только диапазон
его значения; добавлен — вставляется `name: value` в конец аргументов; сброшен к
умолчанию — удаляется вместе с запятой. Незнакомые аргументы, выражения, комментарии,
переносы строк и отступы не трогаются вовсе. Замены применяются одной транзакцией
CodeMirror.

**Rationale**: FR-009 («без изменений — символ в символ») становится тривиальным:
нет изменённых полей — пустой список замен. FR-012/FR-012a выполняются тем же
механизмом: чего форма не меняла, того она не касается. Одна транзакция — один шаг
отмены (FR-010, SC-006).

**Alternatives considered**: пересобрать элемент из значений — отпадает: теряет
форматирование и комментарии, а сохранение незнакомого превращается в отдельную
задачу с риском потерь (SC-004).

## §5. Что считается литералом, а что выражением (FR-012a)

**Decision**: литерал — узел `Int`, `Float`, `Numeric` (`2cm`, `80%`, `1fr`), `Str`,
`Bool`, `None`, `Auto`, содержимое `[…]` и идентификатор из списка допустимых значений
параметра (`center`, `top`, `ttb`, `red`). Всё прочее — `Binary` (`100% - 2cm`),
`FuncCall` (`luma(240)`), чужой идентификатор (переменная) — выражение: поле «как
есть» с исходным текстом.

**Rationale**: именно то, что форма может показать виджетом и записать обратно без
потерь. Идентификаторы-значения — не переменные: `align(center)` пишется именно так.

## §6. Где живёт метка `<fig:…>` (Edge Cases «параметр-метка»)

**Decision**: метка — псевдопараметр элемента, если схема его разрешает
(`label: { prefix: "fig" }`). Читается как узел `Label`, стоящий сразу после элемента,
пишется туда же. Занятые метки заметки ядро отдаёт вместе с разобранным элементом,
исключая собственную метку правимого (поведение нынешнего диалога сохраняется).

## §7. Разметка без `#` — заголовок, список, код, формула

**Decision**: у элементов-разметки в схеме свой **профиль разметки** — только то,
что выражается самой разметкой: заголовок — уровень (число `=`), кодовый блок — язык
(после ```` ``` ````), формула — строчная/выключная (пробелы внутри `$…$`). Прочие
параметры тех же функций Typst (`heading(outlined: …)`) правятся в `#set`-элементах
каталога, а не превращением разметки в вызов функции.

**Rationale**: форма обещает переписать элемент на месте (FR-008); превратить `== Итоги`
в `#heading(level: 2, outlined: false)[Итоги]` значило бы переписать чужой стиль
заметки. Полнота SC-001a для таких элементов меряется по профилю разметки, а у
соответствующих `#set` — по полному набору settable-параметров.

## §8. Как схема и форма доходят до всех клиентов (FR-022)

**Decision**: четыре чистые функции ядра — `element_schema`, `element_at`,
`render_element`, `plan_element_edit` — объявляются по образцу `planInsertion`
(фича 003): статический метод `WebBackend` на wasm-границе, команда Tauri в
`packages/shell/src/lib.rs`, метод `VaultClient` в UI. Форма получает схему при
открытии (клиентов с загруженным wasm на desktop/Android нет — см. память проекта).

**Rationale**: платформенного шва нет — функции чистые, но транспорт до них у
клиентов разный, и ровно для этого `VaultClient` уже существует.

## §9. Сочетание по умолчанию для «Параметров» (FR-006)

**Decision**: `Mod+Shift+E` — рядом с ⌘E меню вставки: «вставить элемент» и «параметры
элемента» — пара одного жеста. Команда `element-params` добавляется в набор
`CommandId` ядра, назначается как остальные (фича 006, раздел «Кейбиндинги»).

**Alternatives considered**: `Mod+.` — занят в части раскладок и браузеров;
`Mod+P` — ожидается как «печать»/«палитра».

## §10. Что происходит с нынешним диалогом рисунка и таблицы

**Decision**: `BlockParamsDialog` заменяется общей формой по схеме; рисунок и таблица
становятся двумя записями схемы (`figure` с вложенным `image`/`table`). Регулярный
разбор `blockAtOffset`, `blockTemplate`, `labelsInText` уходят из UI в ядро.
Поведение, которое пользователь видит сейчас, сохраняется — это требование
Assumptions спеки.

## §11. Незаполненные подстановки старых сниппетов (Edge Cases)

**Decision**: подстановок в тексте заметки нет — сниппет при вставке оставляет обычный
текст (`${2}` превращается в `2`). Форма правки читает его как обычное значение и пишет
обратно так же. Особого состояния «незаполнено» у разобранного элемента нет.

**Rationale**: поля сниппета живут только в состоянии CodeMirror (`snippet.ts`), в файл
уходит текст. Изобретать признак «это ещё подстановка» значило бы угадывать.

## §12. Когда при вставке открывается форма (SC-001, FR-003)

**Decision**: вставка — форма, если параметров ≥ 2 или есть обязательный без умолчания;
правка — у любого элемента с ≥ 1 параметром (contracts § «Когда форма»). Правило считает
ядро при загрузке схемы.

**Rationale**: иначе обычный заголовок, у которого единственный параметр — уровень,
открывал бы форму при каждой вставке, хотя сейчас вставляется сразу.
