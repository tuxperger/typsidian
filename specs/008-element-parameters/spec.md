# Feature Specification: Element Parameters

**Feature Branch**: `008-element-parameters`

**Created**: 2026-09-25

**Status**: Draft

**Input**: User description: "Параметры любого элемента Typst — форма вместо сниппета, редактируемая в любой момент. Сейчас диалог параметров есть только у рисунка и таблицы (#figure), и он умеет как вставлять новый блок, так и править существующий под кареткой. Нужно распространить это на все элементы каталога вставки, у которых есть параметры: заголовок (уровень), список (маркер, нумерация), кодовый блок (язык), цитата (источник, блочность), выделенный блок (заливка, отступы), внешняя ссылка (адрес, текст), сноска, оглавление (глубина), колонки (число, промежуток), сетка, блок с изображением, #set-элементы со своими аргументами и т.д. Требования: (1) у каждого такого элемента форма с именованными полями вместо слепого заполнения полей сниппета по Tab; (2) блок «Будет вставлено» пересобирается на каждое нажатие; (3) параметры уже вставленного элемента можно открыть и изменить в любой момент — каретка внутри элемента поднимает кнопку/команду «Параметры», форма заполняется текущими значениями, применение переписывает элемент на месте; (4) если разметка элемента не разбирается формой однозначно, правка не предлагается вовсе, чтобы ничего не терялось молча; (5) незнакомые формой аргументы при правке не должны пропадать."

> **Отправная точка.** Форма параметров уже существует для одного вида блоков —
> рисунка и таблицы в `#figure(…)`: она вставляет новый блок и правит блок под
> кареткой, показывая «Будет вставлено» на каждое нажатие. Эта фича превращает
> частный случай в общее правило каталога вставки.

> **Никакого WYSIWYG.** Редактор остаётся исходником Typst. Форма — это способ
> **набрать и переписать текст** именованными полями вместо угадывания порядка
> аргументов; между формой и документом нет промежуточного представления, и
> закрытая форма не оставляет за собой ничего, кроме обычного текста заметки.

## Clarifications

### Session 2026-09-26

- Q: Где и как описываются параметры элементов? → A: Все параметры каждого элемента
  каталога — полный набор аргументов элемента Typst, а не только самые частые, —
  фиксируются в одной схеме параметров. Форма не знает элементов сама: при открытии она
  подгружает схему нужного элемента и строит по ней поля; вставка и правка пользуются
  одной и той же схемой, и править можно любой параметр из неё.
- Q: Кто может менять схему параметров? → A: Только приложение: схема поставляется с
  ним, одна на все клиенты, и обновляется вместе с поддерживаемой версией Typst;
  пользователь её не меняет и не дополняет.
- Q: Что делать с параметром, в котором вместо значения записано выражение? → A: Он
  показывается в форме полем «как есть» — исходным текстом Typst — и по умолчанию
  возвращается в элемент символ в символ; пользователь может заменить его значением.
  Остальные параметры элемента правятся формой как обычно.
- Q: Как показывать в форме полный набор параметров элемента? → A: Параметры, отмеченные
  в схеме как основные, видны сразу; остальные — в свёрнутом блоке «Все параметры».
  Блок раскрыт сам, если в правимом элементе задан хотя бы один параметр из него.
- Q: Откуда вызываются «Параметры» для элемента под кареткой? → A: Из четырёх мест —
  кнопка на панели вставки, пункт «Параметры…» в контекстном меню редактора, команда
  палитры и назначаемое сочетание клавиш с умолчанием.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Вставка элемента с параметрами через форму (Priority: P1)

Пользователь выбирает в каталоге вставки элемент, у которого есть параметры —
кодовый блок, цитату, колонки, оглавление, внешнюю ссылку. Вместо сниппета с
полями, которые нужно обходить по ⇥ и угадывать по месту в строке, открывается
форма с именованными полями. Пока он заполняет их, блок «Будет вставлено»
показывает ровно тот текст, который окажется в заметке.

**Why this priority**: это и есть сама фича — снять необходимость помнить
порядок и написание аргументов Typst. Без неё остальные истории не нужны.

**Independent Test**: выбрать любой элемент с параметрами, заполнить два-три
поля, убедиться, что вставленный текст совпадает с показанным в «Будет
вставлено», и что элемент собирается компилятором.

**Acceptance Scenarios**:

1. **Given** открытая заметка и каталог вставки, **When** пользователь выбирает
   элемент с параметрами, **Then** открывается форма с именованными полями и
   значениями по умолчанию, а не сниппет в тексте.
2. **Given** открытая форма, **When** пользователь меняет любое поле, **Then**
   блок «Будет вставлено» пересобирается и показывает текущий результат целиком.
3. **Given** заполненная форма, **When** пользователь применяет её, **Then** в
   заметке появляется ровно показанный текст, а курсор встаёт в первое
   незаполненное место, если оно осталось.
4. **Given** элемент без параметров (перенос строки, разрыв страницы),
   **When** пользователь его выбирает, **Then** он вставляется сразу, без формы.

### User Story 2 - Правка параметров вставленного элемента в любой момент (Priority: P1)

Пользователь возвращается к написанному месяц назад тексту, ставит каретку
внутрь элемента — и открывает ту же форму, заполненную текущими значениями.
Поменяв язык кодового блока или глубину оглавления, он применяет правку, и
элемент переписывается на месте.

**Why this priority**: «в любой момент» — половина запроса. Форма, доступная
только в момент вставки, оставляет пользователя один на один с синтаксисом при
первой же правке, то есть решает задачу наполовину.

**Independent Test**: открыть заметку с ранее вставленным элементом, поставить в
него каретку, изменить один параметр, убедиться, что текст переписан на месте и
одна отмена возвращает прежний вид.

**Acceptance Scenarios**:

1. **Given** каретка внутри элемента с параметрами, **When** пользователь
   вызывает «Параметры», **Then** открывается форма, заполненная значениями из
   текста.
2. **Given** открытая форма правки, **When** пользователь ничего не меняет и
   применяет её, **Then** текст заметки остаётся прежним символ в символ.
3. **Given** открытая форма правки, **When** пользователь меняет параметр и
   применяет, **Then** элемент переписан на месте — не продублирован и не
   перенесён.
4. **Given** применённая правка, **When** пользователь делает отмену, **Then**
   возвращается текст, который был до применения, одним шагом.
5. **Given** каретка вне любого элемента, **When** пользователь ищет
   «Параметры», **Then** команда недоступна и объясняет, что править нечего.

---

### User Story 3 - Отказ от правки вместо молчаливой потери (Priority: P1)

Пользователь правил элемент руками: добавил аргумент, которого в форме нет,
или написал вычисление вместо числа. Там, где непонятое можно сохранить
нетронутым, форма открывается и возвращает его на место символ в символ. Там, где
разметку нельзя разобрать однозначно, приложение **не предлагает** форму — вместо
неё названа причина.

**Why this priority**: это условие, при котором фичей вообще можно пользоваться.
Форма, которая при «Применить» молча выбрасывает непонятое, опаснее её
отсутствия: потеря обнаруживается при сборке, а иногда позже.

**Independent Test**: дописать в элемент незнакомый аргумент, убедиться, что
правка либо не предлагается с названной причиной, либо сохраняет аргумент в
тексте после применения.

**Acceptance Scenarios**:

1. **Given** элемент с аргументом, которого форма не знает, **When** этот
   аргумент можно вернуть на место нетронутым, **Then** форма открывается, а
   после применения аргумент остаётся в тексте.
2. **Given** элемент, разметку которого форма разбирает неоднозначно, **When**
   пользователь ставит в него каретку, **Then** «Параметры» недоступны, а
   причина названа словами.
3. **Given** элемент, в параметре которого стоит вычисление вместо значения,
   **When** пользователь вызывает «Параметры», **Then** форма открывается, этот
   параметр показан исходным текстом, и после применения без его изменения он
   остаётся в тексте символ в символ.

---

### User Story 4 - Форма целиком доступна с клавиатуры (Priority: P2)

Пользователь, не снимая рук с клавиатуры, вызывает «Параметры», проходит поля
⇥, применяет ⌘↵ или отменяет Escape.

**Why this priority**: продукт keyboard-first; форма, требующая мыши, спорит с
остальным интерфейсом. Но она полезна и мышью, поэтому это не P1.

**Independent Test**: пройти сценарии US1 и US2, не касаясь мыши.

**Acceptance Scenarios**:

1. **Given** каретка в элементе, **When** пользователь вызывает команду
   «Параметры» из палитры команд или назначенным сочетанием, **Then** форма
   открывается с фокусом в первом поле.
2. **Given** открытая форма, **When** пользователь нажимает Escape, **Then**
   форма закрывается, текст заметки не меняется, а каретка возвращается туда,
   где была.

---

### User Story 5 - Вложенные элементы (Priority: P3)

Рисунок внутри колонок, кодовый блок внутри цитаты: пользователь ставит каретку
и получает параметры того элемента, в котором он на самом деле стоит.

**Why this priority**: без этого фича работает, но в сложной разметке ведёт себя
непредсказуемо — а именно в ней она нужнее всего.

**Independent Test**: вложить один элемент с параметрами в другой, проверить обе
позиции каретки.

**Acceptance Scenarios**:

1. **Given** элемент внутри другого элемента, **When** каретка стоит во
   внутреннем, **Then** открываются параметры внутреннего.
2. **Given** та же разметка, **When** каретка стоит во внешнем элементе, но вне
   внутреннего, **Then** открываются параметры внешнего.

---

### Edge Cases

- Элемент вставлен, но его поля ещё не заполнены (в тексте остались
  подстановки) — что показывает форма правки и что она запишет?
- Каретка стоит ровно на границе элемента (перед `#` или после закрывающей
  скобки): считается ли она внутри?
- Разметка не дописана — незакрытая скобка, оборванная строка.
- Файл изменился снаружи, пока форма открыта: применять правку к диапазону,
  которого уже нет, нельзя.
- В заметке есть неразрешённый конфликт правок — правка параметров обязана
  подчиняться тому же запрету записи, что и остальной текст.
- Один и тот же параметр указан дважды (`width: 40%, width: 60%`).
- Значение содержит то, что ломает наивный разбор: скобка в строке, вложенные
  квадратные скобки в подписи, экранированные кавычки.
- Очень длинная заметка и быстрый набор: поиск элемента под кареткой не должен
  ощущаться при печати.
- Параметр-метка: подсказка по умолчанию, совпадение с уже занятой меткой,
  собственная метка правимого элемента.
- Пользователь применил правку и сразу отменил её, затем повторил — состояние
  текста обязано быть предсказуемым.

## Requirements *(mandatory)*

### Функциональные требования

- **FR-001**: Параметры каждого элемента MUST браться из самого Typst в момент
  обращения — из описания функции, которое отдаёт компилятор (`Func::params()`): имя,
  вид значения, допустимые значения, значение по умолчанию, обязателен ли он, и его
  описание из справочника. Схема MUST охватывать полный набор аргументов функции
  Typst, а не выборку, и MUST NOT храниться отдельным файлом данных, который нужно
  сверять с Typst или дописывать руками. *(Пересмотрено 2026-09-26 по решению
  владельца проекта: прежде схема была файлом `schema.json` с машинной частью из
  Typst и ручными подписями.)*
- **FR-001a**: Форма вставки и форма правки MUST строиться по схеме элемента,
  подгружаемой при открытии формы, и MUST NOT иметь собственного, отдельного от схемы,
  списка полей. Любой параметр из схемы MUST быть доступен для правки.
- **FR-001b**: Новый или изменившийся параметр функции после обновления Typst MUST
  сразу отражаться в форме и при вставке, и при правке — без изменения ни формы, ни
  данных приложения.
- **FR-001d**: Какой элемент вставляет запись каталога, ядро MUST узнавать разбором её
  шаблона тем же парсером Typst, что и элемент в заметке; значения шаблона MUST
  становиться начальными значениями формы. Отдельного списка элементов в ядре нет.
- **FR-001e**: Поле формы MUST называться именем параметра в Typst — тем словом, что
  пользователь пишет в тексте и видит в справочнике, — а описание параметра из
  справочника Typst MUST быть доступно как подсказка к полю.
- **FR-001c**: Схема параметров MUST поставляться вместе с приложением и быть одной и
  той же на всех клиентах; пользователь MUST NOT иметь способа её изменить или
  дополнить в рамках этой фичи.
- **FR-002**: Элемент с параметрами MUST открывать форму с именованными полями
  вместо вставки сниппета с полями обхода по ⇥.
- **FR-003**: Элемент без параметров MUST вставляться сразу, как сейчас.
- **FR-004**: Форма MUST показывать блок «Будет вставлено» и пересобирать его
  после каждого изменения любого поля.
- **FR-005**: Текст, попадающий в заметку при применении, MUST совпадать с
  показанным в «Будет вставлено» символ в символ.
- **FR-006**: Пока каретка стоит внутри элемента с параметрами, пользователю MUST
  быть доступна команда «Параметры», открывающая форму этого элемента, из четырёх
  мест: кнопка на панели вставки, пункт «Параметры…» в контекстном меню редактора,
  команда палитры и назначаемое сочетание клавиш, у которого есть умолчание. Там, где
  правка недоступна (FR-011), каждое из этих мест MUST называть причину.
- **FR-007**: Форма правки MUST быть заполнена значениями, прочитанными из
  текста элемента.
- **FR-008**: Применение правки MUST переписывать элемент на его месте в тексте,
  не создавая второй копии и не меняя окружающий текст.
- **FR-009**: Применение правки без единого изменения полей MUST оставлять текст
  заметки неизменным символ в символ.
- **FR-010**: Одна отмена после применения MUST возвращать текст к состоянию до
  применения.
- **FR-011**: Если разметка элемента разбирается неоднозначно, система MUST NOT
  предлагать правку и MUST называть причину, по которой она недоступна.
- **FR-012**: Если форма открыта для элемента с аргументами, которых она не
  знает, эти аргументы MUST сохраняться в тексте после применения; сохранить их
  нельзя — правка MUST NOT предлагаться (FR-011).
- **FR-012a**: Параметр, значение которого записано выражением, а не литералом,
  MUST показываться в форме исходным текстом Typst и MUST возвращаться в элемент
  символ в символ, если пользователь его не менял; пользователь MUST иметь
  возможность заменить его значением. Выражение в одном параметре MUST NOT делать
  недоступной правку остальных.
- **FR-012b**: Схема MUST отмечать основные параметры каждого элемента — по правилу, а
  не руками: позиционные и обязательные параметры, параметры, заданные в шаблоне
  каталога или в правимом тексте, а у элемента с тремя параметрами и меньше без
  таковых — все. Форма MUST
  показывать основные параметры сразу, а остальные — в свёрнутом блоке «Все
  параметры»; если в правимом элементе задан хотя бы один параметр из этого блока,
  блок MUST быть раскрыт при открытии.
- **FR-013**: Необязательные параметры со значением по умолчанию MUST NOT
  попадать в текст: вставка не должна дописывать то, чего пользователь не
  выбирал.
- **FR-014**: Параметр с ограниченным набором значений MUST предлагаться
  выбором из них, а не свободным вводом.
- **FR-015**: Значение, которое элемент не примет, MUST быть названо ошибкой до
  применения, а само применение MUST быть заперто, пока ошибка не исправлена.
- **FR-016**: Для вложенных элементов форма MUST открывать тот элемент, который
  непосредственно содержит каретку.
- **FR-017**: Форма MUST открываться, проходиться и применяться с клавиатуры:
  переход по полям, применение и отмена без мыши.
- **FR-018**: Escape MUST закрывать форму, не меняя текста заметки.
- **FR-019**: Правка параметров MUST подчиняться тем же запретам записи, что и
  обычная правка текста: недоступный на запись vault и неразрешённый конфликт
  запрещают применение, и причина называется.
- **FR-020**: Если текст элемента изменился снаружи, пока форма открыта,
  применение MUST NOT записывать правку поверх — расхождение MUST быть названо.
- **FR-021**: Поиск элемента под кареткой MUST NOT замедлять набор текста в
  заметках обычного размера.
- **FR-022**: Возможность MUST быть одинаковой на всех клиентах (web, рабочий
  стол, Android) — различаться может только способ вызова, но не наличие.
- **FR-023**: Ни вставка, ни правка параметров MUST NOT обращаться в сеть.

### Ключевые сущности

- **Параметр элемента**: имя в Typst (оно же подпись поля), описание из справочника
  Typst, вид значения (выбор из списка, число, строка, путь, логическое), значение по
  умолчанию, обязательность, основной он или дополнительный.
- **Схема параметров**: единое описание всех элементов каталога — для каждого
  элемента полный набор его параметров и правило, как из значений собирается текст
  Typst. Единственный источник полей для формы вставки и формы правки.
- **Разобранный элемент**: найденный в тексте элемент — его границы в заметке,
  прочитанные значения параметров и та часть разметки, которую форма не знает,
  но обязана вернуть на место.
- **Форма параметров**: состояние заполнения — текущие значения, найденные
  ошибки и собранный по ним текст.

## Success Criteria *(mandatory)*

### Измеримые результаты

- **SC-001**: Каждый элемент каталога, у которого есть хотя бы два параметра,
  открывает форму — и при вставке, и при правке.
- **SC-001a**: Для каждого элемента набор параметров формы совпадает с набором
  аргументов этой функции в используемой версии Typst — 0 пропущенных — по
  построению: параметры читаются из компилятора, а не из копии.
- **SC-002**: Правка параметров вставленного элемента занимает не больше трёх
  действий: поставить каретку, вызвать «Параметры», применить.
- **SC-003**: Применение формы без изменений не меняет файл ни в одном из
  поддерживаемых элементов (100 % проверенных случаев).
- **SC-004**: Ни один сценарий правки не теряет разметку: незнакомое либо
  сохраняется, либо правка не предлагается — 0 случаев молчаливой потери.
- **SC-005**: Пользователь не замечает задержки: «Будет вставлено»
  пересобирается в темпе набора, а перемещение каретки по заметке в 10 000
  строк не подтормаживает.
- **SC-006**: Одна отмена возвращает документ к состоянию до применения в 100 %
  случаев.
- **SC-007**: Сборка заметки после применения формы проходит без ошибок
  синтаксиса, внесённых самой формой.

## Assumptions

- Состав каталога элементов и набор их параметров задаёт приложение и может
  расширяться без пересмотра этой спецификации; полнота покрытия проверяется по
  SC-001, а не списком имён.
- Разбор значений ограничен литералами (число, строка, единица измерения, выбор из
  набора). Выражение вместо значения (`100% - 2cm`, вызов функции, переменная) не
  разбирается, а переносится исходным текстом (FR-012a). Неоднозначной считается
  только разметка, границы которой нельзя установить: незакрытая скобка, повтор
  одного параметра (FR-011). Полный разбор языка Typst — работа компилятора, а не
  формы.
- Форме не нужен компилятор: она работает с текстом заметки. Проверка, что
  получившийся элемент собирается, остаётся за обычным предпросмотром.
- «Параметры» вызываются и мышью (панель вставки, контекстное меню редактора), и с
  клавиатуры (палитра команд, назначаемое сочетание) — FR-006. Какое сочетание
  станет умолчанием, решается на планировании.
- Форма — модальное окно поверх редактора, как нынешний диалог параметров
  блока; пока она открыта, текст не правится.
- Формат файлов не меняется: заметка остаётся обычным Typst, и элемент,
  вставленный или поправленный формой, читается любым редактором.
- Существующее поведение диалога рисунка и таблицы сохраняется и становится
  частным случаем общего правила.

## Out of Scope

- Пользовательская схема параметров (описание параметров своих функций и шаблонов
  файлом в папке заметок) — возможна позже, поверх схемы приложения.
- Визуальный редактор документа: форма правит параметры элемента, а не текст
  внутри него.
- Вызов параметров с листа предпросмотра (нажатие по блоку на странице).
- Правка параметров сразу у нескольких элементов.
- Обзор файлов vault для параметров-путей (выбор картинки из папки заметок) —
  отдельная возможность, зависящая от того, что ядро отдаёт о содержимом папки.
- Добавление в каталог новых элементов Typst: фича даёт форму тем, что уже есть.
- Правка параметров внутри досок и вставок (фича 002).

## Отношение к принятым ранее решениям

- **Принцип I (логика в ядре).** Разбор разметки Typst — правило о языке, а не
  оформление. Спецификация не предписывает, где он живёт, но требует одного
  места: два разных разбора (для вставки и для правки) разойдутся, и FR-009
  перестанет выполняться.
- **Принцип II (паритет таргетов).** FR-022 запрещает возможность, существующую
  только в одной оболочке.
- **Принцип III (спецификация описывает поведение).** Ни одно требование не
  называет ни компонента, ни формата хранения.
- **Принцип VI (данные принадлежат пользователю).** FR-012 и SC-004 — прямое
  следствие: приложение не выбрасывает из файла то, чего не поняло.
