# Feature Specification: Редактор правил исключения

**Feature Branch**: `012-ignore-rules-editor`

**Created**: 2026-10-09

**Status**: Draft

**Priority**: P3

**Summary**: Правила исключения истории и Syncthing (`.gitignore`, `.stignore`) открываются и правятся прямо в приложении: виден весь файл, чужие правки не затираются, а правила, нужные приложению, нельзя сломать незаметно.

**Input**: User description: "Добавь возможность редактирования gitignore и stignore из интерфейса"

## Clarifications

### Session 2026-10-09

- Q: Нужен ли в первой версии предпросмотр последствий правки (какие файлы начнут или
  перестанут исключаться)? → A: Нет. Первая версия — редактор и проверка обязательных
  правил; последствия для правил истории видны после сохранения в списке изменений
  панели (FR-009). Предпросмотр — Вне скоупа.
- Q: Можно ли в редакторе менять блок приложения? → A: Да, весь файл — обычный текст.
  При нехватке обязательных правил приложение называет их, предлагает вернуть одним
  действием и требует подтверждения при сохранении (FR-010…FR-013).

## Термины

- **Файл правил** — один из двух файлов в корне vault: правила истории (`.gitignore`) и
  правила доставки Syncthing (`.stignore`). Термины «история», «снимок», «доставка»,
  «хранитель» — из 011.
- **Блок приложения** — отмеченный участок файла правил, который приложение дописывает
  само (011 §FR-003, §FR-027): служебные каталоги, производные кэши, конфликтные копии.
- **Обязательные правила** — правила блока приложения; без них служебные данные попадают
  в снимки или в доставку (011 §FR-026).
- **Правила пользователя** — всё остальное содержимое файла правил.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Открыть файл правил и изменить свои правила (Priority: P1)

Пользователь в панели синхронизации открывает правила истории или правила Syncthing, видит
файл целиком — свои правила и блок приложения, — дописывает или убирает строку и
сохраняет. Изменённый файл лежит на диске в vault, как если бы его поправили во внешнем
редакторе. Если файла ещё нет, пользователь создаёт его тем же действием.

**Why this priority**: Это и есть фича. Сейчас файлы правил скрыты из дерева vault, и
поправить их можно только во внешней программе, а на Android и в web — практически никак.

**Independent Test**: Открыть vault с историей, открыть правила истории, добавить строку
`черновики/`, сохранить; убедиться, что файл на диске содержит новую строку и прежнее
содержимое без изменений, а файлы из `черновики/` исчезли из списка изменений панели.

**Acceptance Scenarios**:

1. **Given** vault с файлом правил, **When** пользователь открывает его из панели
   синхронизации, **Then** видит полное содержимое файла, в котором блок приложения
   визуально отделён от правил пользователя.
2. **Given** открытый файл правил с правкой, **When** пользователь сохраняет, **Then**
   файл на диске совпадает с текстом редактора байт в байт, кроме окончаний строк,
   которые остаются такими, какими были в файле.
3. **Given** vault без файла правил, **When** пользователь открывает правила, **Then**
   видит пустой редактор с предложенным блоком приложения и пояснением, что файл будет
   создан при сохранении; до сохранения файл не появляется.
4. **Given** сохранённая правка правил истории, **When** пользователь возвращается в
   панель синхронизации, **Then** список изменённых файлов уже отражает новые правила.
5. **Given** открытый файл с несохранённой правкой, **When** пользователь закрывает
   редактор, **Then** система спрашивает, сохранить, отбросить или вернуться к правке, —
   правка молча не теряется.
6. **Given** vault, который не доставляется Syncthing, **When** пользователь открывает
   правила Syncthing, **Then** редактирование доступно, а система поясняет, что Syncthing
   в этой папке не обнаружен и правила начнут действовать, когда папка станет его папкой.
   То же — для правил истории в vault без истории.

---

### User Story 2 - Не сломать правила, которые нужны приложению (Priority: P2)

Блок приложения можно править, как и остальной текст, — это файл пользователя. Но если
после правки обязательных правил не хватает, система говорит, каких именно и чем это
грозит, и предлагает вернуть их одним действием. Сохранить файл без них можно только
после явного подтверждения; предупреждение 011 в панели синхронизации при этом остаётся.

**Why this priority**: Без обязательных правил служебный каталог истории уезжает через
Syncthing на другие устройства и портится, а конфликтные копии и кэши попадают в снимки.
011 уже следит за этим; редактор не должен стать способом сломать это незаметно.

**Independent Test**: Открыть правила Syncthing, удалить строку блока приложения,
исключающую служебный каталог истории; увидеть предупреждение с названием правила,
нажать «вернуть» — строка восстановлена на прежнем месте, правила пользователя не тронуты.

**Acceptance Scenarios**:

1. **Given** открытый файл правил, **When** из текста пропадает обязательное правило,
   **Then** система перечисляет недостающие правила и последствие каждого вида (служебные
   данные в доставке, конфликтные копии в снимках).
2. **Given** недостающие обязательные правила, **When** пользователь выбирает «вернуть
   правила приложения», **Then** блок приложения восстановлен в тексте редактора, правила
   пользователя сохранены без изменений, повторное действие ничего не дублирует.
3. **Given** недостающие обязательные правила, **When** пользователь сохраняет, **Then**
   система требует отдельного подтверждения с названием риска; без него файл не пишется.
4. **Given** строка пользователя, которая дословно отменяет обязательное правило (то же
   правило со знаком отмены там, где она сильнее самого правила: в правилах истории —
   ниже него, в правилах Syncthing — выше), **When** текст проверяется, **Then** система
   считает обязательное правило нарушенным так же, как при его удалении.

### User Story 3 - Не затереть чужую правку файла (Priority: P2)

Файл правил может измениться, пока он открыт в редакторе: его принёс Syncthing (правила
истории доставляются между устройствами), поправил другой редактор или само приложение
дописало блок. При сохранении система замечает это и не перезаписывает файл молча.

**Why this priority**: Правила истории — общий файл всех устройств. Тихая перезапись
стирает правку, сделанную на другом устройстве, и её уже не вернуть без истории.

**Independent Test**: Открыть правила истории, изменить файл на диске другой программой,
нажать «сохранить» в приложении; убедиться, что файл не перезаписан и показаны обе версии.

**Acceptance Scenarios**:

1. **Given** открытый файл без несохранённых правок, **When** файл изменился на диске,
   **Then** редактор показывает новое содержимое и сообщает, что файл обновлён извне.
2. **Given** открытый файл с несохранённой правкой, **When** файл изменился на диске и
   пользователь сохраняет, **Then** система не пишет файл и предлагает выбрать: взять
   версию с диска, записать свою поверх или вернуться к правке, показав различие версий.
3. **Given** открытый файл, **When** он удалён с диска, **Then** система сообщает об этом
   и при сохранении создаёт файл заново только с подтверждения пользователя.

---

### Edge Cases

- Файл правил не является текстом в UTF-8 или больше предела размера заметки (001):
  редактор не открывается для правки, система говорит почему и не трогает файл.
- Файл правил — символическая ссылка или каталог с таким именем: правка недоступна,
  причина названа (как для прочих таких путей в 001).
- Vault открыт без права записи (web без разрешения, папка только для чтения): файл
  виден, сохранение недоступно и отмечено причиной.
- Сохранение оборвалось (нет места, отозвано разрешение): на диске остаётся прежний файл
  целиком, текст в редакторе не теряется, ошибка показана.
- Правила истории лежат в vault внутри чужого репозитория (011, «vault — часть более
  крупного репозитория»): правится файл в корне vault, и система поясняет, что на файлы
  действуют также правила вышележащих каталогов, которые здесь не показаны.
- В подкаталогах vault есть собственные файлы правил истории: они продолжают действовать,
  но в редакторе не открываются (Вне скоупа).
- Правило пользователя отменяет обязательное не дословно, а шаблоном: проверка этого не
  замечает (она сверяет строки, а не рассчитывает действие правил) — последствие видно в
  списке изменений панели и в предупреждении 011 §FR-026, если оно сработает.
- Идёт получение, слияние или автоснимок (011): сохранение правил истории ждёт окончания
  операции или отклоняется с названной причиной — файл не пишется посреди операции.
- Правила Syncthing у каждого устройства свои (Syncthing этот файл не доставляет):
  редактор говорит об этом, чтобы пользователь не ждал правку на другом устройстве.
- Пустой файл после правки: сохраняется пустым (с подтверждением из US2), не удаляется.
- Файл с окончаниями строк CRLF или без завершающего перевода строки: вид окончаний
  сохраняется. Файл, в котором окончания строк смешаны, после сохранения получает единые
  окончания LF — это единственный случай, когда запись меняет байты вне правки.

## Requirements *(mandatory)*

### Functional Requirements

**Открытие и сохранение**

- **FR-001**: Панель синхронизации MUST давать вход в редактор каждого из двух файлов
  правил корня vault — правил истории и правил Syncthing — независимо от того, включена
  ли история и обнаружен ли Syncthing.
- **FR-002**: Редактор MUST показывать файл целиком и позволять править любой его
  участок как обычный текст. Блок приложения MUST быть визуально отделён и подписан.
- **FR-003**: Сохранение MUST записывать текст редактора в файл правил без каких-либо
  добавлений со стороны приложения; вид окончаний строк и наличие завершающего перевода
  строки MUST сохраняться такими, какими были в файле.
- **FR-004**: Запись MUST быть атомарной: при сбое на диске остаётся прежний файл целиком.
- **FR-005**: Если файла нет, редактор MUST открываться с предложенным блоком приложения
  и создавать файл только при сохранении.
- **FR-006**: Закрытие редактора с несохранённой правкой MUST требовать решения
  пользователя: сохранить, отбросить, вернуться.
- **FR-007**: Если правила сейчас не действуют (нет истории для `.gitignore`, Syncthing
  не обнаружен для `.stignore`), редактор MUST сообщать об этом, не запрещая правку.
- **FR-008**: Редактор правил Syncthing MUST сообщать, что этот файл у каждого устройства
  свой; редактор правил истории — что файл общий для устройств и попадает в снимки.
- **FR-009**: После сохранения сводка и список изменений панели синхронизации (011
  §FR-035) MUST отражать новые правила без перезапуска и повторного открытия vault.

**Обязательные правила**

- **FR-010**: Система MUST проверять текст редактора на наличие обязательных правил
  (011 §FR-003, §FR-026) по мере набора и перечислять недостающие с последствием. Проверка
  MUST давать тот же ответ, что и предупреждение 011 §FR-026 для того же текста.
- **FR-011**: Система MUST предлагать вернуть блок приложения в текст редактора одним
  действием; правила пользователя MUST сохраняться, повторное действие MUST NOT
  дублировать правила (011 §FR-027).
- **FR-012**: Сохранение текста с нарушенными обязательными правилами MUST требовать
  отдельного явного подтверждения. После такого сохранения предупреждение 011 §FR-026 в
  панели синхронизации MUST оставаться.
- **FR-013**: Обязательное правило, дословно отменённое строкой, которая по порядку своего
  формата сильнее него (в правилах истории — ниже, в правилах Syncthing — выше), MUST
  считаться нарушенным.

**Внешние изменения и отказы**

- **FR-014**: Система MUST замечать изменение или удаление файла правил на диске, пока
  он открыт: без несохранённой правки — показывать новое содержимое с уведомлением; с
  несохранённой правкой — не перезаписывать файл и не заменять текст редактора молча.
- **FR-015**: При расхождении сохранение MUST предлагать: взять версию с диска, записать
  свою, вернуться к правке, — с показом различия версий.
- **FR-016**: Файл, который нельзя безопасно править (не текст, больше предела, ссылка,
  каталог, нет права записи), MUST NOT изменяться; причина MUST быть названа.
- **FR-017**: Сохранение правил истории во время незавершённой операции истории (011)
  MUST NOT выполняться посреди неё.
- **FR-018**: Отказ сохранения MUST оставлять текст редактора нетронутым и сообщать
  причину; общих сообщений «не удалось» быть не должно.

**Оболочки и общие правила**

- **FR-019**: Редактор и проверка обязательных правил MUST работать
  одинаково в web, на рабочем столе и на Android и MUST NOT требовать сети.
- **FR-020**: Редактор MUST быть доступен на любом устройстве vault, независимо от роли
  хранителя: это правка файла vault, а не операция истории.
- **FR-021**: Все тексты редактора MUST идти через локализацию (010).
- **FR-022**: Редактор MUST быть полностью управляем с клавиатуры и работать на узком
  экране телефона.

### Key Entities

- **Файл правил**: вид (история или Syncthing), содержимое, наличие на диске, отметка
  версии на диске, возможность правки и причина её отсутствия.
- **Проверка правил**: недостающие и отменённые обязательные правила, предлагаемый блок
  приложения.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь добавляет правило исключения папки и сохраняет его менее чем
  за 30 секунд от открытия панели синхронизации, не покидая приложения, — на каждой из
  трёх оболочек.
- **SC-002**: Ни один сценарий с внешним изменением файла не приводит к потере чужой
  правки без явного выбора пользователя.
- **SC-003**: Ни одно сохранение, нарушающее обязательные правила, не проходит без
  отдельного подтверждения.
- **SC-004**: Правила пользователя в файле после любого действия приложения (сохранение,
  возврат блока приложения) совпадают с введёнными им посимвольно.

## Assumptions

- Вход в редактор — из панели синхронизации (011); файлы правил по-прежнему не
  показываются в дереве vault (001).
- Редактируются только два файла в корне vault. Блок приложения — тот же, что в 011, и
  определяется теми же отметками начала и конца.
- Блок приложения не защищён от правки: файл принадлежит пользователю, приложение
  предупреждает и требует подтверждения, но не запрещает (в 011 от правил Syncthing тоже
  можно отказаться).
- Правка правил истории не убирает из истории и из будущих снимков файлы, которые в неё
  уже попали: приложение это поясняет, а не делает само.
- «Заметки и доски» определяются так же, как в дереве vault (001, 002).
- Предел размера файла правил — предел размера заметки из 001.
- Подсветка синтаксиса правил и подсказки при вводе не обязательны для первой версии.
- Сохранение правил истории само по себе снимок не создаёт: изменённый файл правил
  появляется в списке изменений, как любой другой файл vault.

## Вне скоупа

- Файлы правил в подкаталогах vault, глобальные правила пользователя и правила,
  хранящиеся в служебном каталоге истории.
- Удаление из истории файлов, которые в неё уже попали.
- Изменение правил Syncthing через сам Syncthing и правила на других устройствах.
- Предпросмотр последствий правки до сохранения — список файлов, которые начнут или
  перестанут исключаться, предупреждение об исключённых заметках (Clarifications
  2026-10-09). Требует собственного расчёта правил обоих форматов — отдельная фича.
- Конструктор правил «галочками» по дереву vault — возможное продолжение.
