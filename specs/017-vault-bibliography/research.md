# Research: Библиография vault

**Feature**: 017-vault-bibliography · **Date**: 2026-10-10

Спека этой фичи не проходила отдельный `/speckit-clarify`. Неоднозначности закрыты здесь —
по коду и конституции; спека не переписывалась. Решения, меняющие объём, помечены
**[объём]** и вынесены в отчёт планирования.

Сборка и тесты на этапе планирования не запускались (общий бриф P2). Всё, что ниже названо
«проверено», проверено чтением исходников крейтов из реестра cargo и кода репозитория;
утверждения, требующие сборки, закреплены задачей-зондом (tasks.md T001).

## §1 Чем читать файлы источников

**Decision**: крейты `hayagriva 0.10.1` (единая модель записи для обоих форматов и разбор
YAML), `biblatex 0.12.0` (разбор BibTeX) и `serde_yaml 0.9` (разбор YAML до записей)
объявляются **прямыми** зависимостями `packages/core/Cargo.toml` в тех же версиях, что уже
стоят в `Cargo.lock`. Своего разбора BibTeX и Hayagriva нет.

**Rationale**:
- Все три крейта уже приезжают транзитивно: `typst-library 0.15.1` зависит от
  `hayagriva 0.10.1` с признаками по умолчанию (`biblatex`, `archive`), тот — от
  `biblatex 0.12.0` и `serde_yaml 0.9.34` (`Cargo.lock`). Прямое объявление ничего не
  добавляет ни к сборке, ни к весу wasm-модуля — как `regex` в текущем `Cargo.toml`.
- Под wasm32 они уже собираются: это часть `typst`, а ядро собирается под оба таргета с
  фичи 005. Условие принципа II выполнено построением.
- Это тот же код, которым файл читает сам Typst (`typst-library/src/model/bibliography.rs`,
  `decode_library`): расхождение «приложение источник видит, а сборка — нет» возможно только
  там, где мы намеренно терпимее (§2).
- `biblatex` раскрывает TeX-записи (`{\"o}` → `ö`) и сокращения `@string` — поиск по
  фамилии обязан идти по раскрытому тексту.

**Alternatives considered**:
- Свой разбор BibTeX регулярными выражениями — второй источник истины о формате (принцип I),
  неверен на вложенных скобках и TeX-командах. Отклонено.
- Только `biblatex` без `hayagriva` — две модели записи (BibTeX-поля и YAML) и собственное
  сведение их к «авторы, название, год, вид». Отклонено: `hayagriva::Entry` уже есть это
  сведение (`TryFrom<&biblatex::Entry>`, `interop.rs`).

## §2 Ошибка в одной записи не роняет остальные (FR-008)

**Проблема** (проверено по исходникам): штатные входы — «всё или ничего».
`hayagriva::io::from_biblatex_str` возвращает `Err` целиком при первой синтаксической ошибке
(`Bibliography::parse` → `ParseError { span, kind }`) и при любой ошибке типа
(`Vec<TypeError>`); `from_yaml_str` — при первой негодной записи. Так ведёт себя и сборка
Typst. Для списка источников это не годится.

**Decision**: штатный вход — быстрый путь; при отказе — чтение по записям через **публичный**
API тех же крейтов.

BibTeX (`sources/bibtex.rs`):
1. `RawBibliography::parse(text)`. Успех → шаг 3.
2. Отказ → текст режется на куски по началам записей (строка, начинающаяся с `@имя{` или
   `@имя(`), каждый кусок разбирается `RawBibliography::parse` отдельно. Кусок с ошибкой —
   одна ошибочная запись с местом (строка начала куска); записи и сокращения `@string`
   удачных кусков собираются в один `RawBibliography` (поля структуры публичные). Проход
   линейный по размеру файла. Своего разбора здесь нет: наш код только находит границы, а
   каждую запись читает крейт.
3. `Bibliography::from_raw(raw)` целиком. Отказ (повтор ключа, неизвестное сокращение,
   негодная TeX-команда, ошибка перекрёстной ссылки) → `from_raw` по одной записи
   (`RawBibliography { entries: vec![одна], abbreviations: общие }`); отказавшая запись —
   ошибочная. Повтор ключа внутри файла: первая запись остаётся, вторая названа ошибочной.
   Затем `from_raw` на оставшихся записях разом — чтобы восстановить `crossref`; если и он
   отказал, берутся результаты по одной записи (без наследования полей).
4. Каждая `&biblatex::Entry` → `hayagriva::Entry` через `TryFrom` по одной; `TypeError` —
   ошибочная запись с местом.

Hayagriva YAML (`sources/yaml.rs`):
1. `hayagriva::io::from_yaml_str(text)`. Успех → готово.
2. Отказ → `serde_yaml::from_str::<serde_yaml::Mapping>(text)`. Не разобралось (ошибка самого
   YAML, повтор ключа верхнего уровня) → **ошибка уровня файла** с местом из
   `serde_yaml::Error::location()`; записей из файла нет. YAML не даёт границ записи при
   сломанном синтаксисе, и это честный предел.
3. Разобралось → каждая пара верхнего уровня превращается в отдельную `Library` через
   `serde_yaml::from_value` (карта из одной записи). `hayagriva::Entry` сам не реализует
   `Deserialize` — только `Library`, поэтому единица чтения — библиотека из одной записи.
   Отказ → ошибочная запись; место — строка, где ключ стоит в начале строки файла.

Место ошибки наружу — номер строки с единицы и колонка, как у `DiagnosticLocation`; байтовые
смещения крейтов переводятся в строку в ядре.

**Предел**: не больше 200 названных ошибок на файл; остальное сворачивается в одну запись
«и ещё N» (`SourceProblemKind::TooMany`). Без предела файл не того формата дал бы тысячи
строк отчёта.

**Запасной путь**, если зонд T001 покажет, что `from_raw` по одной записи или
`from_value::<Library>` ведут себя иначе, чем прочитано: шаг 3 BibTeX заменяется
исключением записи, на чей диапазон указывает `ParseError.span`, и повтором `from_raw`
(не больше 200 повторов); для YAML — тем же исключением ключа из `Mapping`. Форма
`FileReading` (data-model.md) от этого не меняется.

**Alternatives considered**: показывать файл с ошибкой как нечитаемый целиком (как сборка) —
прямо противоречит FR-008. Отклонено.

## §3 Какие файлы — файлы источников (FR-001)

**Проблема**: `vault::classify` относит `.bib` и `.yml` к `FileKind::Other`; в индекс и в
события вотчера такие файлы не попадают. `.yml` в vault — не обязательно список источников
(настройки чужих программ, данные для `#yaml()`).

**Decision**:
- **Кандидат** — файл с расширением `bib`, `yml` или `yaml` (без учёта регистра), для
  которого `classify` даёт `Other`: не служебное место, не снимок, не конфликтная копия
  Syncthing. Скрытые папки пропускаются тем же правилом, что и в обходе заметок. Правило —
  `sources::discover::source_format(path)`, одно на оба backend.
- `.bib` — файл источников **всегда**.
- `.yml`/`.yaml` — файл источников, если выполнено хотя бы одно:
  1. хотя бы одна запись читается как запись Hayagriva (§2);
  2. файл назван в `#bibliography(…)` какой-либо заметки (известно индексу цитат, §8, и
     тексту открытой заметки);
  3. файл указан пользователем (`VaultOverrides.source_files`, §11).
  Иначе это посторонний YAML: в списке его нет, ошибок по нему не показывается.
- `FileKind` **не расширяется**: файл источников остаётся `Other` — приложение его не
  редактирует и в дереве не показывает. Новый вид задел бы каждое `match` по `FileKind`
  в фичах 001–011 ради признака, который для `.yml` всё равно не выводится из пути.
- Обход — новый метод трейта `VaultBackend::list_source_candidates()` по образцу
  `list_fonts`: только метаданные `{path, size, modified_ms}`, отдельный обход, а не выборка
  из индекса.

**Rationale**: условия 2 и 3 нужны ради FR-008. Файл, подключённый заметкой, но сломанный
целиком, по условию 1 выпал бы из списка молча, а все цитаты заметки стали бы «битыми» без
названной причины.

**Alternatives considered**:
- Считать источниками все `.yml` — посторонний YAML засыпал бы список ошибками. Отклонено.
- Распознавать `.yml` только по явному указанию — нарушает FR-001 («MUST находить»).
  Отклонено.

## §4 Файл источников вне vault и «указать существующий» (US1 AS4) **[объём]**

**Decision**: системного диалога выбора файла и копирования в vault **нет**. «Указать
существующий» — выбор из YAML-кандидатов vault, не опознанных как источники (§3, условие 3).
Выбранный путь записывается в настройки vault. Если таких кандидатов нет, показывается только
«Создать» и строка-подсказка: файл `.bib` или `.yml`, положенный в папку заметок, подхватится
сам (Edge Cases: «вне vault не поддерживается, предложено положить его в vault»).

**Rationale**: самое консервативное чтение. Копирование внешнего файла в vault — операция
фичи 016 (вложения), а не этой; на Android папка vault фиксирована и системный выбор файла
там отдельная работа.

## §5 Создание файла источников (US1 AS4) **[объём]**

**Decision**: «Создать» создаёт пустой `references.bib` в корне vault через атомарную
`write_bytes` (009 research.md §4). Имя латиницей и одинаково для всех языков — по сквозному
решению 7 брифа (`export`, `attachments`). Файл с таким именем уже есть → отказ
`AlreadyExists` (в этом случае файл источников в vault есть и команда не предлагается).
Vault только на чтение → `AccessDenied`, кнопка недоступна с названной причиной (Edge Cases).

**Расхождение с макетом** (1c): там «Подключить Библиография.bib». Решает бриф: имя
латиницей.

**Следствие, вынесенное в отчёт**: редактировать `.bib` в приложении нельзя (вне скоупа
спеки: «редактор записей с формой»; файл не показывается в дереве). Созданный файл
пользователь наполняет внешним редактором или менеджером литературы; панель говорит об этом
прямо.

## §6 «Правка файла источников в приложении» (US3, FR-007) **[объём]**

**Decision**: «в приложении» понимается как изменения, которые делает само приложение
(создание файла, §5) и синхронизация (011). Открытие `.bib`/`.yml` в редакторе Typsidian в
объём 017 **не входит**: дерево показывает только заметки и доски (`FileKind::is_listed`),
редактора нетекстовых-для-Typst файлов нет, и его появление — отдельная фича. Все остальные
правки приходят «извне» и обнаруживаются по §7.

## §7 Как замечается изменение файлов источников (FR-007)

**Проблема** (проверено): на native `dispatch_debounced_event` отбрасывает события для
путей, не прошедших `is_listed`; на web `poll_for_changes` обходит только записи дерева.
Изменение `.bib` сейчас не замечает никто.

**Decision**: новое событие `VaultEvent::SourceFilesChanged` без полезной нагрузки.
- native: `dispatch_debounced_event` для пути-кандидата (§3) шлёт `RawChange`, из которого
  получается это событие (создание, изменение, удаление, переименование — одно событие).
- web: `poll_for_changes` держит снимок `{path → (size, modified)}` кандидатов и кладёт
  событие при расхождении. Обход кандидатов — тот же проход, без чтения содержимого.
- запись кандидата самим приложением (`write_bytes`) кладёт событие на обоих таргетах.

Получив событие, UI вызывает `sources_refresh`; ядро сверяет отпечатки и перечитывает только
изменившиеся файлы. Событие без путей намеренно: кто изменился, решает сверка отпечатков в
одном месте, а не два списка на двух таргетах.

**Alternatives considered**: опрашивать `list_source_candidates` по фокусу окна и при
открытии панели — не замечает правку из Syncthing, пока окно в фокусе; US3 требует, чтобы
отметка появилась в открытой заметке сама. Отклонено.

## §8 Индекс «кто цитирует источник» (FR-005, SC-004)

**Decision**: `sources::citations::CitationIndex` — чистая машина состояний в ядре; строится
проходом по заметкам vault **порциями** по образцу пакета экспорта
(`packages/core/src/export/batch.rs`, 009 research.md §5) и прохода упоминаний 013
(сквозное решение 5 брифа).
- Состояние живёт в ядре по обе стороны границы (wasm-объект `SourceEngine`, состояние
  Tauri `Sources`), а не ездит через границу значением, как `BatchState`: записи о цитатах
  5 000 заметок на каждый шаг — мегабайты сериализации.
- `scan_start(notes)` → очередь; `scan_step(backend, max_notes)` читает не больше
  `max_notes` (50) заметок, разбирает (§9), возвращает `ScanView { processed, total, phase }`;
  `scan_cancel()`. Цикл крутит UI, уступая циклу событий между порциями (принцип X).
  Отмена оставляет индекс частичным и помеченным `Cancelled`; повторный запуск пропускает
  заметки с прежним отпечатком `FileStamp`.
- Проход запускается при первом показе панели «Источники», не при открытии vault: чтение
  всех заметок ради панели, которую не открыли, — напрасная работа.
- После прохода индекс поддерживается по событиям vault: `NoteCreated`/`NoteUpdated` →
  `note_changed(path)` (перечитать одну заметку), `NoteDeleted` → убрать, `NoteRenamed` →
  перенести.
- Индекс — производное состояние в памяти (принцип IX), на диск не пишется.

**SC-004** («список открывается ≤1 с в vault из 5 000 заметок») измеряется на построенном
индексе: выборка по ключу — поиск в `HashMap`. Первый проход — массовая операция с
прогрессом; пока он идёт, панель показывает найденное к этому моменту и строку прогресса.
**[объём]** Хранение индекса в кэше vault (как ссылки `record_links`) дало бы мгновенный
первый показ, но меняет схему кэша на обоих таргетах; отложено.

**Цитаты открытой заметки** с несохранёнными правками в индекс не попадают до сохранения:
индекс отражает диск, как и граф ссылок. Отметки в редакторе (§10) считаются по живому
тексту.

## §9 Разбор цитат в тексте заметки

**Decision**: только через общий модуль `packages/core/src/structure/`, который заводит 015
(сквозное решение 2), и ровно по правилу расширения из
`specs/015-note-outline/contracts/core-structure-api.md` § «Расширение для 018 и 017»: новый
вопрос к тексту — новое поле `NoteStructure` и новая ветка в `walk.rs`, не новый обход.

| Что нужно 017 | Откуда |
|---|---|
| ссылки `@имя` с местом (`RefSite`) | готово в 015 (`NoteStructure.refs`) |
| метки, объявленные в тексте (`LabelSite`) | готово в 015 (`NoteStructure.labels`) |
| вызовы `cite(<ключ>)` и `cite(label("ключ"))` | **добавляет 017**: поле `cites: Vec<CiteSite>` |
| вызовы `bibliography(…)` с путями-литералами (строка или массив строк) и местом аргумента | **добавляет 017**: поле `bibliographies: Vec<BibliographySite>` |
| режим в месте каретки: разметка, математика, код, строка, комментарий | **добавляет 017**: `structure::mode_at(text, utf16) -> TextMode` — по тому же дереву, отдельной функцией, а не полем |

Места — `TextPlace` 015 (`line`, `column`, `from`/`to` в UTF-16). Обход 015 не заходит в
замыкания, циклы и правила `show`/`set` — цитата внутри них в индекс не попадёт и не будет
отмечена; это общее правило модуля, 017 его не меняет.

**Что считается цитатой**:
- `cite(…)` — цитата всегда.
- `@имя` — цитата, если `имя` — ключ источника vault; **не** цитата, если `имя` есть в
  известном наборе меток; если ни то ни другое — «ссылка в никуда» (§10).

Путь в `#bibliography("…")` разрешается так же, как у сборки: `/…` — от корня vault (корень
мира Typst — корень vault, `preview/world.rs`), иначе — от папки заметки.

## §10 Отметка цитат с ненайденным ключом (FR-006, SC-003) и общий механизм с 018

**Decision — механизм** (заводит 017, пользуется 018 — `specs/018-label-completion/research.md`
§8):
- UI: `ui/src/editor/marks.ts` — расширение CodeMirror: `StateField` с `Decoration.mark` и
  `hoverTooltip` с причиной. Вход — `EditorMark { from, to, tone: "error" | "warning",
  message }` (смещения UTF-16, как у `TextPlace` и `elements::edit::TextEdit`); отметки
  кладутся **по поставщикам**: `setMarks(view, "sources", marks)` заменяет только свои.
  018 кладёт свои под именем `"references"`. Тон задаёт подачу: `error` —
  `.ts-mark--error`, красный текст и красный пунктир (макет 017 1a); `warning` —
  `.ts-mark--warning`, жёлтый пунктир (018).
- Ядро: вид и место отметки цитаты — `sources::check::CitationMark`; общего типа отметки в
  ядре нет, потому что 018 отдаёт свои виды своим типом (`ReferenceMark`), а сходятся они
  только в подаче.
- `@codemirror/lint` **не подключается**: это новая зависимость (и правка lock-файлов) ради
  панели и гуттера, которых в макете нет; `@codemirror/view` уже даёт `Decoration` и
  `hoverTooltip`.

**Decision — кто какую ссылку отмечает**. Правило одно, в ядре:
`sources::check::check_note(text, library, known_labels)` (наружу — `SourceEngine::check_note(text, known_labels)`).

| Запись | Условие | Отметка 017 |
|---|---|---|
| `cite(<k>)`, `cite(label("k"))` | `k` нет ни в одном файле источников | `MissingSource` |
| `@k` | `k` — ключ источника | нет |
| `@k` | `k` — метка текста заметки или `k` ∈ `known_labels` | нет |
| `@k` | ни то ни другое, в vault **есть** файлы источников | `MissingSource { ambiguous: true }`: причина называет обе возможности — источника с таким ключом нет, метки с таким именем тоже |
| `@k` | ни то ни другое, файлов источников в vault **нет** | нет — это ссылка на метку, отметка 018 |

Согласование с 018 (её research.md §8: «если 017 уже выдала отметку для диапазона, 018 свою
не добавляет»): на одну ссылку — не больше одной отметки, в неоднозначном случае при
подключённых источниках остаётся красная отметка 017 с формулировкой про обе возможности.
`known_labels` — параметр именно ради 018: в 017 UI передаёт пустой список (метки самой
заметки ядро берёт из `structure::parse`), а 018 **обязана** передавать сюда метки связанных
файлов и свидетельство удачной сборки — иначе её FR-007 («нет отметок для ссылок, которые
разрешаются при сборке») нарушит красная отметка 017. Вынесено в отчёт как точка стыка.

**Известное ограничение до 018**: ссылка `@k` на метку из **связанного файла** в vault с
источниками получит красную отметку 017. SC-003 требует 100 % отмеченных битых цитат, поэтому
из двух ошибок выбрана ложная отметка, а не пропуск.

Отметки пересчитываются по живому тексту редактора с задержкой 300 мс после набора и сразу —
после `sources_refresh`. В статус-баре — «N цитат · M битых» по той же выдаче (макет 1a).

## §11 Настройка vault `source_files`

**Decision**: поле `VaultOverrides.source_files: Vec<String>` в `.typsidian/vault.json` —
пути YAML-файлов, указанных пользователем (§4). Проверка при записи: путь внутри vault, без
`..`, расширение `yml`/`yaml`/`bib`; отказ — `VaultSettingsError::InvalidSourceFile`, файл
настроек не тронут (образец — `export_folder`, 009). Путь, которого больше нет на диске, не
ошибка: он просто не даёт кандидата.

Настройка vault, а не устройства: какие файлы — источники, свойство набора заметок.

## §12 Запись цитаты (FR-003)

**Decision**: `sources::cite::citation_text(key, mode, next_char)`; правила взяты из лексера
`typst-syntax 0.15.1` (`ref_marker`, `is_valid_label_literal_id`):

| Условие | Запись в разметке |
|---|---|
| все знаки ключа допустимы в литерале метки, ключ не кончается на `.` или `:`, следующий за кареткой знак не продолжил бы имя и не `[` | `@ключ` |
| знаки допустимы, но краткая запись прочиталась бы иначе | `#cite(<ключ>)` |
| есть пробелы или иные недопустимые знаки | `#cite(label("ключ"))` с экранированием строки |

В математике — всегда форма `#cite(…)`; в коде — она же без `#`. В строке и комментарии
вставка отклоняется с причиной (`CitationPlanError::NotInsertable`). Режим — из `structure/`
(§9, п. 5). Проверка допустимости знаков — функцией `typst-syntax`, а не своим списком.

Вставка — `sources::cite::plan_citation(text, caret, key)` → `CitationPlan { edits:
Vec<TextEdit>, caret }`; замены — тот же тип `elements::edit::TextEdit`, что у правки
элементов 008, и применяются одной транзакцией редактора (008 FR-010). Вызов палитры по `@`
не делается (это дополнение 018); палитра 017 открывается только командой.

## §13 Предложение добавить список литературы (FR-004)

**Decision**: `sources::cite::bibliography_offer(text, source_file)`:
- в тексте заметки нет вызова `bibliography(…)` → `Add`: замена, дописывающая в конец заметки
  `#bibliography("/путь/от/корня")`. Путь — от корня vault с ведущей `/`: он не ломается
  при переносе заметки в другую папку.
- вызов есть, его пути литеральные и файла выбранного источника среди них нет → `Extend`:
  замена аргумента на массив с добавленным файлом (Edge Cases: несколько файлов источников).
- вызов есть и файл в нём уже назван либо аргумент не литерал → `None`.

Предложение показывается **после** вставки цитаты отдельным ненавязчивым запросом
(«Добавить» / «Не сейчас»); без согласия текст не меняется. Отказ запоминается для этой
заметки до конца сеанса в состоянии UI: заметка-глава, которую подключает другой документ со
своим списком литературы, не должна спрашивать на каждой цитате. Ядро о включающем документе
не знает и не гадает.

## §14 Поиск источников (FR-002, SC-002)

**Decision**: `SourceLibrary::search(query, limit)` — линейный проход по заранее
подготовленным строкам (авторы, название, год, ключ в нижнем регистре); запрос режется по
пробелам, **каждое** слово обязано встретиться подстрокой. Порядок: совпадение с началом
ключа → с началом фамилии → прочее; внутри — по первому автору и году. Выдача ограничена
`limit` (палитра — 50, панель — 200) и несёт `total_matches`.

**Rationale**: 10 000 записей × несколько сравнений подстрок — единицы миллисекунд; индекс
(триграммы, FST) — сложность без измеренной нужды. SC-002 закрепляется бенчмарком
`sources_scale` (10 000 записей) и тестом на оба таргета.

Транслитерации нет: «кнут» находит запись, где фамилия записана кириллицей.

Одинаковые ключи в разных файлах — два источника, каждый со своим файлом в строке списка
(Edge Cases). Цитирующие заметки привязаны к **ключу** и показываются у обоих: по тексту
цитаты их не различить.

## §15 Сочетания клавиш

**Decision**: `CommandId::InsertCitation` (`insert-citation`, **Mod+Alt+B**) и
`CommandId::ToggleSources` (`toggle-sources`, **Mod+Alt+R**).

**Расхождение с брифом**: бриф назначал панели источников Mod+Shift+U. Не взято:
- Ctrl+Shift+U на Linux — ввод знака Unicode по коду (GTK/IBus); в поле ввода сочетание
  перехватывается до приложения. Того же рода, что названный в брифе Ctrl+Alt+L.
- `ui/src/editor/CodeEditor.tsx` подключает `historyKeymap`, где `Mod-u` — отмена выделения,
  а на macOS `Mod-Shift-u` — её повтор.

`Mod+Alt+R` свободно в `default_shortcut` и в таблице брифа; `Shortcut` представляет его как
`(shift: false, alt: true, key: "r")`, `problem()` его не отвергает. `Mod+Alt+B` — так же.

## §16 Расхождения с макетом `Typsidian Библиография.dc.html`

Каждое — отдельное решение; во всех решает спека или сквозное решение брифа.

1. **«⇥ с указанием страницы»** (1b, подвал попапа) — не делается: спека вставляет цитату с
   ключом, дополнения к цитате в ней нет. Подвал палитры: «↑↓ выбор · ↵ вставить · esc
   закрыть».
2. **«Отчёт по цитатам папки»** с подсказкой опечатки и «Заменить на…» (1c) — не делается:
   вне спеки. Стиль карточки отчёта используется для списка ошибок чтения файлов (FR-008).
3. **Строка про стиль ГОСТ и выбор стиля** (1c) — не делается: «Вне скоупа».
4. **Список цитирующих заметок** (FR-005) в макете не прорисован — берётся подача
   строк-фрагментов макета 013 «Связи» 1a под карточкой выбранного источника.
5. **«Вставить цитату»** (US1) — палитра-поиск у каретки по образцу попапа 1b, вызываемая
   командой; набор `@` её не открывает (это 018, которой 017 отдаёт список источников).
6. **Ширина панели** 330px (1a) → общая колонка заметки 248px (сквозное решение 1): панель —
   третий режим `ui/src/note-panel/`, а не отдельная колонка. На телефоне — шторка снизу.
7. **«Подключить Библиография.bib» / «Выбрать другой…»** (1c) → «Создать references.bib» /
   «Указать существующий…» (§4, §5).
8. **Строка «@kuznetsov2020 — в .bib нет» с тегом «битая»** (1a) — сохраняется: это ключи,
   процитированные в заметках, но отсутствующие в источниках; данные даёт индекс цитат.
   Текст обобщён до «нет в файлах источников» (файл может быть и `.yml`).
9. **Тег «не цитируется»** (1a) и US2 AS2: переключатель «Не цитируются» в шапке списка.
   Выключен — показаны все источники, непроцитированные приглушены и помечены тегом;
   включён — показаны только они. До конца первого прохода (§8) тег не ставится: «не
   цитируется» по неполному индексу было бы неправдой.
10. **Тег «34 записи»** — число источников всех файлов; при ошибках чтения рядом тег с их
    числом.

## §17 Состояние панели и производительность чтения

**Decision**: показана ли панель, выбран ли режим «Источники», включён ли «Не цитируются» —
состояние устройства (004), тем же способом, что остальные режимы колонки заметки (013).

Чтение файлов источников (`sources_refresh`) — не массовая операция принципа X: файлов
единицы. Но файл на 10 000 записей разбирается в wasm в главном потоке; бюджет закрепляется
бенчмарком `sources_scale`, а `refresh` читает и разбирает **по одному файлу за вызов**
(`RefreshStep { pending }`), чтобы UI уступал циклу событий между файлами. См. plan.md →
Complexity Tracking.

## §18 Что 017 отдаёт фиче 018

`SourceEngine::sources_for_completion(prefix, limit)` → `Vec<SourceHit>` — тот же поиск §14 и
тот же тип, что у палитры. Дополнение по `@` целиком в 018; 017 только отдаёт список и
`citation_text` для подстановки.
