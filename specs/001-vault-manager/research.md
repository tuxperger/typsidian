# Research: Vault Manager

**Feature**: `specs/001-vault-manager/spec.md` | **Plan**: `plan.md`

Цель этого документа — закрыть технические неопределённости технического плана
(`/speckit-plan` user input) до перехода к дизайну (Phase 1). Каждый пункт: Decision /
Rationale / Alternatives considered.

## 1. Разделение ответственности NativeBackend / WebBackend внутри `VaultBackend`

**Decision**: `packages/core` определяет единственный публичный трейт `VaultBackend`
(open, list, watch, read, write, create, rename, delete). `NativeBackend` реализует его
через `std::fs`/`tokio::fs` и крейт `notify` напрямую — **без** обращения к JS-side
Tauri `fs`-плагину, поскольку `packages/core` на desktop/mobile компилируется нативно и
линкуется прямо в процесс Tauri, а не выполняется в его WebView. Разрешения на доступ к
файловой системе задаются статически через `fs.scope` в `tauri.conf.json`, а не
запрашиваются в рантайме через Tauri IPC. `WebBackend` реализует тот же трейт через
File System Access API (`window.showDirectoryPicker`, `FileSystemDirectoryHandle`) с
привязками через `wasm-bindgen`/`web-sys`.

**Rationale**: формулировка плана «доступ к файловой системе через Tauri fs API» была
неоднозначной — Tauri fs-плагин существует именно для случая, когда бизнес-логика на
JS/TS. У нас бизнес-логика — нативный Rust-код внутри самого приложения, поэтому
проходить через IPC-мост к себе же не нужно и добавляет накладные расходы без выгоды.
Прямой `std::fs` быстрее, тестируется через обычный `cargo test` и не создаёт лишней
зависимости UI-слоя от файловой логики (принцип I конституции).

**Alternatives considered**:
- Обращение к Tauri fs-плагину из Rust-ядра через IPC-клиент — отклонено: неоправданный
  крюк через IPC внутри одного процесса, усложняет тестирование ядра в изоляции.
- Единая реализация поверх абстракции виртуальной файловой системы (VFS) для всех
  таргетов — отклонено: File System Access API и POSIX/Win32 FS слишком различны по
  модели разрешений и асинхронности, чтобы скрыть их за одной низкоуровневой VFS без
  потери специфичных возможностей (например, нативных FS-событий).

## 2. Обнаружение изменений на native таргетах

**Decision**: `notify` с дебаунсингом (аналог `notify-debouncer-full`) и окном
подавления дублей ~300–500 мс на путь, коалescируя серии событий одного файла в одно
логическое событие (create+write+rename трактуются как единая пачка, если укладываются
в окно).

**Rationale**: сценарий из Edge Cases — внешняя программа пишет через временный файл и
затем переименовывает его в целевое имя — иначе даёт вспышку из нескольких сырых
ОС-событий (remove/create/rename) на одно смысловое изменение. Без дебаунсинга дерево
будет мигать и может показать заметку временно отсутствующей. Порог 300–500 мс — ниже
бюджета SC-004 (2 секунды на отражение изменения) с большим запасом.

**Alternatives considered**:
- Обрабатывать сырые события `notify` без дебаунсинга — отклонено: не проходит Edge Case
  про атомарную запись через временный файл.
- Полагаться только на периодическую сверку с диском (как в WebBackend) вместо
  нативных событий — отклонено: на native таргетах ОС-события доступны и дают меньшую
  задержку и меньшую нагрузку на CPU, чем поллинг; отказ от них не нужен.

## 3. Обнаружение изменений в WebBackend

**Decision**: File System Access API не имеет API подписки на изменения — используется
периодическая сверка (сравнение мгновенного снимка `{path, size, lastModified}` по всем
хендлам с последним известным состоянием индекса) с базовым интервалом 1 секунда и
адаптивным увеличением интервала при больших vault (снижение частоты полного обхода
пропорционально его последней измеренной длительности, чтобы не блокировать конкурентно
поллинг и пользовательские операции).

**Rationale**: интервал 1 секунда даёт запас относительно бюджета SC-004 (2 секунды) на
обработку и отрисовку после обнаружения. Адаптивность нужна, чтобы на большом vault
(близко к пределу 10 000 заметок, SC-002) сверка сама не стала узким местом и не
конкурировала за поток с обходом при первом открытии.

**Alternatives considered**:
- Фиксированный интервал 2 секунды (равный бюджету SC-004) — отклонено: не оставляет
  запаса на обработку и отрисовку, нарушение бюджета станет типичным, а не краевым
  случаем.
- Experimental File System Observer API — отклонено на данный момент: недостаточная
  межбраузерная поддержка на дату написания плана; WebBackend спроектирован так, чтобы
  подключить его позже как оптимизацию поллинга без изменения публичного трейта.

## 4. Обход vault и параллелизм на большом масштабе

**Decision**: На native — параллельный обход дерева пулом ОС-потоков (аналог `jwalk`).
На web — обход выполняется в Web Worker пошагово (chunked, с периодической отдачей
управления через `yield`/`postMessage`), без `SharedArrayBuffer` и без многопоточного
WASM.

**Rationale**: многопоточный WASM (`wasm-bindgen-rayon`) требует заголовков
`Cross-Origin-Opener-Policy`/`Cross-Origin-Embedder-Policy` на **всём** хостинге
веб-клиента — это операционное требование, которое выходит за пределы этой фичи и не
должно становиться скрытой зависимостью vault-manager. Однопоточный воркер с чанкингом
достаточен, чтобы удержать бюджеты SC-002 (пригодное дерево ≤3с, полный обход ≤10с) без
блокировки основного потока (FR-005, FR-019).

**Alternatives considered**:
- `wasm-bindgen-rayon` с `SharedArrayBuffer` — отклонено по операционной причине выше.
- Обход в основном потоке web-таргета с ручной нарезкой на кадры — отклонено: сложнее
  Web Worker без выигрыша, плюс блокирует более чувствительные к джанку взаимодействия
  на слабых устройствах.

## 5. Определение конфликта редактирования

**Decision**: Двухступенчатая проверка — сначала дешёвое сравнение `(mtime, size)` с
последним известным снимком; при расхождении хотя бы одного из них заметка помечается
кандидатом на изменение. Если у заметки есть несохранённые правки в буфере редактора,
кандидат подтверждается сравнением содержимого (хэш, например BLAKE3) — если хэш
содержимого на диске совпадает с последним сохранённым (не редактируемым) состоянием,
конфликт не поднимается (пусть даже mtime изменился без смыслового изменения). Хэш
также используется как основа для diff-представления (FR-024).

**Rationale**: mtime разрешение различается по файловым системам (в т.ч. до 2 секунд на
некоторых) и правится некоторыми программами без реального изменения содержимого —
чистое сравнение mtime даёт как ложные срабатывания, так и пропуски. Хэш содержимого
нужен для diff в любом случае, так что вычислять его только при уже заподозренном
кандидате — не лишняя работа, а переиспользование.

**Alternatives considered**:
- Сравнение только по mtime — отклонено: ложные конфликты на грубом разрешении mtime
  бьют по SC-006 (ноль автоматически перезаписанных правок, но также — минимум ложных
  тревог, иначе доверие к диалогу конфликта падает).
- Полное посимвольное сравнение содержимого при каждом FS-событии без дешёвого
  предфильтра — отклонено: неоправданная нагрузка на большом vault под непрерывным
  потоком внешних изменений (SC-005).

## 6. Персистентный кэш и его границы

**Decision**: Персистентный кэш — таблицы SQLite (`notes`, `links`) с одинаковой схемой
для нативного (`sqlx`, драйвер `sqlite`) и web (`wa-sqlite` поверх OPFS) путей, скрытые
за тем же трейтом `VaultBackend`/вспомогательным `IndexCache`-трейтом. Кэш — строго
производное, восстановимое состояние: при рассинхронизации с диском или повреждении
файла кэша система откатывается к полному обходу (FR-002) без потери пользовательских
данных, поскольку кэш никогда не является единственным носителем содержимого заметки.

**Rationale**: прямое требование архитектурного ограничения конституции («производное
состояние… восстановимо и MUST NOT быть авторитетной копией чего-либо, написанного
пользователем») и предпосылка SC-003 (повторное открытие ≤1с без полного пересканирования).

**Alternatives considered**:
- Держать индекс только в памяти без персистентного кэша — отклонено: не даёт SC-003
  на 10 000 заметок без полного обхода при каждом запуске.
- Хранить кэш как единственный сериализованный файл (например, JSON/bincode) вместо
  SQLite — отклонено: SQLite даёт инкрементальные апдейты и запросы по путям/связям без
  перезаписи целого файла на каждое изменение, что важнее на большом vault под потоком
  внешних изменений (SC-005).

## 7. Удаление заметки и «корзина»

**Decision**: На native — перемещение в системную корзину через кроссплатформенный
крейт (аналог `trash`), с откатом на безвозвратное удаление, если платформа/файловая
система корзину не предоставляет. На web File System Access API не имеет понятия
системной корзины — удаление через web необратимо, и диалог подтверждения на web-клиенте
обязан явно предупреждать об этом отдельной формулировкой (детали текста — задача
UI-слоя, не ядра).

**Rationale**: это прямое следствие уже принятого допущения в spec.md («в корзину, если
платформа это поддерживает») — здесь фиксируется, что web-платформа этого не
поддерживает, так что расхождение в поведении между таргетами не является дефектом
паритета (принцип II конституции касается паритета сборки и логики, а не идентичности
там, где сама платформа не предоставляет возможности).

**Alternatives considered**:
- Эмулировать «корзину» на web через скрытую подпапку внутри vault — отклонено:
  загрязняет vault пользователя служебными данными приложения и конфликтует с FR-004
  (директории, начинающиеся с точки, и так исключаются из дерева — эмуляция потребовала
  бы отдельного невидимого правила, что усложняет модель без запроса в spec.md).

## 8. Граница с модулем графа ссылок

**Decision**: Построение и хранение графа ссылок (`packages/core::graph`) — отдельный
модуль ядра, не часть vault-manager. Vault-manager уведомляет его о жизненном цикле
файлов (создан/изменён/переименован/удалён, включая внешние события) через тот же
`VaultEvent`, а для FR-026…FR-031 (какие заметки ссылаются на удаляемую/переименовываемую)
vault-manager запрашивает у graph-модуля обратные ссылки перед подтверждением операции.

**Rationale**: конституция перечисляет «парсинг ссылок, построение графа» и
«vault-manager» как отдельные пункты бизнес-логики ядра (принцип I) — трактуем это как
границу модулей, а не слияние в один. Это также держит vault-manager тестируемым в
изоляции от парсера Typst-ссылок.

**Alternatives considered**:
- Встроить хранение обратных ссылок прямо в vault-manager (таблица `links` внутри его
  же кэша) — рассматривалось и **частично принято**: физическая таблица `links` может
  жить в общем SQLite-файле кэша (см. §6) ради одной транзакции на изменение файла, но
  логика построения графа (парсинг ссылок из содержимого) остаётся в модуле `graph`,
  который пишет в эту таблицу. Vault-manager — потребитель обратных ссылок, не их автор.

## 9. Типы на границе WASM/JS

**Decision**: Все типы, пересекающие границу ядро↔UI (события `VaultEvent`, состояние
конфликта, состояние доступа к vault), определяются один раз в Rust с `serde`/`tsify`
(или эквивалентным генератором) и экспортируются как размеченные (discriminated union)
TypeScript-типы. Ручных параллельных TS-интерфейсов для этих типов нет.

**Rationale**: прямое требование принципа IV конституции («типы, пересекающие границу
WASM/JS, MUST порождаться из определений Rust или сверяться с ними»; `any` запрещён).
Размеченные объединения нужны, чтобы TS `strict` мог исчерпывающе проверять обработку
всех вариантов события/конфликта без `any`/`as`.

**Alternatives considered**:
- Ручные TS-типы, синхронизируемые вручную с Rust-определениями — отклонено: прямое
  нарушение принципа IV, риск незаметного расхождения при следующей фиче.
