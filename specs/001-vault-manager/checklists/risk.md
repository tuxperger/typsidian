# Risk Areas Checklist: Vault Manager

**Purpose**: Проверка полноты и однозначности требований спецификации в трёх областях
повышенного риска: потеря доступа к диску и разрешений (в первую очередь web),
конкурентные изменения одной заметки из нескольких окон или вкладок, поведение на vault
с 10 000+ заметок.
**Created**: 2026-08-07
**Feature**: [spec.md](../spec.md)

**Note**: Это чеклист к тексту требований, а не к реализации. Каждый пункт спрашивает,
достаточно ли ясно и полно что-то **записано в спеке** — не работает ли оно в коде.
Пункт считается пройденным, если ответ на вопрос «да» подтверждается конкретным местом
в `spec.md`.

**Пройден повторно 2026-08-07** после сессии `/speckit-clarify` (см. `## Clarifications`
в spec.md) и написания `plan.md`/`tasks.md`. Ниже — результат построчной сверки с
текущим текстом spec.md, не с состоянием на момент создания чеклиста.

## A. Потеря доступа к диску и разрешений

### Полнота требований

- [x] CHK001 Заданы ли требования, позволяющие различить временную недоступность vault и его безвозвратное удаление? [Gap, Spec §FR-020] — **Резолюция**: FR-020 не требует различать причину; поведение (уведомить, не трактовать как удаление, FR-035 удерживает правки) одинаково независимо от причины — различение причины не нужно по конструкции.
- [x] CHK002 Определено ли, что происходит с несохранёнными правками в момент потери доступа — где они удерживаются и как возвращаются пользователю? [Gap, Spec §US4, §US3 AS6] — Прямо отвечено FR-035: только в памяти сессии, теряются при закрытии приложения до восстановления доступа, пользователь предупреждён заранее.
- [ ] CHK003 Заданы ли требования к восстановлению работы после того, как доступ снова появился (переоткрытие, повторная сверка с диском)? [Gap, Recovery] — **Открыт**. FR-018 покрывает только случай «приложение было закрыто». Случай «доступ пропал и вернулся, пока приложение работало, без перезапуска» не описан в spec.md вообще — является ли это автоматическим восстановлением или требует явного переоткрытия vault пользователем, решено только на уровне plan.md/data-model.md (переход `Unavailable → ReadWrite` «только после явного переоткрытия»), а не как требование, прослеживаемое к spec.md.
- [x] CHK004 Определён ли режим «только чтение» для случая, когда чтение доступно, а запись — нет? [Gap, Spec §Edge Cases] — FR-036 прямо отвечает (осознанно без отдельного заранее объявленного режима, отказ — по факту неудачи записи).
- [x] CHK005 Заданы ли требования к обнаружению внешних изменений в период, пока разрешение на доступ ещё не подтверждено пользователем? [Gap, Spec §Assumptions] — Не применимо: наблюдение начинается только после успешного `open()`, а разрешение — предусловие самого `open()` (FR-007 + Assumptions о запросе разрешения при повторном открытии); отдельного «подвешенного» состояния наблюдения без открытого vault не существует.
- [x] CHK006 Определено ли, какие операции над заметками должны быть недоступны в интерфейсе при потере доступа к vault? [Gap, Spec §FR-009…FR-011] — Резолюция FR-036 (никаких операций не блокируется проактивно — отказ по факту неудачи) распространяется и на Unavailable по аналогии; отдельного проактивного блокирования спека не требует.
- [ ] CHK007 Определена ли судьба уже показанного дерева заметок в момент, когда vault стал недоступен? [Coverage, Spec §FR-020] — **Открыт**. FR-020 запрещает трактовать недоступность как удаление, но не говорит прямо, что дерево должно остаться видимым как есть (последнее известное состояние) — это разумный вывод из формулировки, но не зафиксированное требование.

### Ясность и измеримость

- [x] CHK008 Можно ли объективно проверить требование «понятная формулировка» сообщения о недоступности? [Measurability, Spec §FR-008] — Принято как качественный критерий, проверяемый ревью текста, а не числовой метрикой — согласуется с трактовкой аналогичных формулировок в FR-013/FR-014 по всей спеке; не требует отдельной клэрификации.
- [ ] CHK009 Перечислены ли причины отказа в доступе, которые система обязана различать в сообщении (нет прав, диск отключён, папка удалена, разрешение отозвано)? [Clarity, Spec §FR-008] — **Открыт**. FR-008 — одно обобщённое условие «папка недоступна или доступ к ней не получен», без требования различать причину в тексте сообщения пользователю.
- [ ] CHK010 Определено ли, что считается «разрушительным действием» над оставшимися файлами? [Ambiguity, Spec §US3 AS6] — **Открыт**. Термин используется в US3 AS6 без определения.

### Согласованность

- [x] CHK011 Покрыт ли требованиями случай, когда запомненный vault не может быть открыт без явного жеста пользователя? [Consistency, Spec §FR-007, §Assumptions] — US1 AS4 требует именно явного подтверждения перед открытием последнего vault.
- [x] CHK012 Учитывает ли порог SC-003 время ожидания решения пользователя по запросу разрешения, или измеряется с момента его выдачи? [Conflict, Spec §SC-003] — **Закрыт** сессией `/speckit-clarify` 2026-08-07 (раунд 2): отсчёт с момента получения доступа, ожидание системного диалога разрешения не в счёт.
- [x] CHK013 Согласованы ли требования к отказу в доступе при открытии vault и к потере доступа уже после открытия? [Consistency, Spec §FR-008, §FR-020] — Оба структурно параллельны (уведомить, не ломать приложение), противоречий нет.
- [x] CHK014 Определено ли, считается ли отказ пользователя выдать разрешение ошибкой, и совпадает ли это с формулировкой допущений? [Clarity, Spec §Assumptions] — Assumptions прямо: «отказ в разрешении не считается ошибкой».

## B. Конкурентные изменения из нескольких окон и вкладок

### Полнота требований

- [x] CHK015 Существует ли хотя бы одно функциональное требование для сценария с несколькими окнами, или он присутствует только в разделах Edge Cases и Assumptions? [Gap, Spec §Edge Cases] — FR-034 (добавлен сессией `/speckit-clarify`).
- [x] CHK016 Заданы ли требования к распространению создания, переименования и удаления заметки из одного окна в дерево другого окна? [Gap, Spec §FR-009…FR-011] — Покрыто через FR-034 → FR-016 (обнаружение внешних create/rename/delete не различает источник).
- [x] CHK017 Определён ли исход одновременного сохранения одной заметки из двух окон? [Gap, Exception Flow] — Резолюция через FR-034: запись одного окна — внешнее изменение для другого; порядок задаёт файловая система (последняя завершённая запись), спека не обязана вводить отдельный механизм для этого случая.
- [x] CHK018 Определено ли поведение при закрытии окна, в котором остался неразрешённый конфликт? [Gap, Exception Flow] — **Закрыт** сессией `/speckit-clarify` 2026-08-07 (раунд 2): FR-037 — предупреждение по аналогии с FR-035, потеря правок только по явному подтверждению.
- [x] CHK019 Заданы ли требования к предупреждению о битых ссылках, когда удаление инициировано в одном окне, а удаляемая заметка открыта в другом? [Gap, Spec §FR-027] — FR-027 сформулирован без привязки к окну, применяется одинаково.

### Ясность

- [x] CHK020 Определено ли, считается ли правка из другого окна того же приложения «внешним изменением»? [Ambiguity, Spec §FR-016] — Да, FR-034 / Clarifications Q1.
- [x] CHK021 Определено ли, распространяется ли диалог выбора версии на случай, когда обе версии сделаны одним и тем же пользователем в разных окнах? [Clarity, Spec §FR-021, §FR-022] — FR-034 не делает исключения для «того же пользователя» — общий конфликт-диалог применяется одинаково.

### Согласованность и границы

- [x] CHK022 Согласуется ли допущение о поддержке нескольких окон с отсутствием соответствующих функциональных требований? [Conflict, Spec §Assumptions] — Устранено: FR-034 закрывает несоответствие, отмеченное при первом прогоне чеклиста.
- [ ] CHK023 Заданы ли требования к блокировке одновременного редактирования, либо её отсутствие зафиксировано как осознанное исключение? [Gap, Spec §Out of Scope] — **Открыт**. Отсутствие блокировок подразумевается конструкцией FR-021…FR-025 (optimistic conflict resolution), но явного пункта в Out of Scope нет.
- [x] CHK024 Различаются ли требования для вкладок веб-клиента и окон desktop, где механизмы изоляции разные, или требования заявлены едиными? [Coverage, Gap] — Намеренно едины (FR-034 говорит «окна или вкладки» без различения) — соответствует принципу паритета таргетов.
- [ ] CHK025 Определено ли, применимы ли требования этого раздела к одному vault, открытому одновременно на разных клиентах одного устройства (например, web-вкладка и desktop-приложение)? [Coverage, Gap] — **Открыт**. Assumptions говорит «несколько окон приложения», не уточняя, распространяется ли это на разнородные клиенты одновременно.

## C. Производительность на vault с 10 000+ заметок

### Полнота требований

- [x] CHK026 Определена ли верхняя граница размера vault, до которой действуют заявленные пороги? [Gap, Spec §SC-002, §Edge Cases] — SC-002: 10 000 заметок, явно.
- [ ] CHK027 Заданы ли требования к потреблению памяти на большом vault? [Gap, NFR] — **Открыт**. Не заданы нигде.
- [ ] CHK028 Определён ли порог размера отдельной заметки, до которого гарантируется заявленное поведение? [Gap, Spec §Edge Cases] — **Открыт**. Edge Cases упоминает «необычно велика», без порога.
- [ ] CHK029 Определён ли предел глубины вложенности папок? [Gap, Spec §Edge Cases] — **Открыт**. Не определён.
- [x] CHK030 Нормирована ли стоимость построения и поддержания сведений о ссылках между заметками на масштабе 10 000 заметок? [Gap, Spec §FR-026, §FR-031] — **Закрыт** сессией `/speckit-clarify` 2026-08-07 (раунд 2): граф ссылок явно исключён из бюджета SC-002, строится в фоне без отдельного порога.
- [ ] CHK031 Заданы ли требования к деградации поведения при превышении заявленного масштаба? [Gap, Edge Case] — **Открыт частично**. SC-002 фиксирует «best-effort» по времени, но не фиксирует качественный пол (не должно быть краша/потери данных выше предела).

### Измеримость

- [x] CHK032 Определён ли аппаратный и платформенный базис, на котором проверяются временные пороги (desktop, mobile, web дают разные результаты)? [Measurability, Spec §SC-002] — Да, Clarifications Q4 + Assumptions (SSD, потребительское оборудование, единый базис для всех клиентов).
- [x] CHK033 Можно ли объективно измерить «пригодность дерева для навигации»? [Measurability, Spec §SC-002] — **Закрыт** сессией `/speckit-clarify` 2026-08-07 (раунд 2): верхний уровень иерархии виден и раскрываем, содержимое вложенной папки появляется по раскрытию.
- [x] CHK034 Квантифицирована ли «отзывчивость интерфейса» конкретным порогом задержки отклика? [Measurability, Spec §FR-005, §FR-019, §SC-005] — **Закрыт** сессией `/speckit-clarify` 2026-08-07 (раунд 2): задержка отклика на ввод ≤100 мс (FR-005, FR-019, SC-005).
- [ ] CHK035 Определено ли, при каком размере vault измеряется задержка отражения внешнего изменения? [Clarity, Spec §SC-004] — **Открыт**. SC-004 не привязан к размеру vault, при том что механизм обнаружения на web (поллинг) чувствителен к масштабу.

### Согласованность и покрытие

- [x] CHK036 Согласованы ли масштабы массовой операции: 1 000 файлов в критерии успеха и «сотни файлов» в описании edge case? [Consistency, Spec §SC-005, §Edge Cases] — Не конфликт: «сотни» в US3 AS5 — иллюстративный пример, находящийся строго внутри гарантии SC-005 (1000), а не альтернативный порог.
- [x] CHK037 Разделены ли требованиями первичный обход vault и повторное открытие ранее открытого vault как разные по стоимости сценарии? [Coverage, Spec §SC-002, §SC-003] — Да, SC-002 (холодный старт) и SC-003 (кэш) — разные критерии с разными числами.
- [ ] CHK038 Покрыт ли критериями успеха сценарий, где большой vault сочетается с потоком внешних изменений, а не только каждый по отдельности? [Coverage, Gap] — **Открыт**. Нет составного критерия «10 000 заметок + одновременный поток внешних изменений».

## D. Сквозные проверки

- [ ] CHK039 Прослеживается ли каждая из трёх областей риска хотя бы к одному измеримому критерию успеха? [Traceability] — **Открыт частично**. Производительность — да (SC-002…SC-005). Потеря доступа и многооконность опираются только на MUST-требования (FR-020/034/035/036) без отдельного числового SC (например, доли уведомлений о потере доступа или доли конфликтов, корректно пойманных из другого окна).
- [x] CHK040 Согласуются ли требования этих трёх областей с принципом корректной деградации в офлайне? [Consistency, Constitution §VII] — Да; все три области полностью локальны, сетевого взаимодействия не касаются вообще.
- [x] CHK041 Свободны ли требования этих областей от неявно зашитых технических решений (кэш, индекс, механизм наблюдения за файлами)? [Clarity, Constitution §III] — Да, проверено — ни в FR/SC этих трёх областей, ни в формулировках нет упоминаний конкретных механизмов реализации.

## Notes

- Отмечайте выполненное как `[x]`, находки записывайте рядом с пунктом.
- Пункт с маркером `[Gap]` означает, что требование в спеке предположительно отсутствует.
  Ответ «требование не нужно» — допустимый исход, но он должен быть записан в `spec.md`
  (в разделе `Out of Scope` или `Assumptions`), а не остаться устной договорённостью.
- Пункты с маркером `[Conflict]` указывают на противоречие между разделами спеки;
  их разрешение меняет содержание требований, а не только формулировку.
- Непройденные пункты — вход для `/speckit-clarify`. Пункты, которые останутся
  непройденными осознанно, должны быть отражены в спеке до `/speckit-plan`.
