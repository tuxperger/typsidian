# Quickstart: Vault Manager

**Feature**: `specs/001-vault-manager/spec.md` | **Plan**: `plan.md`

Сценарии для проверки, что фича действительно работает сквозь ядро и оба backend'а —
не полный набор тестов (он в `tasks.md`/реализации), а быстрый ручной/скриптовый
прогон golden path и ключевых edge cases.

## Предпосылки

- Собранное ядро под нативный таргет (`cargo build -p core`) и под
  `wasm32-unknown-unknown` (`wasm-pack build packages/core --target web`) —
  принцип II конституции требует оба таргета для готовности фичи.
- Тестовый vault: папка с ~20 заметками во вложенных подпапках, включая заметки со
  взаимными ссылками (для сценариев US5).
- Для web-сценариев — браузер с поддержкой File System Access API (Chromium-based).

## Сценарий 1 — Открыть vault и увидеть дерево (US1, FR-001…FR-003)

1. Запустить native-клиент (или web-клиент), выбрать тестовую папку как vault.
2. Ожидаемо: дерево появляется, повторяет иерархию папок на диске, скрытые/служебные
   каталоги (`.git` и т.п.) не показаны (FR-004).
3. Открыть произвольную заметку — содержимое отображается в редакторе (FR-006).

## Сценарий 2 — CRUD заметки из интерфейса (US2, FR-009…FR-015)

1. Создать заметку в подпапке через UI → проверить её появление на диске (`ls`).
2. Переименовать её → файл на диске переименован, открытый редактор не потерял связь
   с заметкой (FR-015).
3. Попытаться создать заметку с именем, уже занятым в той же папке → операция
   отклонена, существующий файл не тронут (FR-012).
4. Удалить заметку → исчезает из дерева и с диска.

## Сценарий 3 — Внешнее изменение без перезапуска (US3, FR-016…FR-020)

1. При открытом vault создать файл заметки напрямую в файловой системе (вне
   приложения) → должен появиться в дереве без перезапуска, в пределах ~2 секунд
   (SC-004).
2. Удалить файл заметки снаружи → исчезает из дерева.
3. Смоделировать атомарную запись редактором (временный файл + rename) → заметка не
   должна кратковременно пропадать/дублироваться в дереве (Edge Cases).
4. Отключить доступ к папке vault (например, размонтировать диск в тестовом
   окружении) → приложение показывает явное уведомление, не трактует это как удаление
   всех заметок (FR-020), несохранённые правки открытой заметки остаются в памяти
   сессии (FR-035).

## Сценарий 4 — Конфликт редактирования (US4, FR-021…FR-025, FR-037)

1. Открыть заметку, внести несохранённые правки.
2. Изменить тот же файл на диске снаружи.
3. Ожидаемо: диалог с тремя вариантами (оставить свою / принять внешнюю / посмотреть
   diff), ни одна версия не применяется автоматически (FR-021).
4. Проверить каждый из трёх исходов по отдельности (US4 Acceptance Scenarios 2–4).
5. Повторить шаги 1–2 в отдельном окне приложения и закрыть это окно, не выбрав ни один
   из трёх вариантов → ожидаемо предупреждение о несохранённых правках перед закрытием,
   потеря только по явному подтверждению (FR-037, US4 AS7).

## Сценарий 5 — Ссылочная целостность (US5, FR-026…FR-031)

1. Создать заметку A, сослаться на неё из B и C.
2. Удалить A через UI → перед удалением показан список [B, C] (FR-027).
3. Подтвердить удаление → B и C помечены как содержащие битую ссылку, находимы позже
   (FR-030).

## Сценарий 6 — Несколько окон (FR-034, Clarifications Q1)

1. Открыть один и тот же vault в двух окнах/вкладках приложения.
2. Отредактировать заметку X в окне 1 без сохранения.
3. Изменить ту же заметку X в окне 2 и сохранить.
4. Ожидаемо в окне 1: то же поведение, что и при стороннем внешнем изменении —
   диалог конфликта (не тихая перезапись, не отдельный механизм синхронизации окон).

## Сценарий 7 — Производительность на масштабе (SC-002, SC-005)

1. Сгенерировать vault из 10 000 заметок на эталонном оборудовании (research.md,
   SSD, современный потребительский класс — см. Assumptions в spec.md).
2. Открыть vault → дерево пригодно для навигации ≤3с, полный обход ≤10с (SC-002).
3. Закрыть и открыть тот же vault повторно → дерево готово ≤1с за счёт персистентного
   кэша (SC-003).
4. Смоделировать внешнее массовое изменение 1000 файлов (например, `git checkout`
   между двумя ветками с массовыми правками) → приложение приходит в соответствие с
   диском ≤15с, интерфейс остаётся отзывчивым (SC-005).

## Проверка паритета таргетов (принцип II конституции)

Каждый сценарий выше прогоняется как минимум один раз на native-сборке и один раз на
web-сборке (`wasm32-unknown-unknown`). Фича не считается готовой, пока оба прогона не
дают одинаковый наблюдаемый результат в терминах FR/SC (расхождения, допустимые по
research.md §7 — «только чтение vs корзина» — не в счёт).
