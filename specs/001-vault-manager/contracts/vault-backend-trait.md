# Contract: `VaultBackend` (internal core trait)

**Feature**: `specs/001-vault-manager/spec.md` | **Plan**: `plan.md`

Это внутренний контракт ядра (`packages/core`): единственная точка входа в
vault-логику, с двумя реализациями (`NativeBackend`, `WebBackend`) за одной
абстракцией, как того требует принцип II конституции (NON-NEGOTIABLE). UI не
обращается к `NativeBackend`/`WebBackend` напрямую — только к трейту.

Ниже — контракт по операциям и их наблюдаемым эффектам (в терминах FR/SC из spec.md),
не готовый код.

## Операции

### `open(root_path) -> Result<VaultHandle, OpenError>`

- Реализует FR-001, FR-002, FR-003.
- Успех эмитит начальный снимок дерева; если обход не завершился за 1 секунду —
  эмитит промежуточный прогресс (FR-005).
- `OpenError` различает как минимум: доступ запрещён (FR-008), путь не существует,
  путь — не папка. Ошибка не должна оставлять приложение в нерабочем состоянии.
- Если для `root_path` есть валидный персистентный кэш (research.md §6), `open`
  использует его для немедленного дерева и запускает сверку в фоне, вместо полного
  синхронного обхода (SC-003).

### `list() -> Stream<Note>` / `list_folder(path) -> Vec<Note>`

- Реализует FR-002, FR-003, FR-006. Не включает файлы вне определения заметки
  (Assumptions: только Typst-файлы) и исключения FR-004.

### `watch() -> Stream<VaultEvent>`

- Реализует FR-016, FR-017, FR-018, FR-019, FR-020, FR-034.
- Единственный канал, по которому UI узнаёт о внешних изменениях — включая изменения
  из другого окна того же приложения (FR-034) и изменения, накопившиеся, пока
  приложение было закрыто (обнаруживаются при `open`, а не задним числом здесь).
- Массовые изменения оборачиваются `BulkChangeStarted`/`BulkChangeSettled`
  (data-model.md).

### `read(path) -> Result<NoteContent, ReadError>`

- Реализует FR-006.

### `write(path, content, expected_snapshot) -> Result<(), WriteError>`

- Реализует FR-014, FR-017, FR-021…FR-025, FR-035, FR-036.
- `expected_snapshot` — версия диска, от которой отталкивался редактор (см.
  `EditConflict.disk_snapshot`). Если снимок на диске разошёлся с `expected_snapshot`
  на момент записи — операция отклоняется с `WriteError::Conflict`, а не
  перезаписывает молча (FR-021), даже если конфликт возник между обнаружением и
  записью.
- Если `access_state == ReadOnly`, возвращает `WriteError::AccessDenied` немедленно,
  не пытаясь писать (FR-036).

### `create(path) -> Result<(), CreateError>`

- Реализует FR-009, FR-012, FR-013.
- `CreateError::NameConflict` и `CreateError::InvalidName` проверяются до касания
  диска.

### `rename(from_path, to_path) -> Result<(), RenameError>`

- Реализует FR-010, FR-012, FR-013, FR-015.
- Вызывающий код (UI) обязан заранее запросить `backlinks(from_path)` и получить
  подтверждение пользователя, если список не пуст (FR-028) — сам `rename` не
  блокирует операцию молчаливой проверкой ссылок, чтобы не дублировать политику
  подтверждения между backend и UI.

### `delete(path) -> Result<(), DeleteError>`

- Реализует FR-011, FR-014.
- Как и `rename`, ссылочная проверка (FR-027) — ответственность вызывающего кода
  через `backlinks(path)` перед вызовом `delete`.
- Реализация выбирает корзину/безвозвратное удаление по правилам research.md §7.

### `backlinks(path) -> Vec<Note>`

- Реализует FR-026, FR-027, FR-028, FR-030. Делегирует модулю `graph`
  (research.md §8); vault-manager не парсит содержимое заметок сам.

## Инвариант паритета

Каждая операция выше должна иметь идентичную сигнатуру и наблюдаемое поведение (в
терминах FR) на `NativeBackend` и `WebBackend`. Расхождения, продиктованные
возможностями платформы (например, «только чтение vs корзина» из research.md §7),
документируются как таковые в реализации и не меняют публичную сигнатуру трейта.
