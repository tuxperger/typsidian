# Роадмап

Запрос пользователя: `$ARGUMENTS`

Роадмап — это не отдельный документ, а проекция каталога `specs/`. Каждая строка
`specs/ROADMAP.md` — фича со своей спекой; стадия выводится из того, какие
артефакты лежат в каталоге. Файл генерируется, руками его не правят.

```bash
.specify/scripts/typsidian/roadmap.sh            # перегенерировать specs/ROADMAP.md
.specify/scripts/typsidian/feature.sh list       # все фичи и стадии
.specify/scripts/typsidian/feature.sh next       # первая незакрытая по номеру
.specify/scripts/typsidian/feature.sh use 007    # сделать фичу активной
```

| Стадия | Что есть в каталоге | Следующая команда |
| --- | --- | --- |
| `spec` | spec.md | `/speckit-clarify` → `/speckit-plan` |
| `plan` | + plan.md | `/speckit-tasks` |
| `tasks 0/N`, `implement k/N` | + tasks.md | `/speckit-implement` |
| `done` | все задачи `[X]` | — |

## Зафиксировать идею

Идея, которую сейчас не реализуем, фиксируется спекой стадии `spec`:

1. `/speckit-specify <описание>` — одна идея, один вызов, один каталог.
2. В шапке спеки заполнить:
   - `**Priority**: P1 | P2 | P3` — P1: закрывает дыру в текущем сценарии или
     блокирует другие фичи; P2: заметная польза, независима; P3: расширение охвата.
   - `**Summary**:` — одна строка от лица пользователя, без технологий.
3. Спека для идеи такая же полноценная, как для фичи в работе: сценарии,
   требования, критерии успеха. Но объём соразмерен — маленькая возможность не
   требует пяти user stories.
4. После фиксации пачки идей вернуть активную фичу на ту, что в работе:
   `feature.sh use NNN`. `/speckit-specify` переписывает `feature.json` на новую
   спеку, и без этого шага хук `spec-gate` начнёт спрашивать на каждой правке.

Не плоди дубли: перед `/speckit-specify` проверь `feature.sh list` — возможно, идея
уже заведена или является user story существующей незакрытой спеки.

Спеки 001–010 написаны до роадмапа: строк `**Priority**` и `**Summary**` в них
нет, в таблице стоит прочерк. Дописывать их задним числом — только по просьбе
пользователя: приоритет — его решение.

## Выбрать следующую

`feature.json` — ненадёжный признак «что делать дальше»: он указывает на фичу
последней запущенной `/speckit-*` команды. Здесь почти все фичи висят в стадии
`implement` с хвостом незакрытых задач, поэтому порядок такой:

1. то, что пользователь назвал сам;
2. незакрытые в стадии `implement` — по номеру, раньше начатая раньше и
   закрывается (на неё опираются следующие);
3. затем P1 по номеру, P2, P3.

Перед тем как браться за хвост, прочитай открытые задачи: часть из них ждёт
внешнего условия (устройство, подпись, сеть) и не закрывается из сессии — такую
фичу не выбирают «следующей», а называют пользователю причину.

Зависимости записаны в разделе Assumptions спеки («зависит от NNN») — зависимую
фичу не начинают раньше той, от которой она зависит.

## Когда приоритет меняется

Правится строка `**Priority**` в спеке — роадмап перегенерируется хуком при
сохранении. Фича, от которой отказались, не удаляется: в шапке ставится
`**Status**: Rejected` и одна строка «почему» под ней.
